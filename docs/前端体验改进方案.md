# 前端体验问题分析与解决路径

> 依据：`web/app.py`、`web/frontend/src/App.tsx`、`Paper2Video-main/src/{pipeline,talking_gen,speech_gen,language_config}.py`
> 的证据 + 任务 `job_0918_224354_9487`（14 页，22:43:54 → 22:59 完成）的 `progress.jsonl` / `run.log` 实测复现。
> 五个问题都经过代码定位；其中 #2 #3 #4 有实测数据支撑，不是猜测。

## 总览

| # | 问题 | 性质 | 根因一句话 | 主要改动面 |
|---|---|---|---|---|
| 1 | 无参考音频入口，也不能选男女音色 | **功能缺失** | `--ref_audio` 参数早就有了，但 web 层从不传，音色被语言档位写死 | 后端新增上传端点 + 音色库 + argv 透传；前端加控件 |

## #1 参考音频上传 / 男女音色

### 现状（读代码得到的事实）

- 音色**完全由语言档位决定**，没有第二条路径：

  | 讲稿语言 | 参考音频 | 说明 |
  |---|---|---|
  | `en` | `assets/demo/zeyu.wav` | 上游作者的原声（男声英文） |
  | `zh` | `assets/demo/zeyu_zh.wav` | 本机用跨语言克隆造的**中文同音色**版本，配同名 `.txt` 作参考文本 |

  见 `language_config.py:101-125`（`SCRIPT_LANGS`）与 `:275-298`（`resolve` 返回 `ref_audio`/`ref_text`）。

- **流水线本身早就支持外部参考音频**，只是没人用：
  - `pipeline.py:133-135` 有 `--ref_audio` / `--ref_text`，`:180-181` 是 `args.ref_audio or lang["ref_audio"]` 的回落；
  - 但 `app.py:514-538` 的 `_build_argv` **完全没有这两个参数** → 永远走档位默认。
- 参考文本机制：优先读**与音频同名的 `.txt`**（`_sibling_ref_text`）；没有就交给 `Qwen3-ASR` 转写（`speech_gen.py:365-367`）。
  ⚠️ 已知 ASR 转写会出错（`language_config.py:304-307` 记录了实测："zeyu.wav 被转成错的英文"），而**错误的 ref_text 会直接拉低克隆保真度** → 上传音频时必须提示"能提供参考文本最好"。
- 界面上连"音色"这个词都没出现（`App.tsx` 全文件无 voice/audio 上传控件）。

### 解决路径

**A. 上传自己的参考音频（必做，成本低）**

1. 新增 `POST /api/voice`，**照抄 `/api/portrait` 的模式**（`app.py:824-892`）——流式落盘 + 按文件头嗅探 + 失败删壳 + 返回 warnings。这条模式已被验证过（当初复用 `/api/ingest` 就是错的，导致人像永远传不上去）。
2. 校验项（按参考音频的物理要求）：
   - 格式：`wav / mp3 / m4a / flac`，**按文件头判断，不看扩展名**；
   - 时长：**3~30 秒**，短于 3 s 直接拒（克隆会不稳定），长于 30 s 只警告（编码变慢）；
   - 采样率 / 声道：非 16k+ 单声道只警告不拒（解码链路会重采样）；
   - 峰值/静音：全静音或峰值过低给警告（克隆必然失败，现场很难判断原因）。
3. 可选上传**参考文本**（一个文本框），走 `--ref_text`；留空则回落到 ASR（界面注明"可能不准"）。

**B. 内置音色库（要选男女，必须有素材）**

- 目录约定：`Paper2Video-main/assets/voices/<name>.wav` + 同名 `.txt`（参考文本）。
- `language_config.py` 增加 `VOICES` 表，按 `(script_lang, voice)` 解析出 `ref_audio/ref_text`；`voice` 为空时保持现在的行为（**零回归**）。
- `/api/options` 下发可选音色列表（按 `script_lang` 过滤，避免"中文讲稿 + 英文参考音频"这种音色漂移组合）；
- 前端给每个音色一个**试听**按钮：新增 `GET /api/voices/{name}/sample` 直接返回 wav，`<audio controls>` 播放。**这一步很重要**——不试听就选音色，用户只能靠试错。

**C. 透传**：`_build_argv` 加 `--ref_audio`（+ `--ref_text`），config 加 `voice` / `ref_audio` / `ref_text` 三个字段。

**D. 素材来源（需要你决策，是这条路径唯一的卡点）**

Qwen3-TTS 的 `...-1.7B-Base` 是**克隆模型，不能凭空生成音色** —— 想要"男/女"就必须有对应的种子音频。三个选项：

1. **你提供**：各录 10~15 秒（中文男 / 中文女 / 英文男 / 英文女），成本最低、音色最可控、授权最干净；
2. **开源素材**：找许可明确（CC0/CC-BY）的多说话人语料切两段，需要核对许可，且音色风格未必适合学术讲解；
3. **先只做 A（上传）**：用"你自己上传"覆盖男/女需求，内置库后补。**这条最省事，且不阻塞其他四个问题**。

> 迁移提醒：种子音频是**素材**，要跟着仓库走（`assets/voices/`）；如果放外部目录，`HF_HOME` 那类"权重放英文目录"的约束同样适用于这里——**路径不能含中文、不能带盘符**。

## #2 "一直显示启动中"

### 根因（两条叠加）

1. **`job.phase` 全流程只被写 3 次**：建任务 `排队中`（`app.py:928`）→ `_run_job` 开头 `启动中`（`:611`）→ 收尾 `已完成/失败/已取消`（`:671-674`）。中间过程阶段**完全依赖 `progress.jsonl`** 的 `phase` → `_PHASE_LABEL`（`app.py:203-210`）。
2. **前置结构化那一步不写任何进度**：`_prepare_latex`（`:557-600`）调的是 `scripts/paper_struct.py`，它不经过 `progress_report`，且此时 `progress.jsonl` 还不存在 → `_progress_from_jsonl` 返回 None → 日志兜底要求出现 `start stage`（`:319-322`）→ 也没出现 → `phase` 保持 `启动中`。

**实测**：本次任务 22:43:54 建任务，结构化 + stage 1 期间界面一直"启动中"，直到 stage 1 真正开跑才有 `generating slides` 之类字样。你这次的结构化还**撞上限重试过一轮**，所以"启动中"停留得更久。

### 解决路径

1. **定义一张统一的阶段表**（唯一来源，后端下发，前端不硬编码），字段：`key / 中文名 / 权重 / 是否有页数`。
2. **补齐阶段上报**：
   - `_prepare_latex` 前后各写一次 `job.phase`（"分析论文正文" → "结构化 LaTeX"）——它本来就是 `await` 的，插两行即可；
   - `paper_struct.py` 也接入 `progress_report`（它已经在写 `report.json`，加一路 `report("struct")` 很轻）；
   - `_PHASE_LABEL` 补 `struct`；
   - **`_PHASE_LABEL.get(x, "")` 这个兜底要显式化**：现在遇到未知 phase 会回落成空串，能不能显示全靠上一层"空值不覆盖旧值"的巧合（`:349`）。应该改成**明确保留上一阶段**，并在日志里记一条"未知 phase"。
3. **前端从"一行文字"改成"步骤条"**：8 个阶段横排，三态（已完成 / 进行中 / 未开始），进行中的那个带当前页数与耗时。这比一个单词的 phase 好读得多，也顺带解决 #3 的"看不出还剩多少"。
4. **顺带修一个会误报的东西**：`stalled_seconds` 用的是 `progress.jsonl` 最后一条记录的时间戳（`:286-289`），而数字人阶段整个过程**不写记录**（见 #3）→ 那 5~10 分钟里 `stalled_seconds` 一路涨到 600+，界面会弹「**疑似卡住**」。这条误报会把刚才花力气修好的"日志可信度"又还回去。修法见 #3 的数据源改造。

## #3 进度条误导（幻觉最严重的一个）

### 实测复现

用真实 `progress.jsonl` 代入前端公式（`App.tsx:356-360`：`done = talking_done || tts_done`，`pct = done/total`）跑出的完整序列：

```
生成幻灯片  pct=  0%   (total=0 → 条是空的)
生成讲稿    pct=  0%
合成语音    pct=  7% → 14% → ... → 100%     ← 唯一一段真实推进（14 页 / 311 秒）
光标定位    pct=100%                        ← 停在满格
生成数字人  pct=  7%                        ← 从 100% 掉回 7%（回跳）
生成数字人  pct= 14% → ... → 100%
合成视频    pct=100%
```

**更关键的一条证据**：数字人那 14 条进度记录的**时间戳全部是 `22:58:21`**（相差 1~2 毫秒）：

```
ts=1789743501.435  22:58:21  done=1  page=0
ts=1789743501.436  22:58:21  done=2  page=1
...
ts=1789743501.445  22:58:21  done=14 page=13
```

原因是**批量路径的结构**：`talking_gen.py:536-568` 先 `rc = _run(cmd, ...)` 让 MuseTalk 一个进程把 N 页全跑完，**然后**才开始逐页取回产物并 `report()`。所以：

- 数字人真正在跑的 5~10 分钟里，`progress.jsonl` **一行都不写**；
- 界面上的表现是：条停在 100%、阶段停在"光标定位"、`stalled_seconds` 一直涨（见 #2 第 4 点）；
- 批量结束后 14 条记录一次性补报，条在几十毫秒内从 7% 冲到 100% —— 用户看到的就是"跑完了"。

### 解决路径

1. **总进度改成阶段加权**（权重来自实测耗时，可标定）：
   `结构化 8% · 幻灯片 12% · 讲稿 10% · 语音 30% · 光标 5% · 数字人 30% · 合片 5%`
   段内按页数线性 → 总进度**单调不减**（天然消除回跳）。
2. **给数字人阶段补真实数据源**（这是本条的核心，不补则权重再合理也是假的）：
   - 批量路径在 `_run(cmd)` 阻塞期间，起一个**后台线程**轮询"预期产物是否已出现"，出现一页就 `report("talking", done=k, total=N)`；
   - 数据源就是 `musetalk_batch_output(repo_dir, profile, avatar_id, key)` 算出来的路径（`talking_gen.py:548` 已经在用），**不需要改 MuseTalk**；
   - 顺带把 `stalled_seconds` 的误报消掉（有记录了）。
3. **页数计数器（pips）只在"有页数概念的阶段"显示**：幻灯片/讲稿/光标/合片阶段显示成"处理中"，不要显示一排空点。
4. **文案把话说白**：条上标 `总进度 42%`，主行标 `生成数字人 · 第 6/14 页`，并给一句剩余时间估计（后端已有标定值 `sys.calibration`，`App.tsx:196-214` 的模型直接复用）。
5. 段内没有真实数据源时（结构化/幻灯片/讲稿/光标），**明确写成"进行中（无逐页进度）"**，而不是画一条假装在走的条。

## #4 产物不自动显示

### 现状与实测

- **后端没问题**（对已完成任务实测）：
  `GET /artifacts` → 200 / 9 项；`GET /pages` → 200 / `total=14`；SSE 末帧payload 带 `status=done`。
- **问题在前端的拉取时机**（`App.tsx:303-319`）：产物与逐页素材**只在 `[jobId, job?.status]` 变化时拉一次**。
  - 运行期间 `status` 恒为 `running` → **运行中一次都不刷新**（这也意味着一整轮里产物区始终是空的）；
  - SSE 的 `onerror` 直接 `es.close()`（`:99`）→ **禁用了 EventSource 自带的重连**，且不给用户任何提示。**一旦这条流断开，`status` 就永远停在最后一次收到的值，"status 变化"这个唯一的触发点再也不会到来** —— 产物区从此冻结，只能刷新页面。
- 另一处相关缺陷：`jobId` 只存 React state（`:177`），刷新后回到"未选中任何任务"。

### 解决路径

1. **产物/逐页改成三个触发点**：运行中**轮询**（5 s，和任务列表同步节奏）+ `status`/`phase` 变化时拉一次 + 终态收敛一次。轮询只在 `running` 时开，完成后自动停（本地工具，开销可忽略）。
2. **修 SSE 的可用性**：
   - 恢复重连（指数退避，比如 1s→2s→5s，封顶 10s）；
   - 加**心跳**：后端每 15 s 发一个注释帧（`: keep-alive`），避免中间层按空闲超时掐断；
   - 状态**降级可见**：连续重连失败时在界面上写"实时连接已断开，正在重连（第 n 次）"，而不是静默冻结。
3. **产物区在运行中就显示**：把 `artifacts.length > 0 &&` 的门槛去掉，改成"有产物列产物 + 没有就显示当前阶段的占位"，这样 `1_merage.mp4` / `2_merage.mp4` 这类中途产物也能被看到。
4. **完成后自动收敛**：终态时自动拉一次并高亮成片；`<video>` 已经在做（`:692-694`），保持。
5. **`jobId` 持久化**（localStorage + URL `#job=xxx`），刷新后自动恢复查看对象 —— 这条和 #5 是同一个机制，可以一起做。

## #5 API key 本地保存

### 现状

- 前端：`apiKey` 只是 `useState`（`App.tsx:171`），**刷新即丢**；界面还明确写着「仅存内存，不落盘」（`:584`），与"保存到本地"直接矛盾，**文案必须同步改**。
- 后端：提交时把 key 塞进 `_SESSION_KEYS`（`app.py:58`），然后 `_run_job` 从它注入子进程环境（`:627-633`）。

### ⚠️ 先说一个必须先处理的坑（与"存本地"直接相关）

`_SESSION_KEYS` 是**模块级全局字典**，`/api/key/verify`（`:756`）和建任务（`:906`）都会写它。也就是说：

- 现在的行为是"**最后输入的人覆盖所有人的凭据**"；
- 单人本机用没问题；**迁到学校服务器多人使用后，A 的 key 会被 B 的任务拿去用**（B 甚至不知道自己花了 A 的钱）；
- 更糟的是：一旦把 key 存进浏览器本地，这个覆盖行为**更难被发现**（每个人的浏览器里都显示着自己填的 key，看起来一切正常，而实际执行用的是别人的）。

**所以 #5 要和它一起修**：把"服务端全局一份 key"改成**按任务注入** —— `_run_job` 从该任务自己的记录里取（内存 dict `{job_id: key}`，不落盘），删掉全局回落。任务重启后该 job 的 key 丢失没关系：前端本来就存着，续跑时随请求带上（与现在的行为一致）。

### 解决路径

1. **前端 localStorage 保存** `api_key` / `api_base`（key 值本身不加密，见下方边界说明），挂载时回填；提供一个「**记住本机**」勾选（默认勾上）+「**清除本地凭据**」按钮。
2. 文案改成"保存在本机浏览器（localStorage），不会上传到服务器"，把真实的边界说清。
3. **不要写进 URL / 不要写进 `job.json`**（`job.json` 会落盘，且现在的产物目录可能被打包归档）。
4. **打印/日志脱敏**：任何回显只给前 4 后 4 位（`sk-12****cd`），避免截图演示时泄露。
5. **安全边界要写进文档**：localStorage 是同源可见的，本机/内网工具够用；**如果将来做公网访问，必须换成服务端会话（HttpOnly cookie + 每用户隔离）**，不能靠 localStorage 存密钥。

## 一起做能省一次改动的小事

- `_PHASE_LABEL` 的未知值兜底（#2 第 2 点）与阶段表（#2 第 1 点）是同一处改动；
- 阶段加权条（#3）与步骤条（#2）共用同一张阶段表；
- `jobId` 持久化（#4 第 5 点）与 localStorage 封装（#5 第 1 点）共用一个 `storage.ts` 小模块；
- #4 的 SSE 重连 + 心跳是**纯后端/纯前端各几行**，建议顺手一起改，否则"断流即冻结"的隐患会一直埋着。
