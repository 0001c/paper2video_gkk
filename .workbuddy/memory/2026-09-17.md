### 关键技术发现（对后续改造很重要）

1. **`src/wei_utils.py` 的 `get_agent_config()` 有兜底分支**：任何不在白名单的模型名都会走
   `ModelPlatformType.OPENAI_COMPATIBLE_MODEL`。所以换 DeepSeek **只需设 `OPENAI_API_BASE`
   + `OPENAI_API_KEY`，再传 `--model_name_t deepseek-flash`，不必改代码**。
2. **GUI-Owl 1.5 与原代码坐标约定同源**：`cursor_gen.py:55` 本来就是
   `parse_action_to_structure_output(..., factor=1000, model_type="qwen25vl")`，
   而 GUI-Owl 输出也是 0-1000 归一化网格 → 替换近乎零改造。
3. **Hallo2 的死结不是显存而是 CUDA**：官方锁 torch 2.2.2/cu118，cu118 无 sm_120 编译目标，
   5070 Ti 装上即报算力不支持。InfiniteTalk 官方要求 CUDA ≥12.8，正好解掉。
4. **`infer_cursor()` 每句都重建 transformers pipeline**（`pipe = pipeline(...)` 写在函数内），
   被 Pool 反复调用 → 每句重载 4.4B 模型。应改模块级惰性单例。
5. **单卡必须改并行策略**：`pipeline.py` 的 `multiprocessing.Pool(processes=num_gpus)`
   每个 worker 各持一份完整模型，四套权重同时驻留约 24GB+ → 必须按阶段加载/卸载。
6. 项目路径 `E:\Development\26年\...` **含中文**，而 InfiniteTalk 明确要求纯英文路径。

## 工作内容：Phase 1 首次真正跑通 LLM 幻灯片生成（同日再续）

此前冒烟测试全部走演示资源、不经过 camel，所以「LLM 生成幻灯片」这一步其实**从没被执行过**。
本次真跑，一连暴露 5 个问题（提交 `b265486`）。

### 1. `mcp` 2.x 与 camel-ai 不兼容（ImportError）

```
ImportError: cannot import name 'FastMCP' from 'mcp.server'
```

- `camel-ai 0.2.90` 的 `camel/toolkits/base.py` 写的是 `from mcp.server import FastMCP`
- `mcp 2.x` 已把 FastMCP **改名 MCPServer**（`mcp.server.mcpserver.MCPServer`），且不再从
  `mcp.server` 顶层导出。报错信息自己就写了「pin `mcp<2`」
- camel-ai 的 METADATA 只写 `mcp` 没有上限，**属于上游打包缺陷**，必须在 install_deps 里兜住
- 处理：`mcp<2`（实测落到 1.30.0）；pip 卸载 2.2.0 时留下 `~cp` / `~cp-2.2.0.dist-info`
  两个残骸目录，会让 pip 每次告警 `Ignoring invalid distribution ~cp`，已手工清掉

### 2. 推理模型必须显式设 max_tokens

`ChatGPTConfig().as_dict()` 在 camel 里是**空 dict** → 不传 max_tokens，由服务端兜底。
deepseek-flash 是推理模型，**思维链计入 comprehension_tokens**（实测回一个 "OK" 就吃 18 token）。
长 Beamer 代码极易被截断，且截断后的报错点是 LaTeX 编译失败，**极难定位**。
处理：`wei_utils` 的 openai-compatible 分支显式 `max_tokens=16384`。
事后验证必要性：某次布局改进调用用掉 **13153/16384**，确实贴着上限。

### 3. `compile_tex` 的 `"error" in feedback` 子串判错 —— 最阴的一个

tectonic 在 Windows 上**每次编译（含成功）**都会往 stderr 打：

```
Fontconfig error: Cannot load default config file: No such file: (null)
```

这行字面量含 `error`，而上游判错方式是 `if "error" in feedback`（stdout+stderr 合并后的
**子串匹配**）→ **每一次成功编译都被判定为失败**，于是白跑一轮修复调用。
更糟的是 `re.findall(r'^(error: .+)')` 抓不到任何错误行（这行开头是 `Fontconfig` 不是 `error:`），
所以送给模型的是「The errors are: 」后面空白 —— 模型自然给不出有用回复。

处理：`compile_tex` 改为**按退出码判定**，返回 `(ok, feedback)`（调用点 5 处已同步）；
并过滤两类噪声（Fontconfig 行 + 几十条 `warning: accessing absolute path` 字体警告）。

> 顺带修掉一个隐藏问题：那些字体警告有几十条，会把真正的 `Overfull` 警告挤出
> `improve_layout` 里 `warning_info[:len//2]` 的前半段 → 树搜索会误判「无需改进」而静默跳过。

### 4. 破坏性写文件（上游 bug，实测已毁掉一次结果）

```python
if not isinstance(code, str): print("failed to fix code")   # 只打印，不停
with open(beamer_save_path, "w", encoding="utf-8") as f: f.write(code)  # open 先截断！
```

`open(path,"w")` 会**先把已经能编译的 slides.tex 截断成 0 字节**，再因 `write(None)`
抛 TypeError。结果：模型没生成出代码 → 反而把上一版好文件毁掉。
处理：生成/修复拿不到可用字符串时**保留上一版并停止**，绝不写 None。

### 5. `--if_tree_search` 是个死开关

`pipeline_light.py` 调用 `latex_code_gen_upgrade()` 时**没有转发** `if_tree_search`，
而该函数默认 `True` → 用户传 `False` 也照样跑「每帧 4 候选 + VLM 选优」（实测白跑 7 次 VLM 调用、多花约 3 分钟）。
处理：显式转发。

## 换型：InfiniteTalk → LongCat-Video-Avatar-1.5（2026-09-17 03:40，用户决策）

```

  → quanto qbytes.create → MarlinFp8QBytes.__init__
  → marlin/fp8/packed.py:183  torch.ops.quanto.pack_fp8_marlin
  → quanto extensions/cuda:167 gptq_marlin_repack
  → torch.utils.cpp_extension.load(...)   ← 现场编译
```

**重要认知**：量化表里存的是普通 fp8（606+168 条全是 `qfloat8_e4m3fn`），Marlin 是 quanto
在 capability ≥ 8 的 CUDA 设备上**自动升级**的排布优化 —— 是**性能**需求，不是正确性需求。

编译要同时满足：ninja 在 PATH（venv 未激活时不会自动加）+ `cl.exe` 在父进程 PATH
（torch 2.11 的 `_write_ninja_file` 在父进程跑 `where cl`，VC 环境却只补给 ninja 子进程）
+ nvcc 支持目标 arch（**本机 12.6 最高 compute_90，没有 compute_120**，只能编 `9.0+PTX`）。
前两条可解，第三条与 quanto 的 `-DQUANTO_CUDA_ARCH=1200` 宏是否冲突未能验证 → 用户决定换模型。

### 新模型要点（`meituan-longcat/LongCat-Video-Avatar-1.5`，MIT）

**通用教训**：判断「某库能否在 Blackwell 上跑」不能只看「有没有 win wheel」，
还要看它的 **CUDA kernel 编到了哪个 compute capability**。`xformers` 尤其容易踩：
它的官方 wheel 长期只编到 sm_90 以下。

### ③ 显存：三模型常驻 15.7GB（96%），采样必 OOM

int8 DiT(15.1GB) + UMT5(9.4GB bf16) + Whisper(1.5GB) + VAE 全在卡上 = 15723/16303。

### ④ ⚠️⚠️ 根本性障碍：三种注意力后端全部不可用（换型后最大的坑）

数字人 DiT 的主 attention 序列长度 = **36480**（空间 1520 × 24 帧 latent），
三条路**全部堵死**：

| 后端 | 状态 | 原因 |
|---|---|---|
| flash-attn | 装不了 | Windows 无官方 wheel，只有 sdist 需编译（MSVC + CUDA 12.8，本机 nvcc 12.6 无 sm_120） |
| xformers 0.0.35 | 有 wheel 但**用不了** | CUDA kernel 只编到 sm_90，Blackwell(sm_120) 报 `NotImplementedError: capability (12,0) too new` |
| torch SDPA | 能用但**慢到不可用** | O(N²) 在 N=36480 上，8 分钟卡在 Denoising 0/8（第 0 步都没走完） |

**这是 InfiniteTalk → LongCat 换型后踩到的第二个、也是最致命的 sm_120 兼容问题。**

已确认 xformers 的 kernel 编译上限：`fa3F`/`fa2F`/`cutlassF-pt` 全部 `requires
capability <= (9,0)`。**教训再强调一次**：判断库能否在 Blackwell 上跑，必须看它
kernel 编到的 compute capability，而不是有没有 wheel。xformers 官方 wheel 长期
只编到 sm_90 以下，Blackwell 用户是「装得上但跑不动」。

**可能的出路（待评估）**：
1. 编译 flash-attn 2.8.x（需要 CUDA 12.8 toolkit，本机 12.6 需升级）
2. 找预编译 sm_120 的 flash-attn wheel（社区，风险高）
3. 换更小的分辨率/帧数降低序列长度（治标，36480 即使减半 SDPA 仍慢）
4. 接受「数字人环节放服务器 8×A6000 跑」（服务器 Linux + 48GB，flash-attn 可装，
   且 A6000 是 sm_80 有现成 wheel）—— 这其实最符合导师「后续上服务器」的规划

### ⑤ 已证伪的两条路（实测结论，别再重试）

**降帧数无效**：`num_frames=45`（序列 18240，减半）实测 SDPA 第 0 步仍卡 3 分钟+
（GPU 98% 但日志 185s 无更新）。SDPA 的 O(N²) 在 18240² 和 36480² 都是天文数字，
减半只从「永远算不完」变「还是算不完」。

**显存卸载不可行**：想采样前把 UMT5/Whisper 移 CPU，但 pipeline 的
`_get_t5_prompt_embeds`（pipeline_longcat_video_avatar.py:174）在采样循环里

device mismatch。且 `generate_ai2v` 不接受预计算 prompt_embeds，无法在中间插入卸载。

**结论**：本机（RTX 5070 Ti + Windows + sm_120）跑数字人**不可行**，根因是
「视频 DiT 的大序列注意力」×「Blackwell 无预编译高效注意力 kernel」叠加。

**耗时回归（每页耗时 vs 音频秒）**：`耗时 ≈ 82.4 s + 3.05 × 音频秒`
→ **固定开销 82 s/页，占 12 页总时间的约 59%**（16.4 min）。
证据：音频跨度 14.5~22.2 s（1.5 倍），耗时只 117~146 s。

### 优化结论（已论证，待实施）

因为 **GPU 和 CPU 都没饱和**（7% / 26%），这是延迟+IO 受限负载，并发收益大。
但两条：

- **并发度由 CPU 核数定，不是显存**。且**必须给每个子进程设 `OMP_NUM_THREADS`**
  —— 否则 N 进程 × 8 OMP 线程抢 8 核，会全面变慢（这类任务并行的头号翻车点）。
  8 核建议并发 2，`OMP_NUM_THREADS=4`。
- **先做批量模式**：MuseTalk 自带 `scripts/realtime_inference.py`，YAML 支持
  `avator_1: {preparation: True, video_path: ..., audio_clips: {audio_0: ...}}`
  —— 一个进程跑完所有音频，模型只加载 1 次，人脸 latent 缓存成 `latents.pt`。
  我们的 12 页共用同一张参考图，正是它的最佳用例。预期能吃掉固定开销的大头。

### PIP 口型可见度（本次特意验证的点）

PIP 几何：`size = max(1512//6, 2016//6) = 336`，右上角 offset=10
→ 区域 x 1670..2006, y 10..346。头像原图 658x660 → 336x336。

| 指标 | 值 |
|---|---|
| PIP 内人脸框 | x 1775..1893, y 53..201（**148 px 高**，占画面高 9.8%） |
| 嘴部带 | 118 x **41 px** |
| 嘴部/眼部 帧间变化比（成片内） | **16.4**（独立视频里是 89.8） |
| PIP 外区域帧间差 | **0.000**（幻灯片完全静止，叠加未破坏原图） |

结论：口型运动在 PIP 里**存在且可测**，但比值从 89.8 掉到 16.4 —— 因为
336px 缩放 + 二次 H.264 编码把细节抹平、噪声底抬高。这是 1/6 PIP 尺寸的

## 批量模式优化完成（2026-09-17 07:21）—— 提交 1272703

### 结论：12 页 talking 从 1608.2s 降到 334.2s（**4.81×**），全流程 27.8min → 6.7min

产物一致性：12 页逐页时长与逐页模式**完全一致（差 0.000s）**；成片 198.92s =
音频总长。唯一差异是每页少 1 帧（上游线程写帧的 off-by-one，40ms）。

### 做法：不重写推理循环，交给 MuseTalk 自带的批量入口

`scripts/realtime_inference.py` 的 YAML 就是为「一个进程跑完多段音频」设计的：

```yaml
pv_<runid>_0:
  preparation: true          # latents.pt 算一次，复用它名下所有音频
  video_path: <暂存后的参考图>
  audio_clips:
    page_000: <暂存的音频>
    page_001: ...
```

按「暂存后参考图的 sha1」分组 → 一组一个 avatar。当前各页共用同一张参考图，
所以实际只有 1 个 avatar；按指纹分组让逻辑在「每页不同人像」时也成立。
档位新增 `batch` 字段；页数 <2 时退回逐页（没收益）。单页入口保留（冒烟测试用）。

### 三个上游坑（都在命令拼装/调用侧解决，没改第三方代码）

1. `--unet_config` 默认值**指向 v1 的路径**，必须显式覆盖，否则加载失败。
2. **不认 `--result_dir`**：`Avatar.base_path` 硬编码 `./results/<version>/avatars/<id>`，
   产物得去 MuseTalk 仓库里取。另外它**没有 `--use_float16`**（硬编码 .half()），
   所以批量路径恒为 fp16。
3. `preparation=True` 且 avatar 目录已存在时会 **`input()` 询问是否重建** ——
   非交互子进程里直接卡死。**用每次运行唯一的 avatar_id 绕过该分支**
   （同时也绕过它那条 rmtree）。但它留下的 avatar scratch 目录要清掉，
   且**必须在新解释器里删** —— 沙箱 safe-delete 开关是 shim 在 import 时读的，
   本进程内改 os.environ 无效。已在 talking_gen 里起子进程清理，实测 0 残留。

### 方法论：为什么先做批量而不是先上并发

先量后改。回归得 `耗时 ≈ 82.4s + 3.05×音频秒` → 固定开销占 59%；而 GPU 只用 7%、
整机 CPU 26%、单进程 CPU 爆发 646% 后长期只占 1 核 —— **两边都没饱和**，
说明瓶颈是「每页重起进程 + 重读 3.2GB 权重 + 重算 latent」的固定开销，
不是算力。所以确定性的批量优化优先，并发（需要限 OMP_NUM_THREADS，
否则 N 进程 × 8 线程抢 8 核）留作第二层。

### 中文论文支持调研（用户提问）

**关键区分：中文论文 → 英文视频，现在开箱可用；中文论文 → 中文视频要改 4 处。**
（`slide_beamer_prompt.txt` 第一行就写死 "generate a complete **English** PPT"，
这是上游的设计选择而非缺陷 —— 输入论文是什么语言都行，输出恒为英文。）

中文视频需要：① 中文版 prompt；② LaTeX 模板加 `\usepackage{ctex}`；

**实测：tectonic 编中文 beamer 开箱可用** —— 它会自动拉 ctex/xeCJK + 自带的
Fandol 中文字体，PDF 文字可提取（FandolHei）。不需要装任何东西。

## 输出语言可选：幻灯片/讲稿双轴（2026-09-17 07:50）—— 提交 dbce860

### 设计判断：语言是两个独立的轴，不是一个开关

| 幻灯片 | 讲稿 | 场景 |
|---|---|---|
| en | en | 国际会议 / 投稿（原默认） |
| **en** | **zh** | **英文 slides + 中文讲解 —— 国内组会、中文答辩**（国内最常见） |
| zh | zh | 国内汇报 / 科普（幻灯片侧尚未实现） |

单个 `--video_lang` 开关恰会把中间那行排除掉（既不全英也不全中）。
实现为 `--video_lang {en,zh}` 预设 + `--slide_lang` / `--script_lang` 精确控制。
单一真源在 `Paper2Video-main/src/language_config.py`。

**不需要检测输入论文语言**：幻灯片是 LLM 重写的、讲稿是 VLM 看幻灯片图写的，
输入语言不影响输出，只需控制 prompt 要求的输出语言。

### ⚠️ 最关键的洞察：光标描述必须始终是英文

讲稿文件格式 `<讲稿句子> | <cursor description>`。竖线右侧**不是内容**，而是喂给
GUI-Owl 的 grounding 指令 —— `cursor_gen.build_grounding_prompt` 那段 system
prompt 是从上游照搬的**英文工具调用协议**（注释明确写"不能自创提示词"）。
它最终只变成 `cursor.json` 里一个坐标 `[x,y]`，**不出现在成片里**
（字幕取 `text`/`raw_text`，即竖线左侧）。

所以中文讲稿配英文光标描述最优：讲稿/TTS/字幕中文，定位模型仍拿到训练时的语言。
已写进中文 prompt 的硬性要求。**实测 12/12 页都遵守**（左边中文、右边无汉字）。

- 英文版实测每页 16.6 s（198.9 s / 12 页）
- **中文 TTS 实测语速 5.76~5.86 汉字/秒**（57 字 → 9.9 s）

照搬"50 字"会让成片只有应有长度的约六成、语速明显偏快。纯配置看不出来，
**只有对比成片时长才会暴露**。

## 光标乱指：诊断与修复（2026-09-17 23:40）—— 提交 d67758c

用户反馈：中文成片里「每张幻灯片开头能准确指到对应文本，但通常第二句就去指
幻灯片中的图片了」。这个描述本身就是最强线索 —— 开头准、之后乱。

### 根因（铁证）：timesteps() 用**英文词边界**给**中文句子**算时长

```python
words_num = len(re.findall(r"\w+", sentence.lower()))   # cursor_gen.py 旧实现
```

`` 是词边界，中文不写空格 → 一整串汉字只命中一次。实测第 0 页（讲稿共 133
个有效字符，Qwen3-ForcedAligner 输出 **89 个逐字单元**）该计数是 **3 / 9 / 3**，
而真实有效字符是 36 / 51 / 46，**差一个数量级**。

于是指针 `current_idx` 走得极慢，每句都只能从「音频开头附近」取值：

| 句 | 旧时间轴 | 真实长度 |
|---|---|---|
| 句0 | 0.08 → 0.56（0.48s） | 36 字 |
| 句1 | 0.56 → 3.20（2.64s） | 51 字 |
| 句2 | 3.20 → **19.92**（16.72s） | 46 字 |

末句的 19.92 来自 `result[-1]["end"] = get_audio_length(...)` 的**无条件兜底**。
44 句里 **12 句时长 < 0.6s**，末句独吞 84~93%。

**后果不是「精度差一点」，而是光标在错误的时间停在错误的位置**；而末句常讲流程图，
观感就成了「总跑去指图片」。英文链路不受影响（有空格，`\w+` 就是词），
**所以这个缺陷只在中文模式下暴露**。

### 修法：按「有效字符」统一口径

把对齐单元展开成**字符级时间轴**（英文词在它的 start/end 之间按字符数插值），
再按句子的有效字符数单调切分。中英同口径、保留对齐器的真实语速与停顿、
单调无缝。**关键前提经实测成立：对齐侧与句子侧有效字符数完全相等（133 == 133）。**
末句 end 改为只在明显短于音频时才补齐。

### 验证（三独立证据）

1. 时长 <0.6s 的句子：**12 条 → 0 条**；页0 三句 0.6/2.6/16.7 → **5.5/7.3/7.0**，
   与字符数比 36:51:46 吻合。
2. 重跑光标定位（仅此一环，用现有讲稿+音频）→ 新 cursor.json 时间轴 0 → 287.84s。
3. **成片抽帧检测红色光标位置**：变化时刻 0.0/6.0/13.0/20.0/27.5/36.5 与句子
   边界 0.0/5.5/12.8/19.8/27.3/36.1 **逐一对应**（0.5s 采样精度内）。
   —— 修复前每页只有 1~2 次有效变化。
4. 重跑 stage 3 合片，退出码 0，`3_merage.mp4` 288.98s / 2016x1512 / 带音轨。

### 第二层问题：**描述与幻灯片实际内容脱节**（尚未修）

实测 44 条 cursor 描述，只有 **6 条（14%）**的关键词能在 `slides.pdf` 的文本块里
找到。VLM 写的是**概念化表述**而非幻灯片原文：

- `cursor on the title banner`（幻灯片上没有 "title banner" 字样）
- `cursor on the authors and affiliation`（只有人名，没有 "authors"）
- `cursor on the Limitations box`（该页没有 "Limitations" 字样）
- `cursor on the presentation icon`（×3，最模糊）

而 GUI-Owl 的 system prompt（项目注释明确写「必须照搬官方工具调用协议，不能自创」）
要求它找 **buttons / links / icons** —— 它是 **UI grounding 模型**，训练目标是找
可点击控件。幻灯片上没有这些，它拿到幻灯片上不存在的词**只能猜**。

另有 **8 条句子的描述完全重复**（如页10 句0/句1 都是 `the Limitations box`
→ 落点都是 (40,373)）→ 观感是「指着一个地方长时间不动」。

### 建议的下一步（已论证，未实施）

### 顺带修掉的两处「跑起来就崩」

1. `pv_env.gpu_list()` 现在兼容 list：`pipeline.py` 的 `--gpu_list` 走 `str2list`
   得到 `[0]`，而 `gpu_list()` 只做 `str(raw).split(",")` → `int("[0]")` 抛
   `ValueError` → **pipeline.py 的 stage 2 只要调用就崩**。`pipeline_light` 传的是
   str，所以一直没暴露。
2. `cursor_gen` 里两处 `cv2.imread` 改为 PIL：OpenCV 走 Windows ANSI API，
   **读不了含中文的路径**。生产目前只是因为 `--result_dir` 传的是**相对路径**
   （字符串本身纯 ASCII，由系统按 cwd 解析）才没暴露；改用绝对路径就崩在取尺寸。

### 诊断方法论（值得复用）

- **`\w+` 这类「英文正则」用在中文上是静默失效**：不报错，只是数量级不对。
  中英混排项目里，凡是「按词计数/切分」的地方都要单独验证。
- **验证定位质量需要 ground truth**：`slides.pdf` 的文本块 bbox 就是现成的
  ground truth（LaTeX 编译产物结构精确）。比「肉眼看成片」可靠得多。
- **抽帧检测光标质心**是验证「时间轴是否正确」的客观手段：红像素质心 vs 句子边界。
