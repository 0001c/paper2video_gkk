`prompts/slide_beamer_prompt_zh.txt`（连同"绝对不要用 tabular/hline/toprule"）。

### 顺带加固：extract_beamer_code 过于脆弱

原实现一行正则，只认裸 `\documentclass{beamer}` 且强制要求 `\end{document}`：
  * 不认中文常用的 `{ctexbeamer}`；
  * 输出被 max_tokens 截断时整段被丢弃（推理模型的思维链会挤占输出预算），
    而截断代码常常只差一个收尾，交给下游编译纠错完全可能救回来。
改为「优先取完整环境；取不到则取到末尾并补 `\end{document}`」，
并把失败信息补全（返回长度 / 是否含 documentclass / 首尾 500 字符）。

### Qwen3-TTS 退化护栏（已实现并实测）

实测 `generate_voice_clone` 接受 `max_new_tokens` 并透传到底层 generate：
**80 token -> 6.32s，400 token -> 14.64s**。而 Qwen3-TTS 是 **12Hz** 编码
=> **音频秒数 ≈ token 数 / 12**。据此加两级护栏（`speech_gen.py`）：
1. 整页生成给宽松上限（估算时长 ×2.5 + 180 token）；
2. 撞上限即判为退化，改为**逐句生成再拼接**（句间补 0.35s 静音）。

上限充裕性已用 gkk_zh 真实讲稿自检：第 0 页估算 23.1s / 上限 72.8s / **实际 17.2s**，
最紧的第 3 页估 35.7s / 上限 104.3s，**不会误杀正常语速**。

### `--reuse_script`（为省钱而加）

讲稿生成是整条链路里**唯一必须联网付费**的一步（VLM 读全部幻灯片）；
TTS / 光标定位 / 数字人 / 合片全是本地计算。所以后续阶段失败、只重跑 stage 2 时，
没有这个开关就要**再付一次 VLM 费用**。现已支持：
`--reuse_script True` 时若讲稿存在且通过 `validate_script_output` 则跳过 VLM 调用。
顺带把写讲稿的 `open(path,'w')` 加上显式 `encoding='utf-8'`（读回处固定 utf-8，
写入端不该依赖环境默认编码）。

## H5 可视化改造方案（2026-09-18 设计，待用户确认）

方案文档：`docs/Web可视化方案.md`。调研出的四条硬事实：

1. **入口吃 LaTeX 源码目录，不是 PDF**：`--paper_latex_root` 下必须有 `main.tex`（文件名写死）。
   `assets/papers/gkk_mengxin/main.tex` 头部注释写明「由 PDF 提取重建」—— **这一步是人手工做的，

2. **只需一组 API key**：`OPENAI_API_KEY` / `OPENAI_API_BASE`。`.env` 里的 `DASHSCOPE_API_KEY`
   只在 `scripts/check_env.py` 被检查存在性，**流水线根本不读**（TTS/ASR 全是本地权重）。
3. **成本可精确计量**：`result/<名字>/token.json` 是现成的。实测 `gkk_en` = 55,608 token
   （slide_gen 13,265 + 讲稿 42,343），**讲稿占 76%** → `--reuse_script` 是省钱主力，H5 上应做成醒目按钮。
4. **进度可零改造拿到**：日志格式稳定（`[speech_gen] 第 N 页合成完成`、`[talking_gen] 第 N 页完成`，
   总页数可从 `slides_rendered.pdf` 的页数确定），后端 tail + 正则即可；建议 P1 再加 `progress.jsonl`
   以摆脱对日志文本的依赖。

- **用子进程不用 import**：显存释放靠进程退出保证（单卡 16GB 必须按阶段加载/卸载），

API key 提交前**自检**（余额耗尽在 DeepSeek 侧会伪装成空响应，必须明确区分欠费/鉴权/网络三类）。

## 前端依赖安装：三次失败的排查（2026-09-18 傍晚）

### 现场

`web/frontend`（React + Vite + TDesign）装依赖，pnpm 连续两次失败、npm 一次失败。

### 三个根因（都不是"网络慢"这么简单）

**① pnpm 挂在链接阶段**：日志停在 `Packages: +92` 后不再更新；进程 10 秒只耗
0.06 秒 CPU（≈0.6%），20 线程全阻塞。→ 放弃 pnpm。

**② `npm` 在 Bash 工具里返回「拒绝访问。」**：Windows 上 npm 是 `npm.cmd`，
需经 `cmd.exe` 启动，**被沙箱安全策略拦**。输出写成 16 字节 UTF-16LE 文件，
按 UTF-8 读是乱码（`b~0` 之类），极易误判成"npm 没执行"。
→ 改用 `node <npm-cli.js>` 直接执行，绕开 cmd.exe。

**③ 装得慢的真凶是 registry 并发/代理排队**，不是磁盘：
- 实测本机文件操作**很快**（创建 5393 文件/秒、删除 4257 文件/秒），
  推翻了"腾讯电脑管家拖慢一切"的既有印象 —— 至少 E 盘不小文件不受影响；
- 同一 tarball（rollup-4.63.3.tgz）走代理 0.31s（1.76 MB/s）、
  绕过代理 0.12s（4.44 MB/s），**两者都快**；
- 但 `loglevel=http` 显示单个包耗时 35s / 50s / **126s** —— 这是**排队+重试的总时长**，
  不是纯下载。npm 默认并发有限，经代理时排队被放大。

### 方法论：怎么判断"卡死还是在算"

**只看日志会误判**（pnpm 链接阶段完全不打日志）。要同时看两个量：
1. 进程 `cpu_times()` 的**增量** —— 不涨 = 被阻塞（而不是在算）
2. 目标目录的**文件数增量** —— 不涨 = 没在写盘

两个都不涨，才是真卡死。只看目录体积也会错（体积早就到位、链接还在做）。

### 最终做法

交给使用者在**自己的终端**手动装（不受沙箱限制，`npm` 可直接用），
`node_modules` 保留增量补齐（终止时已有 60 个顶层包、8015 个文件）。

## 端口 8848 被占 + Windows SO_REUSEADDR 的坑（2026-09-18）

使用者启动服务时报 `[Errno 10048] ... ('127.0.0.1', 8848)`。

**占用者是我自己**：pid 16080（`python -u web/app.py`，跑了 37 分钟，之前后台启动没关），
外加同命令的子进程 27360。已终止，端口释放。

顺手把这件事修成了能力（`web/app.py`）：
- 启动前自行探测端口，被占时**打印占用者**（进程名/pid/已运行时长）并给三条出路
- 新增 `--host` / `--port` / `--auto-port`（优先级高于环境变量）
- 前端产物不存在时也提示一句

### 值得记住的坑：Windows 的 SO_REUSEADDR 语义与 Linux 相反

第一版预检**失效了** —— 明明 8848 被占，它却报告"空闲"并继续启动。
原因：探测 socket 上设了 `SO_REUSEADDR`。该选项在 Windows 上
**允许 bind 到一个已被占用的端口**（Linux 上只是允许复用 TIME_WAIT 地址）。
→ **用 bind 探测端口空闲时，不能设任何 SO_* 选项。**

实测三场景全通过（假监听占 8848）：
| 场景 | 结果 |
|---|---|
| 被占、不加 --auto-port | 退出码 2 + 占用者信息 + 三条出路 ✔ |
| 被占、加 --auto-port | 自动改用 8849 并成功监听 ✔ |
| 空闲 | 正常监听 8848 ✔ |

### 更正：端口预检改成按平台分支（同上，2026-09-18）

上一版把"探测端口不能设 SO_REUSEADDR"当成了**通用规则**，这是错的 ——
它只对 Windows 成立。在 POSIX 上：

- `SO_REUSEADDR` 是正规用法（复用 TIME_WAIT 地址），
  且**服务端本身就会设**（asyncio `create_server` 在 POSIX 上 `reuse_address=True`）；
- 探测时不设 → **刚关服务就重启**会把 TIME_WAIT 误判成"被占用"，
  拦下一个本来能启动的端口。即"把 Windows 的 bug 换成 Linux 的 bug"，
  而**本项目正要迁到 Linux 服务器**，这条尤其危险。

正确实现（`web/app.py`）：
| 平台 | 探测选项 | 理由 |
|---|---|---|
| Windows | 不设 `SO_REUSEADDR`，加 `SO_EXCLUSIVEADDRUSE` | 该选项在 Windows 是"抢占"语义，会永远报空闲 |
| POSIX | 设 `SO_REUSEADDR` | 与服务端语义一致，避免 TIME_WAIT 假阳性 |

同时把判据收窄成"**本服务能不能起来**"，不去猜别的进程状态 ——
猜容易假阳性（别人绑 0.0.0.0 而我绑 127.0.0.1、或只剩 TIME_WAIT），
而假阳性会拦下能用的端口。`_port_owner()` 只用于把报错写具体，不参与判断。

新增 `scripts/smoke_web_port.py`：把平台差异拆成
「选项层断言（平台无关、可静态验证）+ 行为层 + 真实启动路径」三层。
实测全通过。**迁 Linux 后需重跑**（POSIX 的运行期行为无法在 Windows 复现）。

所以**页数少的中文组合可能比页数多的英文组合更久**（gkk_zh 11 页 15.6 min
> gkk_en 15 页 14.5 min）。

标定值由后端下发（`CALIBRATION`），前端不写死；`perf_factor` 是按显存档位折算的
**启发式**（本机只有一块卡，没有别的硬件可标定），界面已注明是粗估。

### 核实一处易误判的显示

本机 `os.cpu_count()` / `psutil.cpu_count()` / `NUMBER_OF_PROCESSORS` **三者都是 8**，
即 BIOS 关了超线程 —— 不是探测有 bug。physical == logical 时界面只报线程数。

## 接口联调：冒烟测试抓出两个真实缺陷（2026-09-18 傍晚）

P0 剩最后四个接口没验证过（SSE / 取消 / 产物 Range / 进度解析）。
真跑一次要 15~25 分钟 + API 费用，所以用两个手段把它们变廉价：

1. **进度解析**用**真实历史日志**（gkk_en / gkk_zh 的 run.log）当输入，
   地面真值取 `audio/*.wav` 的条数（15 / 11）—— 不是拿同一个正则自证。
   另取日志前 45% 截断，验证中途阶段判定。
2. **队列 / SSE / 取消 / 产物**：进程内替换 `_build_argv`，让假命令按同样格式
   打印进度行，"排队→运行→进度递增→取消"与"跑完→done"两条路径
   都在 1 分钟内走完，**零 API 费用**。

新增 `scripts/smoke_web_api.py`，20 项断言。第一次跑就抓出两个缺陷：

### 缺陷一：`running_job` 永远是 null

`_run_job` 只设了 `_CURRENT["proc"]`，**从未设 `_CURRENT["job_id"]`**，
于是 `/api/system/gpu` 的 `running_job` 恒为 None。

### 缺陷二：任务记录的两个写入者互相整份覆盖

worker（收尾写 done/failed + exit_code + elapsed）与取消接口（写 canceled）
都是 "load → 改 → save"，中间有 `await`（取消接口里就是 `proc.wait()`）。
后写的那份用**旧快照**覆盖，旧快照里没有对方新增的字段。

诊断现场（`diag_cancel.py`）给出的决定性证据：

```
status=canceled  exit_code=None  elapsed=None   proc 已清空
```

`proc` 已清空说明 `_run_job` 确实恢复执行了，可 `exit_code`/`elapsed` 一个没留下
→ 只能是**后写的覆盖了先写的**（`updated_at` 均为同一秒）。反向时序就是
"已取消被改写成失败"。

修法：新增 `_JOB_LOCK` + `_update_job()`，统一"读-改-写"，各写入者只改自己的字段；
`_run_job` 收尾额外尊重取消意图（status 保持 canceled，但仍记 exit_code）。

### 测试设计上的一条经验

取消那条最初"通过"了 —— 因为我 sleep 4 秒就读状态，读到的是竞态中**较早的那次写**。
改成等 `exit_code` 落盘（它只由收尾逻辑写）再判状态后，才真正暴露问题。
**判据要挑"只由一个写入者写、且必然在收尾落盘"的字段**，不能只睡一下。

## 顺着一条 warning 查出的真缺陷：run.log 编码（2026-09-18 晚）

使用者贴出运行日志，怀疑"模型名称填错了"。查证结论：**名字没错**，
但同一条日志暴露了一个真缺陷。

### 模型名核查（用拦截法，零费用）

用一个假 `chat.completions.create` 拦下真实请求参数：

```
model_type : deepseek-flash   (platform = OPENAI_COMPATIBLE_MODEL, max_tokens = 32768)
base_url   : https://api.deepseek.com/v1/
请求里的 model 字段 : 'deepseek-flash'
```

即**发给 API 的就是这个名字**，且 stage 1（幻灯片 31s）、stage 2（讲稿 50s）都成功返回
→ 服务端认它。所以 `deepseek-flash` 既是 camel 侧的别名，也是真实 model id。

### warning 的性质

`Unknown model 'deepseek-flash': context window size not defined. Defaulting to 999_999_999.`
来自 `camel/types/unified_model_type.py` 的**基类兜底 property**。
已登记模型是 `ModelType` 枚举成员、自带自己的 property（实测 gpt-4o → 128000），
我们的别名落到 1e9 兜底。

`token_limit` 只被 camel 的上下文摘要逻辑消费（`num_tokens > token_limit` 才触发），
本项目每阶段都是一次性 prompt，**永远达不到** → 功能上无影响。
但两点值得修：日志里少一行"像错误"的东西；以及万一日后做多轮对话，
1e9 意味着**永不触发摘要**，那层保护形同虚设。

修法（`wei_utils`）：只覆盖基类属性、先查自己的表、查不到交回原实现 →
已登记模型与别的未知名字行为都不变（已实测）。

### 真正的问题：run.log 是两种编码混写的

`_log_line` 用 UTF-8 写父进程的行；子进程 stdout 默认按 **GBK** 输出。
同一个文件里混着两种编码，**utf-8 与 gbk 解码都会抛 UnicodeDecodeError**。

后果两层，第二层更隐蔽：
1. 界面「日志尾巴」乱码；
2. **日志兜底解析的正则命中 0 条**（实测：修复前 0，修复后 11）。不报错，只是数不出来。

修法：子进程加 `PYTHONIOENCODING=utf-8`（治本；**不设 PYTHONUTF8**，
避免改变子进程 `open()` 的默认编码）+ 读取端 `_read_log_text()` 逐行编码回落（兼容旧日志）。

### LaTeX 的 warning：确认良性

`Missing character ... in font nullfont`（38 条，数字 1~9 杂合，都落在 frame 结束行）
与 `Overfull vbox (0.34pt / 0.85pt)`。核实渲染产物：**页码完整**
（"1 / 11"、"8 / 11"）、日期与机构号都在 → 无可见内容丢失；
Overfull 是亚像素级（< 1pt）。属引擎级良性警告，不必处理。

### 测试

新增第 7 组 7 项断言，含一条**对照组**（断言"整文件严格 utf-8 解码确实会失败"），
防止将来有人把逐行编码回落当成过度设计删掉。全量 **83 项断言通过**。

另给 `check()` 补约定：detail 要写**观察到的事实**、不写否定句（成功时也会打印，
「✔ 某某 — 没找到某某」会误导读者）。本次自己先踩了一次。


## 数字人整批产出为空 —— 上游 libx264 奇数尺寸（2026-09-18 晚）

使用者报「进程终止了」，看日志发现任务 exit_code=1、11 页数字人**全部没有产物**。
顺着日志查出是**两个独立问题**，第一个是真根因。

### 真根因：人脸裁框 215x221（奇数）→ libx264 拒绝编码

日志里最上游那一句才是原因：

```
[libx264] width not divisible by 2 (215x221)
[out#0/mp4] Nothing was written into output file ...
[in#1] moov atom not found
Error opening input file ./results/.../temp.mp4
```

**libx264 的 yuv420p 要求宽高都是偶数**；上游命令只有 `-vf format=yuv420p`，
于是编码器初始化失败 → temp.mp4 是 **0 字节** → 合音频读不进去 → 该页无产物。
11 页全是同一个尺寸，所以 11 页全废。

**为什么之前能跑**：奇偶取决于**参考图**。本次用的是
「屏幕截图 2026-09-18 173619.png」（**截图，不是人像照**，人脸占比小 → 裁框小且为奇数），
而 gkk_en / gkk_zh 用 `assets/gkk/portrait.png` 恰好裁出偶数。

修法：滤镜链加 `crop=trunc(iw/2)*2:trunc(ih/2)*2`，两个入口都改。

**我的第一版补丁自己写错了**：注入未转义的双引号 → f-string 提前闭合 → SyntaxError
→ 又是"退出码 1、11 页全失败"，与原始故障几乎一样。教训：
改上游 f-string 命令时引号必须转义（源码写 `\"`，因为 os.system 走 cmd.exe 不吃单引号），
且改完必须用**该仓库自己的解释器** py_compile 一次。

A/B 实测（奇数帧 + 从源码 eval 出原始命令执行）：
| | 退出码 | 产物 |
|---|---|---|
| 不加 crop | -542398533 | temp.mp4 **0 字节** |
| 加上 crop | 0 | 214x220、h264 视频 + aac 音频 |

### 第二个：最后一步崩掉，20 分钟全废

`pipeline.py` 合片前 `cv2.imread(...).shape` 返回 None → AttributeError。
实测 cv2 会偶发返回 None（`cv2::findDecoder imread_('<路径>')`），
而**同一文件换 PIL / PyMuPDF 能正常打开**（我当场复测 cv2 也成功了 → 状态相关，非路径问题）。
改用 `read_image_size()`：cv2 → PIL → PyMuPDF 依次尝试，全失败才抛错并列出各读取器原因。

### 防复发

- `talking_gen.py` 进批量入口前自检上游是否含 `crop=trunc(iw/2)`，缺失就大声提示（不中断）。
- 新增 `scripts/verify_musetalk_patch.py`，**从补丁后的源码里 eval 出真实命令**再执行
  —— 手写等价命令在多层转义下测过两次假结果，不值得再试第三次。正反方向都验证过。

## 长论文结构化被截断（2026-09-18 晚，使用者实测发现）

使用者传了一篇 **24 页 / 6.6 万字符**的 arXiv 论文（`2609.14542v1.pdf`，
波斯语 ASR 语料库，选题是**机器学习类**，不是人文社科）。

### 症状

    [2/3] 调用 deepseek-flash 结构化 ...
          108.9s | tokens=52707 | finish=length
    compile_ok False

`completion_tokens=32768` **正好贴死上限**（那次思维链约 3.5 万字符）。
main.tex **没有 \end{document}**，尾部断在一张表中间（`XLS-R-300M & ... & 41.28 & 30`），
tectonic 报 `File ended while scanning use of \environment tblr`。

**危害是静默的**：这份 main.tex 正是下游生成幻灯片的输入，
截断 = 后半篇（结果表、结论、参考文献）不进幻灯片，而从成片上看不出来。
这次仍产出了 14 张幻灯片，缺的只是尾部。

### 修法（三层）

1. 默认上限 **32768 -> 65536**（接口实测接受至 131072；上限不产出就不计费）
2. 撞上限**续写**（`_continue_tex`，最多 3 轮，usage 累加）
3. 兜底**收尾**（`_repair_unclosed`：截到最后一个环境配平点 + 补 \end{document}）

**第一版收尾逻辑我写错了**：判据用"环境栈为空"，但正文整体包在
`\begin{document}` 里，文档级扫描下栈永不空 → **65116 字符被削成 17 字符**。
正确基准是"回到 `\begin{document}` 之后的深度"。已写进 docstring。

### 顺手修的两个同源问题

- `compile_tex` 的 `subprocess.run(text=True)` 没指定编码 → 按 GBK 解码 tectonic 的
  UTF-8 输出 → reader 线程 `UnicodeDecodeError: byte 0x93`，
  表现为"编译失败"且日志残缺（这次日志里就有这条 traceback）。
- `paper_struct.py` / `wei_utils.py` 里裸 `\section` / `\end{document}` 写在非 raw
  字符串里 → `SyntaxWarning`。已修，`-W error::SyntaxWarning` 通过。

### 验证（离线，零 API 费用）

| 用例 | 结果 |
|---|---|
| 真实被截断的 main.tex | 65116 -> 64248 字符（丢 1.3%），**tectonic 编译成功**（PDF 126 KB）|
| 完整文档 | 不被误改 |
| 断在半张表上 | 正确补出 `\end{tblr}` 与 `\end{document}` |


## 五个前端体验问题的分析（23:20，仅分析未实施）

使用者提出 5 个问题（无音色入口 / 一直"启动中" / 进度条误导 / 产物要手动刷新 / API key 不保存），
逐一取证后产出方案文档 `docs/前端体验改进方案.md`。三条有实测证据：

**① 进度条（#3）—— 幻觉最重，而且根因不在前端。**
用真实 `progress.jsonl` 复现前端公式（`done = talking_done || tts_done`）：
stage1 0% → TTS 0→100%（14 页 / 311 秒）→ 光标定位 100% → 生成数字人**回跳到 7%** → 100% → 合片 100%。
更硬的证据：数字人 14 条进度记录的时间戳**全部是 22:58:21**（相差 1~2 毫秒）。
原因在 `talking_gen.py:536-568`：批量路径先 `_run(cmd)` 让 MuseTalk 一个进程跑完 N 页，
**之后**才开始逐页取回产物并 `report()`。于是真正在跑的 5~10 分钟里 `progress.jsonl` 一行不写 →
条停在 100%、阶段停在"光标定位"、`stalled_seconds` 一路涨到 600+ 会弹「疑似卡住」**误报**。
修法：阶段加权总进度（8/12/10/30/5/30/5）+ 数字人阶段用后台线程轮询"预期产物是否已出现"
（路径由 `musetalk_batch_output()` 算出，**不需要改 MuseTalk**）。

**② 一直"启动中"（#2）。** `job.phase` 全流程只写 3 次（排队中 / 启动中 / 已完成）；
过程阶段靠 `progress.jsonl`。而前置结构化 `_prepare_latex`（`app.py:557-600`）**不写任何进度**，
此时 progress.jsonl 还不存在 → 那 1~2 分钟必然显示"启动中"。修法：补阶段上报 + 前端改步骤条 +
把 `_PHASE_LABEL.get(x, "")` 的未知值兜底**显式化**成"保留上一阶段"（现在是靠上层"空值不覆盖"的巧合）。

**③ 产物不自动显示（#4）。** 后端实测正常（artifacts 200 / 9 项、pages total=14、SSE 末帧 status=done）。
问题在前端：产物只在 `[jobId, job?.status]` 变化时拉一次 → 运行中从不刷新；
而 `es.onerror = () => es.close()` **禁用了 EventSource 自带的重连**且不给提示 →
一旦断流，status 冻结，"唯一的触发点"永不到来，产物区从此要手动刷新。
修法：轮询 + SSE 重连 + 心跳 + 运行中也显示产物 + `jobId` 持久化。

**④ 音色（#1）。** `--ref_audio / --ref_text` 流水线早就支持（`pipeline.py:133-135,180-181`），
但 `_build_argv` **从不传这两个参数** → 音色被 `language_config.SCRIPT_LANGS` 写死
（en → zeyu.wav 男声英文；zh → zeyu_zh.wav 中文同音色）。要"男女可选"必须先有种子音频
（Qwen3-TTS-**Base** 只能克隆、不能凭空造音色）→ 素材来源待使用者决策。

**⑤ API key（#5）。** 前端只有 React state（刷新即丢），且界面文案「仅存内存，不落盘」与"存本地"矛盾，需同步改。
⚠️ 顺带查出一个**必须先修的坑**：`_SESSION_KEYS` 是**模块级全局**，`/api/key/verify` 与建任务都写它 →
"最后输入的人覆盖所有人"。单人本机无感，但**迁到学校服务器后 A 的 key 会被 B 的任务用掉**；
而一旦把 key 存进浏览器本地，这个覆盖**更难被发现**（每人界面都显示着自己填的 key）。
修法：改成按 `job_id` 注入（内存 dict、不落盘），删掉全局回落。

另：本轮任务 `job_0918_224354_9487` 已完整跑通（14 页、`3_merage.mp4` 9.39 MB），
`paper_type=auto` 对这篇机器学习论文判成了实验结构，符合预期。


## 前端体验 A 包实施（2026-09-18 深夜）

四个问题一起改（阶段显示 / 进度条 / 产物刷新 / API key），因为它们共用同一套地基。
`docs/前端体验改进方案.md` 是设计，本轮是落地。

### 统一阶段模型（关键地基）

`app.py` 新增 `PHASES`：9 个阶段各带**权重 / 有无逐页进度 / 卡住阈值**，
`/api/options` 下发给前端 → **前后端不再各存一份阶段表**（这类"两处维护"迟早漂）。
总进度由后端算（`_phase_overall_pct`），口径：已完成阶段全额计入；有页数的阶段按
done/total 线性；**没有页数的阶段只走到它的起点**（不假装在走）。
于是**单调不减**，顺带消除了旧公式那次 100% → 7% 的回跳。

### 数字人阶段终于有真实进度

`_monitor_batch_progress`（后台线程）在 `_run_musetalk_batch` 阻塞期间轮询
"预期产物是否已出现"：路径由 `musetalk_batch_output()` 算出（与真正的落盘点同源），
新鲜度判据与第 4 步的校验一致（`mtime + 1.0 >= started`，旧文件不算）。
**不需要改 MuseTalk**。批量开始时先 `report(done=0)` → 阶段立刻切换、并重置
"卡住"计时器。这条同时消掉了「疑似卡住」误报的根因（原先那 5~10 分钟零记录）。

### 产物不自动显示：单点触发是病根

产物原先只在 `job.status` 变化时拉一次，而 status 只能从 SSE 更新，SSE 的
`onerror` 又直接 `close()`（把 EventSource 自带重连关掉了）→ 流一断即永久冻结。
现在三个触发点（换对象 / 状态或阶段变化 / 运行中每 5 秒轮询），SSE 指数退避重连 +
心跳注释帧，产物区运行中也渲染，jobId 持久化。

### 凭据：从"进程级一份"改成"按任务一份"

`_SESSION_KEYS` → `_JOB_KEYS[job_id]`。⚠️ 原来的行为是"最后输入的人覆盖所有人"，
单人无感但**迁到学校服务器后 A 的 key 会被 B 的任务用掉**；而 key 一旦存进浏览器，
这个覆盖更难被发现。回落 .env 时**写一行 run.log**（回落路径必须可见，否则
"开发机有 .env 所以看着能跑、服务器静默用错凭据"这类问题永远暴露不出来）。

### 两个工具坑（都记进跨项目记忆了）

- **TestClient 对流式响应是缓冲的**：用它测"SSE 空闲时发心跳"只能靠挂住+超时，
  实测把套件卡死 7 分钟。把帧序列抽成 `_sse_frames()` 后直驱生成器 → 又快又准。
- **沙箱批量删除守卫按每轮累计计数**：测试清理自己的临时目录也被拦
  （`SAFE_DELETE_BULK_CONFIRM_REQUIRED`），跑测试要 `CODEBUDDY_SAFE_DELETE_ENABLED=0`。

### 测试

新增第 9 组 33 项，全套 **126 项通过**。两条**反面对照**：
旧公式确实回跳；监控线程确实把旧产物排除在外（done=1→2，不是 3）。
