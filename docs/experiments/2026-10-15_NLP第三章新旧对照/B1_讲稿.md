## 1. 从定义表达式到得到结果

我们刚写出 h = sigmoid(W·x + b)，但屏幕上并没有数字——为什么定义了表达式，还拿不到结果？


因为 TensorFlow 1.x 的图模式把‘描述计算’和‘执行计算’严格分开：先用代码构建一张静态的计算图，记录所有操作依赖；真正算出数值，必须启动会话并提供输入数据。


这就像写菜谱：‘把鸡蛋打散，加盐搅匀，下锅煎’——你写完了步骤，但锅还没热、蛋也没打，自然吃不到煎蛋。定义表达式只是写好菜谱，不是开火做饭。


具体分三步：第一，定义依赖——声明哪些操作要连在一起，比如 matmul、add、sigmoid；第二，提供数据——通过 feed_dict 给占位符 x 赋值；第三，执行求值——调用 session.run(h) 触发图中必要子图的计算。


一个常见误区是认为‘创建变量就自动有值’或‘写了 h 就等于算出了 h’。其实 W 和 b 是变量，必须显式运行初始化操作；x 是占位符，必须在 run 时用 feed_dict 填入实际张量。否则 h 仍是一个符号，没有数值。


接下来我们会用一个具体例子 E1：设 a=2, b=3, c=4，按 z = (a+b)×c 手动走一遍——看清楚哪一步是构图、哪一步是供值、哪一步是求值。这将帮我们确认：定义表达式 ≠ 得到结果。


记住：本章全部基于 TensorFlow 1.x 的图模式，它要求你主动触发执行；这不是缺陷，而是为分布式训练和优化预留的设计空间。

## 2. E1：计算图的两步运算

我们刚写出 h = sigmoid(W·x + b)，但屏幕上并没有数字——为什么定义了表达式，还拿不到结果？


现在就用这个最简计算图 E1 来手算一遍：教材符号是 d = a + b，z = d * c；教学补充设值 a = 2，b = 3，c = 4。


第一步：先算 d = a + b = 2 + 3 = 5。注意，这一步不是代码自动执行的，而是我们在‘构图完成、供值之后、求值之前’手动模拟的中间结果。


第二步：用上一步结果代入，z = d * c = 5 * 4 = 20。最终输出数值是 20。


这里的关键是：d 和 z 在图中都是 Tensor——它们代表‘待求值的输出’，不是立即存在的数；而加法和乘法是 Operation，负责在运行时真正执行计算。


举个类比：你画了一张电路图，标出‘节点A接电阻R1，再连到节点B’，这相当于定义了 d = a + b；但没通电，A点电压仍是未知的。只有接上电池（提供 a=2, b=3），电流流过（执行加法操作），才能测出 d=5 的电压值。


易错点一：有人以为‘写了 d = a + b 就等于 d 已经是 5’——不对。在图模式里，d 只是一个符号张量，它的值必须通过 session.run(d) 并配合 feed_dict={a:2, b:3} 才能取出。


易错点二：混淆 Operation 和 Tensor。Operation 是动词，比如 ‘add’ 或 ‘multiply’；Tensor 是名词，是该操作的输出结果，比如 add:0 或 multiply:0。后缀 :0 表示第一个输出，零起始计数。


再确认一次：a、b、c 的数值是本实验为教学补充的，仅用于手算核对；教材原文只给符号式，没给具体数字。我们这么做，是为了让你看清‘构图—供值—求值’三阶段如何对应到实际算术步骤。


接下来的问题是：当张量不再是标量，而是向量或矩阵时，我们怎么描述它的结构？比如 [1,2,3] 和 [[1,2],[3,4]] 有什么本质区别？这就要引入‘秩’‘形状’和‘名字’——下一页我们详细展开。

## 3. 张量的秩、形状与名字

刚才我们手算了标量图 d=a+b、z=d*c，现在问题来了：如果张量不是单个数，而是像 [1,2,3] 这样的列表，或者 [[1,2,3],[4,5,6]] 这样的表格，我们怎么准确描述它的结构？


这就需要三个核心属性：秩、形状和名字。秩（rank）就是轴的数量——你可以理解为‘维度数’；shape 是各轴的长度组成的列表；dtype 则说明每个元素是什么类型，比如 float32 或 int64。


举个明确的教学补充例子：向量 [1,2,3] 只有一行数据，它沿一个方向延伸，所以秩是 1；它包含 3 个元素，shape 就是 [3]。


再看矩阵 [[1,2,3],[4,5,6]]：它有 2 行、3 列，两个方向都有长度，因此秩是 2；shape 是 [2,3]——注意顺序：先写行数，再写列数，这和 NumPy 一致。


名字呢？在图中每个 Operation 可能产生多个输出，比如 add 操作若定义了三个输出端口，第三个就叫 add:2——后缀从 0 开始计数，:2 就是第三个。


这里有个关键区分：数据边负责传递数值，比如 a→add 的边把 2 传给加法；而控制边只表示‘必须先完成某操作，才能启动下一个’，它不携带任何数值。


易错点提醒：有人把 shape [3] 误说成‘秩是3’，其实秩是轴数，不是元素总数。[1,2,3] 有3个元素，但只有1个轴，秩是1——记住：秩 ≠ 元素个数。


现在你已经能描述张量的骨架了。下一步自然要问：这些带形状的张量，怎么放进图里求值？谁来提供输入、谁来初始化参数？这就要进入会话（Session）的执行阶段——下一页我们聚焦这个问题。

## 4. 会话负责执行和资源管理

上一节我们明确了张量的秩、形状和名字——这些是图中节点输出的‘结构身份证’。但光有结构还不够，你得让图真正动起来：谁来启动计算？谁来提供输入数据？谁来回收内存？答案就是会话（Session）。


会话的核心职责是两件事：执行计算与管理资源。它不参与构图，只负责在图已定义好的前提下，按需触发运算并释放硬件占用。


整个流程严格分两步：先构图，记录所有依赖关系；再运行，只执行为得到目标结果所必需的子图。比如你想算 h，会话不会去碰梯度或训练步骤——它只沿着 h 的依赖链回溯，把 x→W·x→W·x+b→sigmoid 这条路径上的操作跑一遍。


具体怎么触发？靠 Session.run()。你传给它一个‘求值目标’，比如 h，它就自动找出所有前置依赖，依次执行，并返回 h 的数值结果。


这里有个关键误区必须澄清：创建会话 ≠ 自动求所有梯度或训练。教材第13页曾笼统说‘启动Session会自动计算梯度’，这是不严谨的。实际上，run 只执行你明确请求的张量及其依赖；梯度需要你显式构建 gradient 操作，训练更需要循环调用优化器。会话本身没有‘智能推断’能力。


还有一点常被忽略：会话用完必须关闭。session.close() 不只是礼貌，而是释放 GPU 显存、CPU 线程等资源。尤其在实验环境中反复创建会话却不关闭，很快就会报 OOM 错误。


举个教学补充例子：假设我们有图 z = (a + b) * c，其中 a=2, b=3, c=4。即使你已定义好 add 和 multiply 节点, z 仍是符号表达式——直到你创建 session 并调用 session.run(z)，才会真正算出 z=20。这说明：定义 ≠ 求值，构图 ≠ 执行。


现在问题来了：当图里出现像 x 这样的占位符，或者 W、b 这样的变量时，会话该怎么处理它们？谁负责提供 x 的值？谁负责给 W 和 b 赋初值？这正是下一页我们要解决的问题。

## 5. 占位符与变量：谁供值，谁初始化

上一节我们讲了会话如何执行计算、管理资源，但图里如果出现像 x、W、b 这样的符号，会话到底该向谁要值？谁来负责给它们填上初始数字？


答案取决于它们在图中的角色：x 是占位符（placeholder），它本身不存数值，只在运行时由用户通过 feed_dict 提供具体数据；而 W 和 b 是变量（Variable），它们需要显式初始化才能拥有初始值。


为什么这样设计？因为占位符代表‘每次运行都可能不同’的输入——比如一批新样本的特征；而变量代表‘需要学习或持久保存’的参数，比如神经网络的权重和偏置。这种分工让图既能复用结构，又能灵活换数据。


这里有个高频误区：定义初始化器 ≠ 已经执行初始化。你写 tf.Variable(...) 或 tf.global_variables_initializer()，只是在图里加了一个‘初始化操作节点’；它还没跑，W 和 b 仍是未定义状态。必须显式调用 session.run(init_op) 才真正赋初值。


整个求值流程是严格有序的四步：先初始化变量 → 再提供 x 的具体值 → 然后求 h 的数值 → 最后关闭会话释放资源。漏掉任何一步，都会报错：比如没初始化就求 h，会提示 ‘Attempting to use uninitialized value W’。


再强调一次：本例是单次前向求值，不是训练。它只算一次 h = sigmoid(W·x + b)，不更新 W 和 b，也不涉及梯度或优化器循环。所以你看到的代码里没有 train_op，也没有 for 循环。


接下来的问题是：当 x、W、b 都有了具体数值，h 的形状到底是多少？怎么一步步从 [1,10] × [10,5] 推到最终结果？这个核验过程，我们下一页用教材代码逐行展开。

## 6. E2：沿教材代码核对形状

上一节我们明确了占位符和变量的分工：x靠feed_dict供值，W和b需显式初始化。现在问题来了——当它们都有了具体数值，整个前向计算链的形状到底怎么一步步推出来的？


我们严格按教材代码核对：x定义为shape [1,10]，W是[10,5]，b是[5]。首先看矩阵乘法x × W：这是标准的行向量左乘矩阵，内维10必须匹配，结果自然是[1,5]。


接着加偏置b。b的shape是[5]，而当前结果是[1,5]——它只在最后一轴（即第2轴）长度为5，与b完全一致。根据NumPy和TensorFlow的广播规则，b会自动沿第1轴（批大小轴）复制1次，变成[1,5]，相加后形状不变，仍是[1,5]。


最后是sigmoid函数。注意：它不是矩阵运算，而是逐元素作用——对每个标量独立计算1/(1+exp(-t))。输入是[1,5]的张量，输出仍是[1,5]，元素个数没变，只是数值被非线性压缩到(0,1)区间。


再算参数总量：W是10行5列，共50个标量；b是长度5的向量，5个标量；合计55个可训练参数。这个数字很重要——它决定了后续梯度计算要更新多少个值。


这里有个关键提醒：x和W都是随机初始化的，教材没有给定具体数值。因此，我们只能确定h的形状是[1,5]，但不能编造出唯一的输出数值——比如不能说‘h等于[0.6,0.3,…]’。一个样本对应一个1×5输出，不是单个标量。


还要特别注意代码顺序：教材PDF第14–16页明确写的是tf.matmul(x,W)，也就是x左乘W。这和W左乘x完全不同——如果误写成tf.matmul(W,x)，就会因内维10≠5报错。形状核验的第一步，就是确认乘法方向是否匹配定义。

## 7. 从客户端到实际执行设备

上一节我们核对了x、W、b的形状如何一步步推出h的[1,5]结构——现在问题自然浮现：这个计算图定义好了，它到底在谁手里、怎么跑起来的？


这就引出TensorFlow 1.x图模式的执行架构：从客户端提交请求，到最终在CPU或GPU上算出结果，中间有三个逻辑角色。


client是发起者，它把已经构造好的计算图和执行请求一起提交给系统；就像你写好一道数学题的解法步骤，然后交给老师说‘请算出答案’。


master是协调者，它不亲自算数，而是分析这张图的依赖关系，把大任务拆成若干子图，并分配给合适的执行单元——相当于教务处把考卷分发给各科阅卷组。


worker才是真正的执行者，它拿到自己负责的子图后，调用本地的CPU或GPU硬件资源，只计算请求结果所必需的那部分依赖节点。


这里有个常见误解：以为这三个角色必须对应三台物理机器。其实单机开发时，client、master、worker的职责完全可以由同一个Python进程承担——它们是逻辑分工，不是硬件绑定。


更重要的是：系统绝不会傻乎乎地把整张图全算一遍。它只追踪你通过Session.run指定的输出节点（比如h），然后反向推导出它依赖的最小子图，仅执行这部分——这叫‘按需求值’，能省下大量无效计算。


举个教学例子：假设图里还有个没用到的节点loss = h * 2，但你只run(h)，那么loss根本不会被计算；只有当你显式fetch loss，它才会被触发。这正是图模式高效的关键设计。


理解这套架构，是为了下一节能把‘定义图→初始化变量→提供输入→会话求值’整个链条串起来——我们马上就要用它来检查：如果漏掉feed_dict或初始化，系统到底报什么错、为什么报错。

## 8. 回顾：把一次求值完整串起来

现在我们把前面七节课的知识串成一条完整的执行链：从定义图与张量开始，到初始化变量、提供输入，再通过Session.run求值、取得h、最后关闭会话——这六个步骤缺一不可。


Session.run是执行的触发点：它接收你指定的输出张量（比如h），自动回溯依赖路径，只计算必要子图；结果通过返回值交还给你，之后你必须显式调用session.close()释放资源。


我们来检查第一个典型错误：如果漏掉feed_dict，系统找不到占位符x的值，会直接报错‘You must feed a value for placeholder tensor x’——因为x是placeholder，它的值只能靠feed_dict在运行时注入，不能靠初始化解决。


反过来，如果漏掉变量初始化，比如没运行tf.global_variables_initializer().run()，那么W和b仍处于未赋值状态；当你run(h)时，系统会报‘Attempting to use uninitialized value W’——因为Variable必须显式初始化，不能像placeholder那样靠feed_dict补救。


再看形状问题：x的shape是[1,10]，W是[10,5]，矩阵乘法要求左矩阵列数等于右矩阵行数，10=10成立，结果shape就是[1,5]；b是[5]，按广播规则加到[1,5]上不改变形状；sigmoid是逐元素运算，最终h仍是[1,5]——这五步形状推导，每一步都依赖前一步的维度匹配。


最后强调一个根本区分：定义图是描述‘要算什么’，执行是‘现在算出来’，训练则是‘反复调整参数使结果更好’。本例中只有一次run(h)，没有优化器、没有梯度、没有循环迭代——它只是前向求值，绝不是训练。


总结本课核心：图是蓝图，Session是施工队，变量需初始化、占位符靠feed_dict供值，形状匹配是矩阵运算的前提，而单次求值不等于训练。
