## 一、上游是什么：论文与官方实现

### 1.1 论文解决的两个问题【论文】

**Paper2Video: Automatic Video Generation from Scientific Papers**
arXiv 2510.05096v2（2025-10-09）· Zeyu Zhu\* / Kevin Qinghong Lin\* / Mike Zheng Shou ·
Show Lab, National University of Singapore · 代码 https://github.com/showlab/Paper2Video

学术会议普遍要求作者提交 2~10 分钟的演讲视频。手工做一条要花数小时（设计幻灯片、
写字幕、逐页录音、剪辑）。论文把这件事拆成两个问题：

| 问题 | 论文的答案 | 贡献定位 |
|---|---|---|
| **怎么造**（how to create） | **PaperTalker** —— 首个多智能体学术演讲视频生成框架 | 框架 |
| **怎么评**（how to evaluate） | **Paper2Video** —— 101 篇论文的基准 + 4 项指标 | 基准 |

### 1.2 基准的构成【论文】

- **101 篇**近三年会议论文：41 篇 ML（NeurIPS/ICLR/ICML）、40 篇 CV（CVPR/ICCV/ECCV）、
  20 篇 NLP（ACL/EMNLP/NAACL）
- 每篇配对：**作者录制的演讲视频** + 幻灯片 + 演讲者身份元数据（头像、语音样本）
- 其中 **40%** 额外收集了**原始幻灯片 PDF**，用于「参照式」评幻灯片生成
- 平均 **13.3K 词 / 44.7 张图 / 28.7 页**；演讲平均 **16 张幻灯片**、**6 分 15 秒**（最长 14 分钟）
- 数据在 HuggingFace `ZaynZhu/Paper2Video`

> ⚠️ 这里是理解**本项目最大约束**的地方：基准里的每一项都**自带 LaTeX 工程**，
> 而「工程里必然有 `figure/` 目录」这件事，正是论文那个核心机制赖以工作的前提。
> 详见 §3.E。

### 1.3 四项评测指标【论文】

| 指标 | 衡量什么 | 评测方式 |
|---|---|---|
| **Meta Similarity** | 生成的语音/幻灯片/字幕与真人做的有多像 | VLM 打 1–5 分；语音用说话人嵌入算余弦相似度 |
| **PresentArena** | 哪个视频更好 | VideoLLM 当代理观众，双序成对比较（A,B）与（B,A）后平均，抵消位置偏好 |
| **PresentQuiz** | 视频多大程度传达了论文知识 | 从论文生成四选一题目，VideoLLM 看视频答题，算准确率 |
| **IP Memory** | 视频多大程度让观众记住作者与其工作 | VideoLLM 回忆问答 |

评测用 **GPT-4.1** 作 VLM、**Gemini-2.5-Flash** 作 VideoLLM。

### 1.4 PaperTalker：四个 builder【论文 + 代码】

论文的分工是「按角色解耦，便于扩展」：

```
论文 D ──► ① Slide builder      用 LaTeX Beamer 生成幻灯片（含编译反馈修错 + 树搜索布局优化）
        ──► ② Subtitle builder   VLM 看幻灯片图 → 逐句字幕 T + 视觉焦点描述 P
        ──► ③ Cursor builder     GUI-grounding 模型把 P 定位成坐标 + WhisperX 做时间对齐
        ──► ④ Talker builder     TTS 合成语音 + 数字人渲染 → 逐页并联合片
```

对应到上游代码（`Paper2Video-main/src/`）：

| 论文中的模块 | 上游文件 |
|---|---|
| Slide builder | `slide_code_gen_select_improvement.py`（含 `improve_layout`，即树搜索） |
| Subtitle builder | `subtitle_cursor_prompt_gen.py` |
| Cursor builder | `cursor_gen.py`（空间）+ `cursor_render.py`（轨迹渲染） |
| Talker builder | `speech_gen.py`（TTS）+ `talking_gen.py`（数字人） |
| 合片 | `merge_video.py` / `merge_talking.py` / `1_merage*.bash` |
| 总控 | `pipeline.py`（完整）/ `pipeline_light.py`（轻量） |
| 模型客户端 | `wei_utils.py` |
| 论文评测（我们不使用） | `evaluation/` 子树（81 个文件） |

### 1.5 三项关键机制

#### 机制一：Tree Search Visual Choice（树搜索视觉选择）★

**问题**【论文】：LLM/VLM 对**细粒度数值调整**不敏感 —— 直接提示它「把图片宽度从 1.0 改成 0.75」
效果不稳定（论文指出 PPTAgent 的参数编辑策略也有同样毛病）。

**做法**【论文】：不让模型改数字，而是**用规则枚举候选取代模型的数值推理**：

```
文本页溢出    → 扫字号
含图页溢出    → 先变图片缩放因子 {1.25, 0.75, 0.5, 0.25}，再降字号
                ↓ 每个候选渲染成图
                ↓ 拼成一张 2×2 对比图
                ↓ VLM 当裁判，选布局最好的一个
```

论文 Figure 5 的示意：4 个候选 A/B/C/D 拼图，VLM 输出
`{"reason": "...C 的右侧轴标签与边缘碰撞显示截断...", "choice": "D"}`。
即**宽度 4、深度 1 的束搜索**。

**论文自己的消融**（Table 5，幻灯片质量 1–5 分）：

| 方法 | Content↑ | Design↑ | Coherence↑ |
|---|---|---|---|
| HumanMade | 4.43 | 2.85 | 2.73 |
| PPTAgentGPT4.1 | 4.07 | 2.02 | 2.06 |
| **PaperTalkerGPT4.1（关掉树搜索）** | 4.33 | **2.73** | 3.84 |
| **PaperTalkerGPT4.1** | 4.34 | **2.85** | 3.84 |

论文的措辞是「design quality 显著下降」。**从数字看更准确的说法是**：
树搜索的影响集中在 **Design（+0.12）**，而它把 Design 从 2.73 拉到了 **2.85 —— 正好等于 HumanMade**；
Content（+0.01）与 Coherence（±0.00）几乎无变化。
⇒ 「这是让**版面**追平真人的那一步」，而不是「全面提升」。

> 这个认知对我们很要紧：**树搜索是「设计分」的机制，不是「内容分」的机制**。
> 所以它空转时（见 §3.E），内容分基本不受影响 —— 这也解释了为什么这个 bug 能藏那么久。

#### 机制二：光标的时空对齐【论文】

- **假设**：光标在一句话内不动，只在句间移动 ⇒ 每句估一个位置 + 一个时间段
- **空间**：用 computer-use 类模型（论文用 UI-TARS）按视觉焦点描述 P 定位 (x, y)
- **时间**：用 WhisperX 取词级时间戳，与字幕里对应句子对齐，得到每段的 (t_s, t_e)
- 论文的消融（Table 4）显示光标对「定位类问题」准确率影响极大：**0.084 → 0.633**

#### 机制三：逐页并行【论文】

幻灯片之间是硬切场景，演讲者在相邻页之间不需要时间连续性 ⇒ 可以按页独立生成、并行跑。
论文 Table 3：**287.2 分钟 → 48.1 分钟（6×）**。

> ⚠️ **这是论文与我们的设备差距最大的地方**。论文用 **8×A6000 48GB**；
> 我们是**单张 RTX 5070 Ti 16GB**。所以这条机制在我们这里**被主动放弃了**（见 §3.I）。

### 1.6 上游对输入的要求（这是本项目一切改造的起点）

```
--paper_latex_root  必须是「含 main.tex 的 LaTeX 源码目录」
--ref_img           演讲者头像
--ref_audio         语音样本
```

## 三、逐类详解

### 3.A 输入层：PDF/Word → LaTeX 工程

**上游的行为**【代码】`pipeline.py` 直接读 `--paper_latex_root/main.tex`。
**使用者的现实**：手里是 `.pdf` 或 `.docx`。

补的一层（**论文完全没有**）：

```
.pdf / .docx / .doc / .tex / .zip
   └─► paper_ingest.py    提取纯文本（零 API 成本）
          └─► paper_struct.py  LLM 结构化 → main.tex（唯一花钱的一步）
                 └─► LaTeX 工程 ──► 交给上游 pipeline.py
```

#### 三条实测结论改变了实现方式【实测】

1. **不用 Office/WPS 的 COM 自动化** —— 会连上使用者正在运行的 WPS 实例并**挂死 2.5 分钟**。
   一律纯 Python（`.doc` 走 `olefile`，有损）。
2. **PDF 提取必须做「行合并」** —— PDF 会把句子按列宽硬切成半句，需按中英文标点判断句末再合并。
3. **三种格式内容等价，`.pdf` 信噪比最高** —— 真实 Word **不用标题样式**（heading=0），
   所以 `.docx` 相对 `.pdf` 并无结构优势；三种格式都靠 LLM 推断章节。

#### 结构化层的六个硬约束【实测】

| 约束 | 值 / 做法 | 不这么做会怎样 |
|---|---|---|
| 输出上限 | 65536（`PAPER2VIDEO_MAX_TOKENS` 可覆盖） | 长论文被截断，`main.tex` 没有 `\end{document}` |
| 撞上限 | **续写**（≤3 轮）→ 仍不全则**截到最后环境配平点 + 补 `\end{document}`** | 同上；实测这样做丢 1.3%、**编译通过** |
| 中文排版 | 必须用 `ctex` | 中文变方框 |
| 表格 | 必须用 `tabularray` 的 `tblr` | 与 `ctex` **宏包级冲突** |
| 章节识别 | 真实论文标题无样式标记，靠**语义**识别 | 结构全丢 |
| 忠实性 | 不得编造数据/文献；**不得「顺手纠正」原文** | 这不是摘要任务，改动原文即失真 |

保真度自检：`scripts/check_struct_fidelity.py`。
⚠️ **主指标必须用固定长度窗口** —— 整句比对会产出大量**假阴性**，
而**假警报比不报更糟**（会让人去查不存在的问题）。

**另有一处内容寻址纪律**：命中判据 = 内容 sha1 + `paper_ingest.EXTRACTOR_VERSION`
⇒ **改了提取逻辑必须把版本号 +1**，否则会命中旧缓存**且不报错**。

### 3.B 模型国产化替换

原版模型组合在本机（RTX 5070 Ti 16GB / sm_120 Blackwell / Windows）上是**死局**：

| 原模型 | 死在哪 |
|---|---|
| UI-TARS-1.5-7B | bf16 要 15GB+，直接 OOM |
| Hallo2 | 锁死 cu118，不含 sm_120 编译目标 |
| F5-TTS | CC-BY-NC，**非商用**许可证 |
| WhisperX large-v3 | 依赖链重，且我们已有更好的选择 |

替换结果 —— 本地侧从「5 个异构模型 / 3 套环境 / 2 个许可证雷」收敛为「2 个模型家族」：

| 模块 | 论文原模型 | 我们换成 | 许可证 | 关键理由 |
|---|---|---|---|---|
| 语音合成 | F5-TTS 0.34B | `Qwen/Qwen3-TTS-12Hz-1.7B-Base` | Apache-2.0 | 3 秒零样本克隆；当前最主流开源 TTS |
| 光标定位 | UI-TARS-1.5-7B | `mPLUG/GUI-Owl-1.5-4B-Instruct` | MIT | 同为 0–1000 归一化坐标，4.4B 装得下 |
| 转写 + 对齐 | WhisperX large-v3 | `Qwen3-ASR-0.6B` + `Qwen3-ForcedAligner-0.6B` | Apache-2.0 | 对齐误差 27.8ms（比 WhisperX 好 67–77%） |
| 数字人 | Hallo2 / FantasyTalking | **MuseTalk**（见 §3.I） | MIT | 绕开 sm_120 死结 |
| 音色相似度 | SpeechBrain ECAPA | CAM++（3D-Speaker） | Apache-2.0 | 精度与速度双超 ECAPA |
| 语言 + 视觉（API） | GPT-4.1 | `deepseek-flash`（DeepSeek-V4.1-Flash） | — | 原生图像输入 + 长上下文 |
| 视频理解（API） | Gemini-2.5-Flash | `Qwen3.5-Omni-Plus` | — | DeepSeek 不支持视频，这段必须换人 |

**显存峰值从 24GB+ 降到约 10GB**（靠串行分阶段加载/卸载）。

#### 两个「换 DeepSeek 几乎零改造」的关键事实【代码】

1. `wei_utils.get_agent_config()` **本就有兜底分支** ⇒ 换模型只需设
   `OPENAI_API_BASE` / `OPENAI_API_KEY` + 传 `--model_name_t deepseek-flash`，**不用改代码**。
2. `cursor_gen.py:55` 本就用 `factor=1000, model_type="qwen25vl"`，与 GUI-Owl **同源**。

#### 三条硬约束【实测】

1. **单卡必须按阶段加载/卸载** —— 上游用 `multiprocessing.Pool`，每个 worker 各持一份完整权重，
   单卡上必然 OOM，必须改串行。
2. **项目路径含中文** ⇒ 权重放英文目录（`E:\ai-models\`）；`HF_HOME` 必须在 E/F 盘。
3. **许可证雷区** —— `tencent/HunyuanVideo-Avatar` 是腾讯社区协议（**非商用**），
   商业交付只用 Apache-2.0 / MIT。

#### 一条 API 侧的行为坑【实测】

**DeepSeek 是推理模型**：`max_tokens` 给小了会返回**空 `content`**（预算全被 reasoning 吃掉）
**且不报错**，必须读 `finish_reason` 才能发现。

### 3.C 平台适配层（开发机不炸、服务器炸的那一类）

> 这一节是**迁移到学校 Linux 服务器**时最需要看的。这里的问题在本机**永远不出现**。

#### 核心事实：`open()` 的默认编码不同

Windows 上 `open()` 不带 `encoding` 用 **ANSI(cp936)**；Linux 上是 **UTF-8**。

全仓库扫出 **92 处**文本 `open()` 未指定编码 —— 其中 **81 处**在 `evaluation/` 那棵
论文评测子树里（**我们的链路不使用它**）。

#### 修法分两层，两层都要【代码】

| 层 | 做法 | 覆盖 |
|---|---|---|
| **逐处** | 我们链路上的 **11 处**显式写 `encoding="utf-8"`（含 **3 处写 `.tex`**） | 命令行直接跑 `pipeline.py` 也安全，不依赖环境变量 |
| **治本** | 流水线子进程环境加 **`PYTHONUTF8=1`**（`web/app.py::_run_job`、`scripts/gkk_3combos.py`） | 一条覆盖上游全部 `open()`，并**让 Windows 开发机行为对齐 Linux 服务器** |

> ⚠️ 第二层**推翻了早先的一个决定**。早先刻意只设 `PYTHONIOENCODING`
> （理由：把影响限制在标准流上、不改变 `open()` 默认编码）。
> 现在有反例了 —— 上游大量 `open()` 假设 UTF-8，那个理由不成立，改为**两者都设**。

#### 必须记住的判据：编译成功 ≠ 内容还在【实测】

| `.tex` 写法 | 合法 UTF-8 | tectonic 退出码 | PDF 里「测试标题甲」/「内容乙」/「→」 |
|---|---|---|---|
| 平台默认（cp936） | 否 | **0** | **False / False / False** |
| `encoding="utf-8"` | 是 | 0 | True / True / True |

tectonic 对 GBK 文件只打一句 `Invalid UTF-8 byte ... replaced by U+FFFD`，**退出码仍是 0**。
而我们的 `compile_tex` 只认退出码 ⇒ **编码问题必须在写入端解决**，
靠「编译没报错」永远发现不了。

> 顺带：写 emoji 这类**不在 cp936 里**的字符会直接 `UnicodeEncodeError` 崩掉；
> 而 `→`、`≥` 这些**在** cp936 里，所以是**静默**的。两种都要防。

自检：`scripts/verify_tex_encoding.py` + 冒烟第 13 组。

#### 其余三处平台适配

| 问题 | 本机表现 | 服务器表现 | 修法 |
|---|---|---|---|
| 中文字幕字体 | Windows 字体可用 | 字体不存在 | `_cjk_subtitle_font()` 按平台解析（Linux 用 Noto Sans CJK），可用 `PAPER2VIDEO_CJK_FONT` 覆盖 |
| 权重/缓存路径含盘符 | 正常 | 路径不存在 | 全走环境变量 + 默认值，代码里不出现盘符 |
| GPU 档位写死 | 正常 | 多卡跑不动 | 用 `talking_config` 的档位抽象（`*-local` / `*-server`） |

#### stdout 兜底【实测】

上游有 **4 处** `print` 带 emoji（`✅` / `⚠️`），在 GBK stdout 下抛 `UnicodeEncodeError`，
而**崩点在流水线最末端** —— 跑了一小时的最后一步崩掉。

修法：`pv_env.py` **模块级** `stdout/stderr.reconfigure(errors="replace")`
（该模块被 9 个模块导入，所以一处生效全局）。

#### 日志编码的复合坑【实测】

`run.log` **同时是**父进程的写入目标**和**子进程的 stdout 目标 ⇒ 两种编码混写
⇒ **任何单一解码器都读不了**。表现是**界面乱码 + 日志解析正则命中 0 条**（**不报错**，
因为「匹配不到」不是异常）。

修法：子进程加 `PYTHONIOENCODING=utf-8`；读取端 `_read_log_text()` 逐行回落。

> ⚠️ **迁 Linux 后不要删这一行** —— 历史 `run.log` 仍是混合编码的。

### 3.E 论文核心机制落地：配图提取 ★

> **这是本次整理中最有分量的一节**，因为它直接关系到论文那个「核心贡献」在我们的实现里是否真的存在。

#### 问题：树搜索在本项目里**恒为空转**【实测】

使用者在界面上打开 `--if_tree_search`，观察到「PPT 出得很快」，问是否真的走了树搜索。

查证结论：**开关生效、代码执行了，但一页都没改进过。**

⚠️ **这里有个特别容易骗人的地方**：`improve_layout()` 会**无条件**重写一份
`slides_refined.tex`（`slide_code_gen_select_improvement.py` 第 252–272 行）。
所以「产物变了 / 出现了 refined 文件」**不能**当作它工作过的证据。

**唯一可靠的判据**是 `result/latex_proj/proposal_imgs/` 是否非空：

| 观察 | 值 |
|---|---|
| `proposal_imgs/` | **空** ← 逐页的「4 个候选」循环一次都没进 |
| `proposal_*.tex` | **不存在** |
| `Slide Generation 26.6s` | 与不开开关同量级 |
| 带图 VLM 调用 | 没有发生（树搜索**唯一花钱**的那步） |

#### 根因之一：入选门槛要求「溢出页 **且** 该页含图片」

```
日志 warning 115 条 → 取前一半 57 条 → Overfull 48 条
涉及行号: 15,21,32,43,54,64,75,86,96,106,116,125 —— 各自落在 11 个 frame 里
slides.tex 的 \includegraphics 出现次数 = 0
=> 落入「含图片的 frame」的警告数 = 0
```

树搜索**只会缩放 `\includegraphics` 的宽度**，对纯文字溢出
（`Overfull \hbox ... in paragraph`）**无能为力**。

#### 根因之二：幻灯片里根本没有图

两层原因：

1. **结构性（影响所有论文）** —— 我们喂给模型的工程里**没有图片文件**：
   提示词拿到的路径清单就是 `['main.tex']`。而中文提示词明确写着
   「**若没有可用图片，不要写任何 `\includegraphics`**」⇒ **模型的行为是正确的**。
   上游原本要求使用者提供**带图的 LaTeX 工程**，我们自研的 `paper_ingest → paper_struct`
   把图丢了。
2. **个别论文本身** —— 有的 PDF 内嵌图片数就是 0。

#### 决定性 A/B：【实测】

决定性证据来自一次**正面**对照 —— 跑上游论文**自己的工程**（`result/zeyu`，
`iclr2025_conference` 那套，自带 `figure/` 目录 36 个文件）：

| | **工程带图**（`result/zeyu`） | **我们的 PDF 链路** |
|---|---|---|
| `slides.tex` 的 `\includegraphics` | **8 次** | **0 次** |
| 引用了哪些 | `figure/teaser.pdf`、`method.pdf`、`tree_search.pdf`、`vis.pdf`、`presenter.png`、`paper_topics_wordcloud.pdf`、`logo_.png`×2 | — |
| `proposal_imgs/` | **5 项**（含 `meraged.png`，即 2×2 对比图） | 空 |
| 4 个宽度候选 | `slidesproposal_{0.25,0.5,0.75,1}.{tex,pdf}` **都在** | 无 |
| 树搜索 VLM 调用 | **7 次 / 29912 token** | 0 次 |

⇒ **同一个机制，有图就工作，没图就空转。** 诊断闭环。

#### 解法：`scripts/paper_figures.py`（2026-09-19 实施）

从源文件提图 → `<工程>/figures/` → 生成清单 → 清单进幻灯片提示词。

```
<job>/latex_proj/figures/
    fig01_p06.jpg      ← 第 6 页的第 1 张（文件名纯 ASCII）
    fig02_p09.jpg
    index.json         ← 版本 / 源指纹 / 每张的页号·尺寸·图题
    README.txt         ← 给人看的
```

实测附给模型的清单：

```
本项目已经提供了论文里的插图（放在 figures/ 下），请优先在内容匹配的幻灯片上
用 \includegraphics 引用它们：宽度用相对值（如 width=0.8\textwidth），给它加 caption，
不要引用上面列表之外的图片。

  - figures/fig01_p06.jpg  —— 图1 AI训练语境用途表达的无监督结构识别结果
  - figures/fig02_p09.jpg  —— 图2 不同阈值条件下科研用途语义覆盖度（SCI）的变化趋势
```

#### 七个必须记住的设计决定

| # | 决定 | 不这么做会怎样 |
|---|---|---|
| 1 | 提图**只在 `pipeline.py` stage 1 内、`copy_folder` 之后**做一次 | 第一版写在 web 层往**源工程**写，而模型读的是**副本**，且 `copy_folder` 只在目标不存在时复制 ⇒ 重跑时副本是旧的、提示词读不到图，**而日志还显示「已附清单」**。△ **这正是本仓库反复踩的「两个读取者各读各的」坑**（`_result_dir` 那次也是） |
| 2 | 格式**一律转 PNG/JPEG** | 期刊 PDF 常见 `.jpx`（JPEG2000），而 XeTeX/tectonic 的 `\includegraphics` **不支持**它。实测那两张图**都是 jpx** —— 直接落原格式会得到「编译时才报错」的坑 |
| 3 | 有损源转 **JPEG** 而非 PNG | 161KB 的 jpx → PNG 膨胀到 **1134KB**；JPEG(q92) 是 **377KB**，视觉无差 |
| 4 | 文件名**纯 ASCII**，语义进 `index.json` | 本仓库因中文路径/编码踩过多次（LaTeX 宏包、stdout 编码、`cv2.imread`） |
| 5 | 没找到图**什么都不留**（连 `index.json` 一起删） | 留了会改变「工程文件清单」⇒ 纯文字论文的 deck 指纹变化 ⇒ 使用者为「其实什么都没变」**再付一次钱** |
| 6 | 幂等判据含**源指纹**（`version` + `source_sha1`） | 光比版本号时，「工程复用但换了源文件」会错误跳过 ⇒ 症状是「换了论文，幻灯片里还是上一篇的图」，**不报错** |
| 7 | 「工程自带图」= **`\includegraphics` 真正引用的文件** | 第一版按扩展名扫，把 `main.pdf`（编译产物，工程里必然有）当成图 ⇒ **纯文字论文也被判成有图**。这个 bug 是写测试时才发现的 |

**测试按文件头断言格式**（`\xff\xd8` / `\x89PNG`），不只扩展名 ——
否则「jpx 原样写出但名字叫 `.jpg`」会溜过去。

#### 筛选阈值（实测标定，不是猜的）

| 规则 | 值 | 依据 |
|---|---|---|
| 显示区域占页 | ≥ 3% | 实测两张真图占页 **35.2% / 6.8%**；装饰元素远小于此 |
| 源图短边 | ≥ 150 px | 过滤 logo / 图标 / 公式碎片 |
| 去重 | 按图内容 sha1 | 同一张图在多页重复出现只留第一处 |
| 上限 | 12 张 | 避免「图太多把文字挤没」 |
| 最长边 | ≤ 2400 px | 避免超大图拖慢编译 |
| 矢量簇 | 占页 ≥12% 且宽 ≥30% 页宽 | ⚠️ **未标定** —— 手头两篇 PDF 各聚类出 0 簇；规则保守、标记 `kind=vector` 便于事后核对 |

#### 缓存影响面（已按证据逐个处理）【实测】

新增 `figures` 字段进 `DECK_FIELDS`（**不进** `STRUCT_FIELDS` —— 图不影响 `main.tex`）
会让已有 deck 条目全部换键：

| `3c08e5d9e19e` | 孟欣影视表演（0 张图） | 输入与产出时完全一致 | **改名迁移** → `deac1030094f`，`job.json` 同步 |

#### 决定性验证：图真能进幻灯片【实测】

复刻流水线的复制+提图，再用 tectonic **真编译**一份含 `\includegraphics` 的 beamer：

### 3.F 成本控制：产物按输入指纹寻址（`scripts/artifact_cache.py`）

**动机**：整条链路里**只有两步联网付费**（结构化、幻灯片+讲稿）。重复跑等于白花钱。

```
jobs/_cache/struct/<指纹>/     论文 → main.tex
jobs/_cache/deck/<指纹>/       幻灯片 + 讲稿
```

#### 五条硬规矩

| # | 规矩 | 不这么做会怎样 |
|---|---|---|
| 1 | 两类缓存**各有一份写死的字段表** | 加字段前要问「**它会改变产物吗**」。少了 → 输入不同却命中（静默出错）；多了 → 白花钱 |
| 2 | **键只算一次、由调用方传下去**（`lookup_*` / `publish_*` 都收 `key=`） | 算两次必然漂移（流水线会改写 `main.tex`），表现为「**永远命中不了且不报错**」 |
| 3 | 输入取不到指纹 ⇒ **既不命中也不写入**（`REQUIRED_FIELDS`） | 不同输入会因为字段都是 `None` 而**塌成同一个键** |
| 4 | **只增不删** —— 模块里没有删除实现，`plan_gc()` 只读清点 | 误删正在被引用的缓存 |
| 5 | 命中会改 `config.stages` / `reuse_script` 并重建 argv ⇒ 收尾**必须把这两个一起落盘** | 续跑配置丢失 |

**字段表的取舍（刻意的不对称）**：

| 缓存 | 含 | **不含** | 理由 |
|---|---|---|---|
| `struct` | 源指纹、`main_tex_sha1` | 语言 / 人像 / 音色 | 这些不影响 `main.tex` |
| `deck` | 源指纹、`main_tex_sha1`、两种语言、论文类型、`llm_model`、`vlm_model`、数字人档位、`if_tree_search`、`figures` | 人像 / 音色 | **「换头像不废缓存」是特性** |

**通用判据**（本项目反复用到）：
> 凡「算出来的值**既用于查询又用于写入**」，就**只算一次**。
> 凡是「**路径/位置**」，问一句「**有几个地方在拼它**」。

**逃逸门**：`config.force_regenerate=True`；查看：`GET /api/cache`。

**还没做**：GPU 侧产物（TTS / 光标 / 数字人 / 成片）未进缓存；界面未提示「本次命中了缓存」。

#### 实物成本（**注意这里修正了一个旧口径**）【实测】

`result/<名字>/token.json` 的结构是 `{模型: [幻灯片桶, 讲稿桶], "cursor": 秒数}`。
统计全部样本：

| 样本 | 幻灯片桶 | 讲稿桶 | 合计 | 讲稿占比 |
|---|---|---|---|---|
| `result/gkk_en` | 13265 | 42343 | **55608** | **76.1%** ← 旧文档的「5.6 万 / 76%」出自这里 |
| `result/zeyu_zh_pilot` | 23086 | 24684 | 47770 | 51.7% |
| `jobs/…_f700` | 38391（含 1 次 fix） | 31569 | 69960 | 45.1% |
| `result/zeyu_zh_slides` | 68409（含 1 次 fix） | 40241 | 108650 | **37.0%** |

⇒ **「一篇约 5.6 万 token、讲稿占 76%」只在幻灯片一次都没返工的样本上成立。**
幻灯片一旦需要 `fix` / `improve` 返工，幻灯片桶就会反超（`zeyu_zh_slides` 里幻灯片占 63%）。
正确的说法是：**总量约 4.8 万 ~ 10.9 万 token，讲稿占比 37% ~ 76%，取决于幻灯片返工次数。**

### 3.G 内容寻址与去重

**问题**：同一份 PDF 被反复上传（改参数重跑很常见），每次都存一份、每次都重新提取。

**做法**：

```
jobs/_content/<sha1[:12]>/
    meta.json                     原文件名 / 大小 / 类型
    input/<sha1><ext>             ← 不可变
    ingest/                       派生正文（提取结果）
```

| 纪律 | 内容 |
|---|---|
| 解析上传 id 的**唯一入口** | `_upload_work()` |
| 校验的是 | 「一个路径段 + 不以点开头」—— **不是前缀白名单**（白名单挡不住 `content_../..`，却会误伤手工建的目录） |
| 命中判据 | 内容 sha1 + `paper_ingest.EXTRACTOR_VERSION` ⇒ **改了提取逻辑必须把版本号 +1** |
| 任务自包含 | 派生正文仍按任务复制到 `<job_dir>/ingest/` |
| 老目录 | `ingest_*` / `portrait_*` **不迁移**（可回收仅约 1.2 MB，不值得动历史记录） |

**产物目录也有唯一入口**：`_result_dir(job)`（优先 `config.result_dir`）。
**读取侧（产物列表 / 逐页索引 / 文件服务 / 总页数）必须走它** ——
直拼 `<job_dir>/result` 会让续跑任务**看到空产物**，
且「续跑的续跑」会被 **HTTP 400** 拒掉（第一次续跑时完全看不出来）。

### 3.H Web 服务层

> 原则：**只加外壳、不碰算法**。

#### 架构

```
React + Vite + TDesign 前端  ←REST/SSE→  FastAPI 后端  ←子进程→  Paper2Video 流水线
```

| 设计 | 理由 |
|---|---|
| **用子进程而非 import** | 显存释放靠进程退出保证；天然支持取消与崩溃隔离 |
| **不经 shell**：`Popen(argv, cwd=绝对路径)` | 避免 cmd.exe 被拦、MSYS 下中文路径失败 |
| **单 worker 串行队列** | 单卡 16GB 并行**必 OOM** |
| **只监听 `127.0.0.1`** | 不暴露到网络 |

#### 19 个接口【代码】

```
GET  /api/options                     可选项 / 开关文案与默认值 / 阶段定义（下发）
POST /api/key/verify                  API key 自检（区分欠费 / 鉴权 / 网络不通）
POST /api/ingest                      上传论文
POST /api/portrait                    上传头像
POST /api/voices/generate             造音色（MiMo，云端，一次）
GET  /api/voices/{key}/sample         试听音色
POST /api/voices/upload               上传自定义音色
POST /api/jobs                        创建任务
POST /api/jobs/{id}/rerun             续跑
GET  /api/jobs                        任务列表
GET  /api/cache                       查看产物缓存
GET  /api/jobs/{id}                   任务详情
GET  /api/jobs/{id}/events            SSE 实时进度流
POST /api/jobs/{id}/cancel            取消
GET  /api/jobs/{id}/artifacts         产物列表
GET  /api/jobs/{id}/pages             逐页素材索引
GET  /api/jobs/{id}/files/{rel_path}  文件服务
GET  /api/system/gpu                  GPU 状态
GET  /api/system/info                 系统信息
```

#### 三个设计要点

**① 阶段与总进度只有一处定义** —— `web/app.py` 的 `PHASES`（9 阶段，带权重 / 有无计数 / 卡住阈值）：

| key | 名称 | 权重 | 逐页计数 | 单位 | 卡住阈值 |
|---|---|---|---|---|---|
| `extract` | 分析论文 | 0.02 | 否 | — | 180s |
| `struct` | 结构化正文 | 0.10 | 否 | — | 300s |
| `slides` | 生成幻灯片 | 0.09 | 否 | — | 300s |
| `script` | 生成讲稿 | 0.05 | 否 | — | 300s |
| `tts` | 合成语音 | 0.29 | **是** | 页 | 180s |
| `cursor` | 光标定位 | 0.05 | **是** | **条** | 600s |
| `talking` | 生成数字人 | 0.32 | **是** | 页 | 420s |
| `merge` | 合成视频 | 0.06 | 否 | — | 300s |
| `finish` | 收尾 | 0.02 | 否 | — | 300s |

- 总进度由后端 `_phase_overall_pct` 算且**单调不减**
- **没有逐页计数的阶段不编造进度**，改用「已用 / 约」
- ⚠️ **计数单位随阶段不同（页 / 条）—— 混用会算出「18 页」这种荒谬值，而界面看着正常**
  （这是本项目遇过的最难发现的一类错误）
- 光标阶段权重给 0.05 是因为**方差极大**：PDF 文本定位全命中时只要几秒，
  回退到 GUI-Owl 的指令每条约 30 秒（实测 18 条 ≈ 9 分钟）。静态权重表达不了这种方差，
  所以界面上「**第 k/N 条 + 已用 X 分钟**」才是可信的那部分。

**② 数字人阶段的进度靠旁路取数** —— 批量路径是「一个进程跑完 N 页、之后才逐页 report」
（实测 14 条记录时间戳**全为同一秒**）⇒ 真正在跑的 5~10 分钟里 `progress.jsonl` **零记录**、
进度条停 100%、还会**误报「疑似卡住」**。
现由 `talking_gen._monitor_batch_progress` 后台线程轮询预期产物路径（**不改 MuseTalk**），
旧文件靠 `mtime + 1.0 >= started` 排除。

**③ SSE 的帧逻辑抽成 `_sse_frames()`** —— 两个原因：
- 心跳间隔可用 `PAPER2VIDEO_SSE_KEEPALIVE` 覆盖；
- **TestClient 对流式响应是缓冲的**，测心跳必须**直驱生成器**，否则测试会挂死（实测卡 7 分钟）。

**前端有一条硬纪律**：断流**必须重连并提示**。
原先 `es.onerror = () => es.close()` **禁用了 EventSource 自带重连**，
而产物只在 `job.status` 变化时拉一次 ⇒ **断流后唯一触发点永不到来**。
> 「**单一触发点 + 静默失败**」是同一类坏味道 —— 凡「只在 X 变化时刷新」都要加**轮询兜底**。

#### 三条「能构建但行为不对」的坑【实测】

| 坑 | 症状 |
|---|---|
| TDesign 主题 CSS 漏引入 | `--td-*` 变量**全未定义**，样式静默失效 |
| `ConfigProvider` 只读 `globalConfig` | locale 被**忽略** |
| build 带 `--noCheck` | **掩盖类型错误** ⇒ 现改为 `tsc -b && vite build` |

#### 音色方案（论文完全没有）

**接法**：**云端只造一次音色、逐页仍本地克隆**（不是逐页调云端 TTS）。

| 接法 | 结论 |
|---|---|
| 用 MiMo 逐页合成 | ✗ 云端、14 次调用、限时免费不可依赖 |
| **用 MiMo 生成一段音色样本，逐页本地克隆** | ✅ **推荐** |

- 音色一次定下 ⇒ 全片一致；免费期结束 / 断网 / 无 key 都**不影响出片**
- **参考文本必须由我们给定**（写死在 `mimo_voice.REF_TEXTS`），不能用
  `optimize_text_preview=True` —— 否则 `ref_text` 失控，只能回头靠 ASR 转写，
  **而 ASR 在本项目里是已知会转错的**
- **已生成的音色不需要 key**（缓存命中即可用）⇒ 攒下的音色资产长期有效
- 任何失败都**回落内置音色**，且回落原因进响应与 `run.log`（`[voice]` 行），**不阻断任务**

### 3.I 数字人后端：三次换型

> ⚠️ 这一节纠正了两份旧文档的矛盾记录，见 §5。

#### 换型史

| 代 | 模型 | 结果 |
|---|---|---|
| 0 | **Hallo2**（论文原版） | ✗ 锁死 cu118，**不含 sm_120 编译目标** |
| 1 | **InfiniteTalk**（Apache-2.0，原计划） | ✗ Windows 原生路线上 fp8 加载触发 CUDA 扩展 **JIT 编译**（nvcc 12.6 无 `compute_120`） |
| 2 | **LongCat-Video-Avatar-1.5**（MIT） | ✗ 注意力后端三重障碍：整帧 480p、注意力序列 **36480**、依赖 **flash-attn**（Windows 装不了）；权重 41.7GB |
| 3 | **MuseTalk**（`TMElyralab/MuseTalk`，MIT） | ✅ **当前默认，已跑通** |

#### 为什么 MuseTalk 能绕开 sm_120 死结【代码 + 实测】

| 维度 | LongCat-Video-Avatar | **MuseTalk** |
|---|---|---|
| 生成对象 | 整帧视频（480p） | **人脸裁剪 256×256** |
| 注意力序列长度 | 36480 | **1024**（256/8=32 → 32×32） |
| 注意力计算量 | 36480² ≈ 13.3 亿 | 1024² ≈ **105 万**（差约 **1270 倍**） |
| 注意力实现 | 依赖 `flash-attn`（Windows 装不了） | **标准 `diffusers.UNet2DConditionModel`**（SDPA 即可） |
| 权重大小 | 41.7 GB | **约 3.8 GB** |
| 架构 | 13.6B DiT | SD1.5 UNet + whisper-tiny |

`musetalk/models/unet.py` 的实际内容就是 `UNet2DConditionModel(**unet_config)` ——
没有自定义注意力、不引用 flash-attn / xformers。**小序列 + 标准实现 ⇒ 死结消失。**

#### 档位抽象（`talking_config.py`）【代码】

| 档位 | backend | 说明 |
|---|---|---|
| **`musetalk-local`**（**默认**） | `musetalk` | 本机 RTX 5070 Ti 16GB 单卡（Windows / sm_120） |
| `musetalk-server` | `musetalk` | 学校 8×A6000 48GB（Linux）—— 预留档位，**未实机验证** |
| `local-16g` | `longcat` | 本机（LongCat 路线，保留） |
| `server-8xa6000` | `longcat` | 服务器（LongCat 路线，保留） |

两个后端实现都**保留在代码里**，靠档位的 `backend` 字段分派。

#### MuseTalk 偶数尺寸补丁（**唯一不在本仓库 Git 里**的改动）★

上游 `-vf format=yuv420p` **不处理奇数尺寸**。人脸裁框为奇数（如 215×221）时
libx264 拒绝编码 → `temp.mp4` = **0 字节** → **整批页「跑完但无产物」**，
而**上游照样打印 `result is save`、耗时正常**。

已加 `crop=trunc(iw/2)*2:trunc(ih/2)*2`（源码里要用**转义双引号**，f-string 定界符）。
自检：`python scripts/verify_musetalk_patch.py`；`talking_gen` 批量入口也会提示。

> ⚠️ **MuseTalk 是独立仓库，不在本仓库 Git 里 ⇒ 重装后必须重打这个补丁。**

#### 复用与跳过判据（一处真实的数据丢失风险）

**复用只看 `result_dir`**：落点
`<result_dir>/talking_<backend>/<音频序号>/<参考图主文件名>/merge_video.mp4`，存在即跳过。

- `result_dir` 每任务一份 ⇒ **手动上传相同素材 = 新任务 = 一页都不跳过**
  （中间 workspace 的 `avatar_id` 带时间戳，**刻意禁止跨运行复用**）
- ⇒ **要省数字人那 10 分钟只能用续跑**，不能靠重新上传

**✅ 跳过判据已含音频指纹（2026-09-19 修）**：
原先判据只有（页号, 参考图主文件名），而合片函数签名里没有音频参数、
音轨取自数字人视频自带那条 ⇒ **音频变了而页数/人像名不变时该页被跳过、
旧配音进成片、新 TTS 音频静默丢弃**，全程不报错。
现每页目录落 `.inputs.json`（参考图 + 音频的 size/sha1），两处跳过点都比对；
**任何不确定（旧产物没指纹、指纹损坏、输入读不到）一律判为「不能复用」**。

#### 其他改造

- `talking_gen.py` 批量入口前**自检 MuseTalk 补丁**（否则就是上面那个 0 字节场景）
- `talking_gen.py` 旁路进度监控线程（见 §3.H ②）
- `merge_talking.py`（新增）承担合片

#### 三条测试纪律【实测】

1. **清理只删「进入作用域前 vs 现在」的快照差集** ——
   **绝不按名字前缀批量删共享目录**。曾因此**误删使用者正在运行的任务**
   （复盘见 `docs/事故记录-测试清理误删运行中任务.md`）。
   测试自己的命名空间（`smoke_`）例外。
2. **清理失败必须复核并报告** —— `ignore_errors=True` 会吞掉 Windows 上偶发的删除失败，
   残留会在**下一次**运行时造成「命中了上次遗留」的**假失败**。
   `main()` 末尾的 `_final_sweep()` 负责清掉并打印；
   **「按规矩保留（有任务引用）」与「删不掉」要分开报**。
3. **测试写了用户可见的持久化数据必须在 `finally` 清掉** ——
   曾有一个上传接口的测试往「音色库」落了 5 秒静音参考音频，
   于是使用者的「我的音色」列表里凭空多出一条垃圾。

#### 反面对照（证明测试不是「永远通过」的假绿灯）

- 第 13 组：`evaluation/` 里仍能扫出 81 处未指定编码的 `open()`
- 第 13 组：在**干净环境**（剔除 `PYTHONUTF8`）下不带 encoding 读那份提示词**确实失败**
  > ⚠️ 这条验的是「平台默认」，必须**另起进程且剔除 `PYTHONUTF8`** ——
  > 开发机 shell 里本身就设了 `PYTHONUTF8=1`，直接在宿主进程里测会得到「一切正常」的**错误结论**。
- 第 14 组：合成 PDF 的「大图留下 / 小图过滤 / 重复去重」；纯文字工程必须**什么都不留**；
  `main.pdf` **不算图**；工程自带图时**不提取**

| 3 | **权重路径** | 全走环境变量（`HF_HOME` / `MODELSCOPE_CACHE` / `TORCH_HOME` / `PAPER2VIDEO_WEIGHTS` / `PAPER2VIDEO_CKPT_DIR`）；**代码里不应出现盘符** |
| 4 | **GPU 档位** | 用 `talking_config` 的 `*-server` 档位；档位里写了「未实机验证」，**要在服务器上实测** |
| 5 | **`PYTHONUTF8=1`** | 已在 `web/app.py::_run_job` 设置；**不要删**。`_read_log_text()` 的逐行回落同理（历史日志是混合编码） |
| 6 | **前端构建产物** | `web/static/` 是构建产物且已 gitignore ⇒ 服务器上要装 node 跑一次 `npm run build` |
| 7 | **跑测试** | `CODEBUDDY_SAFE_DELETE_ENABLED=0`（沙箱删除守卫会拦测试自己的清理） |
| 8 | **多人使用还缺四件事** | ① 任务按人隔离（**凭据已按任务隔离** ✅）② 排队可见 ③ **按人统计 token** ④ **只监听内网**（现在只监听 `127.0.0.1`，若要多机访问需改） |
| 9 | **部署方式** | 推荐 Docker：中文字体进镜像、几十 GB 权重用挂载卷 |
| 10 | **成本预告** | 打开树搜索后，**每张溢出页**多 **4 次 LaTeX 编译 + 4 次渲染 + 1 次带图 VLM 调用**（`result/zeyu` 实测：7 次调用 / 29912 token） |
