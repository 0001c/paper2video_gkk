# A1 · 第三章12分钟目标讲稿

## 1. 从定义表达式到得到结果

同学们，我们刚写出 h = sigmoid(W·x + b) 这个表达式，但屏幕上并没有出现任何数字——为什么定义了公式，却还拿不到结果？


这是因为 TensorFlow 1.x 的图模式把‘描述计算’和‘执行计算’严格分开了：就像建筑师画好施工图，不等于房子已经盖好；图只记录了运算依赖关系，它本身不会自动算出数值。


要得到结果，必须完成三个明确阶段：第一，定义依赖——用 Operation 构建节点与边；第二，提供数据——通过 feed_dict 给占位符赋值，或初始化变量；第三，执行求值——在 Session 中调用 run，触发实际计算。


注意一个常见误区：创建 Session 或定义变量，并不等于完成了计算。比如 tf.Variable 只是声明了一个待初始化的存储单元；必须显式运行初始化操作，它的值才真正存在。


接下来，我们就用一个极简的例子——z = (a + b) × c——手算整个流程：先构造加法与乘法两个 Operation，再给 a、b、c 赋值，最后在会话中求出 z 的具体数值。这将清晰展示‘定义’与‘执行’之间的鸿沟如何跨越。

## 2. E1：计算图的两步运算

上一节我们写出了表达式 h = (a + b) * c，但它只是符号结构——没有数值。为什么？因为 TensorFlow 1.x 的计算图严格分为两步：先构建依赖关系，再提供数据求值。


看这个教学示例 E1：教材用符号 d = a + b、z = d * c 描述图结构；我们为手算补充具体值 a=2、b=3、c=4——注意，这些是教学辅助设定，非原书给定，仅用于演示流程。


第一步，按图中依赖顺序算 d：2 加 3 等于 5；第二步, 用 d 的结果算 z：5 乘 4 等于 20。必须严格按箭头方向执行，不能跳过 d 直接算 z。


这里，'加法'和'乘法'是 Operation，它们执行实际计算；而 d 和 z 是 Tensor，代表操作的输出——但定义阶段的 Tensor 只是‘待求值的占位符’，只有运行会话后才变成真实数字。


常见误区是以为写了 z = d * c 就等于得到了 20。其实不然：定义图不产生数值，就像画电路图不等于通电发光。必须显式启动会话、喂入数据、触发求值，才能拿到结果。


接下来我们要问：这个 z=20 的 Tensor 有什么属性？它的形状是多少？类型是什么？——这正是下一页要展开的张量三要素：秩、shape 和 dtype。

## 3. 张量的秩、形状与名字

上一节我们把 z = (a + b) * c 拆成 add 和 multiply 两个操作节点，现在关键问题来了：当图中出现 [1,2,3] 或 [[1,2,3],[4,5,6]] 这类数据时，系统如何识别它是一维向量还是二维矩阵？答案就藏在张量的三个结构属性里。


秩，就是轴的数量。向量 [1,2,3] 只沿一个方向延伸，所以秩是1；矩阵 [[1,2,3],[4,5,6]] 有行和列两个独立方向，秩就是2。注意：秩不是元素总数——这个向量含3个数，但秩仍是1。


shape 描述各轴的具体长度。向量 [1,2,3] 的 shape 是 [3]，表示第一轴长度为3；矩阵 [[1,2,3],[4,5,6]] 的 shape 是 [2,3]，即2行、3列。这就像快递箱标签：[2,3] 代表2层高、每层3格的抽屉柜。


dtype 是元素的数据类型，例如 tf.float32 或 tf.int64，它决定每个数值的存储精度与内存占用——本节暂不深究，但后续训练中它直接影响计算稳定性。


命名规则也很重要：add:2 表示 add 操作的第三个输出，因为索引从0开始计数。为什么需要编号？因为像 split 这样的操作会产出多个张量，必须唯一标识每一份输出。


最后务必分清两类边：数据边负责传递实际数值，比如 add 到 multiply 的边传的是 d=5；控制边只约束执行先后顺序，比如确保 multiply 等 add 完成后再启动，但它本身不携带任何数值——这是初学者最常见的混淆点。


思考一下：shape 为 [1,10] 的张量，它的秩是多少？对，是2——即使第一维长度为1，它仍是二维结构。这个细节直接关系到下一页 x 与 W 的矩阵乘法能否成立：内维必须匹配，而秩决定了维度兼容性。

## 4. 会话负责执行和资源管理

计算图已经构建完成——节点、依赖关系、张量的形状与类型都已登记，但此时所有张量仍处于‘待求值’状态，就像写好了数学公式却没代入数字。


真正让图动起来的是会话（Session）：它不预先执行全部运算，而是根据你请求的结果，反向追踪并仅执行必要的依赖路径。


核心方法 Session.run() 的作用是‘请求结果并执行所需依赖’——例如你 fetch h，它就自动触发 matmul、加法和 sigmoid，但绝不会额外计算梯度或更新参数。


这里必须澄清一个关键误区：创建会话绝不等于自动求梯度或启动训练。教材曾简略表述为‘启动Session会自动计算梯度’，这是不严谨的；梯度需显式添加 gradient 操作，训练还需优化器与循环控制。


会话还承担底层资源管理：它在运行时分配设备内存、调度计算任务；使用完毕后必须显式关闭——调用 session.close() 或用 with 语句包裹，否则张量占用的显存将持续累积，可能导致内存溢出。


举个教学例子：若定义 z = (a + b) * c，即使 a=2、b=3、c=4 已知，z 仍是符号表达式；只有执行 session.run(z)，系统才真正算出 d=5、z=20。定义与求值，严格分离。


下一页我们将聚焦：哪些张量需在 run 时通过 feed_dict 提供值（如输入 x），哪些需提前初始化（如权重 W 和偏置 b）——这正是会话机制协同占位符与变量的核心逻辑。

## 5. 占位符与变量：谁供值，谁初始化

我们已经构造好计算图，现在面临一个关键问题：图里的节点到底谁来提供数值？


x 是占位符（placeholder），它像一个空插座——图构建时只预留接口，真正运行时才通过 feed_dict 插入具体数据。


而 W 和 b 是变量（Variable），它们代表模型参数，需要显式初始化才能拥有初始数值；比如 W 从均匀分布随机生成，b 初始化为零向量。


这里有个常见误解：定义初始化器（如 tf.global_variables_initializer()）只是创建了一个操作节点，并不等于已经执行了初始化。就像写好‘开灯’指令，不按开关灯不会亮。


正确流程是四步闭环：先运行初始化操作 → 再用 feed_dict 提供 x 的值 → 然后求值 h → 最后关闭会话释放资源。


注意，本例仅做一次前向求值，没有梯度计算，也没有训练循环。Session 不会自动训练，也不会默认求所有梯度——它只执行你明确请求的 fetch 和其依赖。


思考一下：如果跳过初始化直接 run(h)，会发生什么？答案是报错——因为 W 和 b 还是未定义状态，就像试图用没装电池的遥控器开机。

## 6. E2：沿教材代码核对形状

我们已经定义了计算图的节点，现在关键一步：动手核对形状——当输入x是[1,10]，权重W是[10,5]时，矩阵乘法结果是否真为[1,5]？


矩阵乘法要求左矩阵列数等于右矩阵行数：x的第二维是10，W的第一维也是10，内维匹配，结果必为[1,5]。这就像10个特征通道汇聚到5个神经元，维度压缩是设计使然。


加上偏置b，它的形状是[5]。TensorFlow按最后一轴广播：[1,5] + [5]，等价于将b复制成1行，结果仍为[1,5]。注意——不是按第一轴广播；若误用[5,1]就会出错。


sigmoid函数逐元素作用，不改变张量结构，只对每个值做1/(1+exp(-t))变换。因此h的输出形状保持[1,5]，对应5个神经元的激活输出。


参数量直接由形状决定：W含10×5=50个标量，b含5个标量，共55个可训练参数。这是模型自由度的量化体现，也是后续梯度更新的对象。


必须强调：x和W初始化为随机值，教材未提供具体数值，因此我们绝不能编造一个确定的h输出。实验复现的目标是形状与结构一致，而非具体数字。


最后确认代码实现：教材PDF第14–16页明确写的是h = tf.nn.sigmoid(tf.matmul(x, W) + b)，即x乘W；顺序颠倒会导致维度不匹配，这是初学者高频错误点。

## 7. 从客户端到实际执行设备

我们已经构建了计算图，也核验了张量形状，现在进入关键一步：这张图如何真正被计算出来？


TensorFlow 1.x 的执行机制把‘定义’和‘运行’彻底分离——就像设计好一座桥的图纸后，还得调集工人、材料与设备，只在需要的位置架设承重结构。


这个运行过程由三个逻辑角色协作完成：client 负责提交整张图并发出求值请求。


master 接收请求后，不亲自计算，而是分析依赖关系，将任务划分为若干子图，分配给执行单元。


worker 才是实际执行者，它在 CPU 或 GPU 上运行被分配到的子图——注意，仅执行请求结果所依赖的部分，不是全图遍历。


常见误区是认为 client、master、worker 必须对应三台物理机器；实际上单机时它们可共存于同一进程，职责分明但无需物理隔离。


更关键的是：系统严格按需执行。例如你只 fetch h，那么 x → matmul(x,W) → +b → sigmoid 这条路径会被触发；图中未被引用的节点（如某个闲置 loss）根本不会参与计算。


这正是前一页强调‘定义图 ≠ 得到数值’的原因：Session.run 的本质，就是向这套协作系统发出一次精准的求值指令，而非自动遍历整张图。

## 8. 回顾：把一次求值完整串起来

现在我们把一次完整的前向求值串起来——从图的定义，到最终拿到结果h，中间每一步都不能跳过。


首先，定义图与张量：你用placeholder声明x，用Variable声明W和b，用matmul和sigmoid组合出h；这些只是‘蓝图’，没有数值，就像画好电路图但还没通电。


接着必须初始化变量：W和b是Variable，它们的初始值由random_uniform和zeros设定，但直到你显式运行tf.global_variables_initializer()，它们才真正被赋值；否则它们仍是未定义状态。


然后提供输入：x是placeholder，它本身不存数据，必须通过feed_dict传入具体值，比如一个shape为[1,10]的随机数组；漏掉feed_dict，Session会报错‘missing input for placeholder’。


进入执行阶段：调用session.run(h)，系统只计算h及其依赖路径上的节点——也就是x→matmul→add→sigmoid这条链，不会算图里其他无关节点。


为什么x乘W得到[1,5]？因为x是[1,10]，W是[10,5]，矩阵乘法要求内维匹配，10=10，结果外维是[1,5]；这是线性代数规则，不是TensorFlow特例。


若缺少feed_dict，会话无法填充x，直接崩溃；若跳过初始化，W和b仍是未定义张量，matmul会报‘Attempting to use uninitialized value’——这两个错误在实验中高频出现，务必警惕。


最后强调：定义、执行、训练是三个独立阶段。本例只有定义和单次执行，没有优化器、没有loss、没有循环；它不训练W和b，只是用当前值算一次h。


记住：图是静态描述，Session是动态执行引擎，变量需初始化，占位符需喂数据——这四点串起来，你就掌握了TensorFlow 1.x图模式的核心逻辑。
