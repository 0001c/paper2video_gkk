# Paper2Video 可视化改造方案（H5）

> 状态：**A / B / C 已定，D 已给建议**（见第 8 节）
> 目标读者：需要决定"做不做、怎么做"的人
> 相关代码：`Paper2Video-main/src/pipeline.py`、`language_config.py`、`pv_env.py`

---

## 0. 一句话目标

把现在只能命令行跑的流水线，包成一个网页：**上传素材 → 选语言 → 填 API key → 点开始 → 看进度 → 拿成片**。
不改变流水线本身的能力，只是把"记参数、开终端、读日志"换成表单和进度条。

---

## 1. 先说三个决定方案形态的事实

这三点不是背景介绍，它们直接决定了架构，绕不过去。

### 1.1 入口吃的是 LaTeX 源码目录，而使用者手里是 Word 或 PDF ← 核心缺口

现有入口参数是 `--paper_latex_root`，它要的是一个**含 `main.tex` 的目录**：

```
--paper_latex_root ../../assets/papers/gkk_mengxin
   └── main.tex        ← 必须有，文件名写死
```

而你现在手上的、以及以后任何一篇论文，拿到的都是 **PDF**。
现状是用例 `assets/papers/gkk_mengxin/main.tex` 的头部注释写得很清楚：

```
% 说明：由 PDF 提取重建的正文源码，仅作为「论文内容」输入生成流水线。
%      章节结构照原文（摘要 / 1 引言 / 2 风格即本体 / 3 本土化的跨国重构 / 4 结语 / 参考文献）。
```

也就是说：**这一步目前是人（我）手工做的，没有自动化**。
H5 如果只是"上传文件"的壳，使用者传个 Word 或 PDF 进去会直接失败 —— 这是本次改造真正要解决的核心问题。

**使用者的真实输入是 Word 或 PDF，不是 LaTeX**（2026-09-18 确认）：自己写的是 Word，
下载或提交的是 PDF。要求使用者准备 `.tex` 源码不现实。所以这一层必须做
**格式转换**：Word / PDF → 提取文本 → LLM 结构化 → `main.tex`。方案见 **决策 A（已定）**。

**为什么不能把原文件直接喂给 LLM**：幻灯片生成是让 LLM 读**论文正文**重写成 Beamer 代码。
给它 PDF/Word 二进制它读不了；要读就得先提文本，而"提成什么结构"恰恰是质量的关键 ——
章节划分错了，后面整套幻灯片的结构就跟着错，且**从成片里很难看出是这一步的错**。

### 1.2 只有一处花钱，而且能精确到 token

流水线分三个阶段，**只有 stage 1 调用外部 API**：

| 阶段 | 内容 | 用什么算 | 花钱 |
|---|---|---|---|
| **stage 1** | (LLM) 生成 Beamer 幻灯片代码 → 编译成 PDF → 转图片<br>(VLM) 看幻灯片图，写讲稿 + 光标描述 | DeepSeek-V4.1-Flash | **是** |
| **stage 2** | Qwen3-TTS 逐页合成音频 + GUI-Owl/PDF 坐标定位光标 | 本机 GPU | 否 |
| **stage 3** | MuseTalk 逐页生成数字人 + 拼接 + 烧字幕 | 本机 GPU | 否 |

实测用量来自 `result/<名字>/token.json`（这是现成的、可以读到前端显示）：

| 组合 | slide_gen | 讲稿生成 | 合计 |
|---|---|---|---|
| `gkk_en` | 13,265（输入 3,362 / 输出 9,903） | 42,343（输入 31,005 / 输出 11,338） | **55,608** |
| `gkk_zh` | 9,238（输入 3,707 / 输出 5,531） | 复用讲稿，未调用 | 9,238 |

两个副作用值得利用：
- **讲稿生成占 76% 的 token**（因为要把全部幻灯片图喂给 VLM）。所以 `--reuse_script` 是省钱主力，H5 上应该做成醒目的一键"只重跑后面两步"。
- 页数越多越贵（图越多 token 越多）。11 页 ≈ 9k，15 页 ≈ 13k，**大致线性**。

### 1.3 单卡 16GB + 一次 15~25 分钟 → 必须异步、必须串行

- 实测 stage 2+3 约 13~15 分钟（11~15 页），加 stage 1 总约 15~25 分钟。
- **不能并行**：单卡 16GB，两个任务同时跑必 OOM（MuseTalk + TTS 各自要几 GB 常驻）。
- 因此后端**不可能是"点一下等 20 分钟返回 JSON"**的同步接口，必须是：任务提交 → 后台队列（并发度 1）→ 进度流 → 完成后取产物。

另外有一个容易忽略的冲突源：**如果你（或我）在终端手动起了一个流水线，H5 再起一个就会抢显存**。
所以后端要在提交前检查是否已有 `pipeline.py` 进程/显存占用，占用时**排队或明确拒绝**，而不是让两个进程互相把对方搞崩。

## 2. 架构

三层，都很薄，**不修改流水线算法**：

```
┌─────────────────────────────────────────────────┐
│  H5 页面（React + Vite + TDesign）                │
│  上传素材 / 语言与类型 / API key / 进度与预览       │
└───────────────┬─────────────────────────────────┘
                │ REST（提交、查询）+ SSE（进度流）
┌───────────────▼─────────────────────────────────┐
│  FastAPI 后端                                     │
│  · 任务注册表（内存 + jobs/<id>/job.json 落盘）     │
│  · 单 worker 串行队列（GPU 独占）                   │
│  · 子进程管理：Popen(pipeline.py, cwd=src)         │
│  · 日志解析 → 结构化进度 → SSE                      │
└───────────────┬─────────────────────────────────┘
                │ 子进程（不经 shell，直接传 argv）
┌───────────────▼─────────────────────────────────┐
│  Paper2Video 流水线（现有代码，不动）               │
│  stage 1 → stage 2 → stage 3                     │
└───────────────┬─────────────────────────────────┘
                │
        jobs/<job_id>/result/   ← 产物落这里
```

**两个刻意的选择**：

1. **用子进程而不是 `import` 调用**。
   理由：流水线里 stage 间的显存释放是靠进程退出保证的（单卡 16GB，必须按阶段加载/卸载）。
   进程内复用会让显存只增不减。子进程还能天然实现"取消"（kill）和"崩溃不影响服务"。

2. **不经 shell 启动**。
   本机有两个已验证的坑：Bash 工具里调 `cmd.exe` 会被安全策略拦；MSYS 的 `cd` 在独立脚本进程里遇到含中文的路径会失败。
   所以后端一律 `subprocess.Popen([python, '-u', 'pipeline.py', ...], cwd=<src 绝对路径>)`，**cwd 用绝对路径、参数走 list**，不拼命令字符串。

## 3. H5 页面（四个区块）

单列纵向布局（`H5` 场景以手机/窄屏可用为前提，但视频预览在桌面上才实用，所以做成响应式、桌面为主）。

### 区块 ① 素材

| 字段 | 必填 | 说明 |
|---|---|---|
| 论文文件 | 是 | `.docx` / `.doc` / `.pdf` / `.tex` / `.zip`（见第 8 节决策 A） |
| 转换预览 | — | 非 `.tex` 输入时显示：`main.tex` 的章节树 + 提取出的正文开头，确认无误再开跑 |
| 人像图 | 是 | 正面照，建议 1:1、人脸占比大、无遮挡 |
| 参考音频 | 否 | 音色克隆源。**不传则按讲稿语言自动选**（中文→`zeyu_zh.wav`，英文→`zeyu.wav`） |
| 参考音频文本 | 否 | 传了音频才需要。不填会退回 ASR 转写，**实测 ASR 会转错**，建议鼓励手填 |

### 区块 ② 语言与类型

这里的选项**不要在前端硬编码**，应该从后端读（后端从 `language_config.py` 反射生成），
否则以后加一种语言要改两处。

| 字段 | 可选值 | 默认 |
|---|---|---|
| 语言预设 `--video_lang` | `en`（全英文）/ `zh`（英文幻灯片+中文讲解） | `en` |
| 幻灯片语言 `--slide_lang` | `en` / `zh` | 跟随预设 |
| 讲稿语言 `--script_lang` | `en` / `zh` | 跟随预设 |
| 论文类型 `--paper_type` | `auto` / `research` / `humanities` | `auto` |

⚠️ **命名有坑，UI 上要写清楚**：现在的预设 `zh` 实际是「**英文幻灯片 + 中文讲解**」，不是全中文。
直接显示 `zh` 会让人以为幻灯片也是中文。UI 上应显示完整描述，或用两个轴让用户自己选。

⚠️ **`--paper_type` 建议默认就是 `auto`，但把三个选项的后果写在旁边**（第 8 节会解释为什么这个别省）。

### 区块 ③ API key

只有**一组**（我核过：`DASHSCOPE_API_KEY` 在流水线里根本没被读到，只在 `scripts/check_env.py` 里做存在性检查；TTS/ASR 全是本地权重）：

| 字段 | 对应变量 | 默认 |
|---|---|---|
| API Key | `OPENAI_API_KEY` | 从 `.env` 预填（掩码显示） |
| API Base | `OPENAI_API_BASE` | 从 `.env` 预填 |
| 模型 | `--model_name_t` / `--model_name_v` | `deepseek-flash` |

**必做的一个按钮：提交前自检**。
这是从一次真实误判里学到的：DeepSeek **余额耗尽时不返回明确错误码，而是返回空响应或被截断的内容**，
症状和"网关抖动"完全一样 —— 我之前就据此判断成"偶发抖动"，排查方向整个偏了，白折腾一轮。

所以自检要做两件事：
1. 发一个**极小**的请求（`max_tokens=1` 级别），验证 key/base 通不通；
2. 明确区分三类失败：**欠费**（余额问题）/ **鉴权失败**（key 错）/ **网络不通**（base 错）。
   这三类的修法完全不同，含糊报"请求失败"等于没说。

### 区块 ④ 运行与产物

- 提交按钮 → 任务进入队列，返回 `job_id`
- 进度区：阶段点 + 页级进度（详见第 6 节）
- 完成后：内联视频播放器 + 逐页素材（幻灯片图、字幕文本、`cursor.json`）+ 下载

**交互上一个明确取舍**：进度用**内联的状态行 + 细进度条**呈现，不要用模态弹窗盖住页面。
理由是这类长任务用户会想切到别的标签页、或翻看已生成的幻灯片图，
被一个遮罩层挡住既没用又烦人；失败时也只需要那一行变红并展开详情，不需要弹窗。

| 讲稿语言 | `--script_lang` | |

| 结果目录 | `--result_dir` | 固定为 `jobs/<id>/result` |
| 阶段 | `--stage` | `["1","2","3"]`；续跑时只传 `["2","3"]` |

| 数字人后端 | `--model_name_talking` | 固定 `musetalk`（本机唯一可用） |
| 数字人档位 | `--talking_profile` | 固定 `musetalk-local`（本机单卡） |
| GPU | `--gpu_list 0` | 单卡写死 |
| **树搜索** | `--if_tree_search False` | ⚠️ **必须写死 False**，见下 |

**`--if_tree_search` 必须写死 `False`，且不要暴露到界面上。**

理由（这次核实后纠正了我原先的记录）：`pipeline.py:31` 的
`# from slide_code_gen import latex_code_gen` 是**注释掉的**，而 `if_tree_search=True`（默认值）时
会走到 `latex_code_gen` → 直接 `NameError`。也就是说**默认值 True 是坏的，必须显式传 False**。
之前几次"跑通"都是用 `pipeline_light.py`，掩盖了这一点。

这是个隐蔽的坑：不传就崩，而报错是 `NameError`，看不出跟"树搜索"有关。
H5 里把它固定掉，用户永远不会踩到；同时它也不该作为一个选项出现 —— **一个必然崩溃的开关没有暴露的意义**。

## 6. 进度机制

### 6.1 现有日志里已经有的进度信号

好消息：**不用改流水线就能拿到相当细的进度**，因为日志格式是稳定的：

| 阶段 | 日志特征 | 能推出 |
|---|---|---|
| stage 1 幻灯片 | `slide_gen` 完成 / `slides_rendered.pdf` 出现 | 页数（读 PDF 页数） |
| stage 1 讲稿 | `token.json` 更新 | 完成/未完成 |
| stage 2 TTS | `[speech_gen] 第 N 页合成完成` | **N / 总页数** |
| stage 2 光标 | `[cursor_gen] ...` | 逐句进度 |
| stage 3 数字人 | `[talking_gen] 第 N 页完成` | **N / 总页数** |

所以 **P0 阶段可以零改造**：后端 tail `run.log` + 正则匹配，换算成百分比推给前端。
"总页数"在 stage 1 结束后就能从 `slides_rendered.pdf` 的页数确定。

### 6.2 建议 P1 加的：结构化进度

日志解析是脆的（改一句 print 就失效）。建议加一个轻量约定：
流水线往 `jobs/<id>/progress.jsonl` 追加一行一行 JSON：

```json
{"stage": 2, "phase": "tts", "done": 7, "total": 11, "t": 1758140000}
```

后端只读这个文件 → 不依赖日志文本 → 前端可以做"每一页一个状态点"的细粒度展示。
这是唯一需要动流水线代码的地方，改动很小（在几个已有的 print 旁边加一行）。

### 6.3 要区分"在算"和"卡死"

真实教训：TTS 曾出现**单页从 30 秒退化成 10 分钟以上**（自回归退化，与文本无关）。
现在已加了时长上限护栏（撞上限自动改为逐句合成）。但 H5 上需要让用户看出区别：

- 日志超过 N 分钟没更新 **且** GPU 利用率接近 0 → 提示"疑似卡死，可取消"
- 日志在更新、GPU 有占用 → 显示"正在计算（本机单卡，单页可能需要数十秒）"

这个判断用**日志 mtime + nvidia-smi** 就够，不需要复杂的心跳协议。

## 7. API key 处理

| 问题 | 决定 |
|---|---|
| 存哪 | 后端**内存**（按会话绑定），默认**不落盘** |
| 回显 | 只回显前后各 4 位（`sk-xxxx****xxxx`），永不把完整 key 发给前端 |
| 日志 | 必须过滤。key 绝不能出现在 `run.log` / 接口响应 / 异常栈里 |
| 要不要写 `.env` | 给一个**显式的**"保存为默认"开关，点了才写，并提示这是明文文件 |
| 服务监听地址 | **只监听 `127.0.0.1`**。这个界面上有 API key 和本机文件系统访问，不能暴露到局域网 |

最后一条不是过度谨慎：上传接口 + 文件服务 + key 输入框的组合，一旦监听 `0.0.0.0`，
同一网络下任何人都能读到你 `jobs/` 里的所有产物。

## 8. 决策点（A 已定，B/C/D 待确认）

### 决策 A：论文输入格式 —— ✅ 已定（2026-09-18）：支持 `.tex` / `.pdf` / `.docx` / `.doc`

使用者要上传的是**自己写的 Word** 和**下载/提交的 PDF**，所以按真实来源设计输入：

| 输入 | 提取方式 | 实测结论 | 结构化成本 |
|---|---|---|---|
| `.tex` / `.zip` | 直接落盘，校验 `main.tex` 存在 | 无损，无需转换 | **0** |
| `.docx` | `python-docx` 逐段读（保留标题层级，可提取内嵌图） | 库已验证可用（1.2.0） | 1 次 LLM |
| `.doc`（OLE2 老格式） | ① 引导另存为 `.docx`；② 后备纯 Python 粗提取 | 实测可从 `WordDocument` 流提出中文正文 | 1 次 LLM |
| `.pdf` | `PyMuPDF` 提取文本（可选提取内嵌图） | 已验证：19 页论文每页 4000~5000 字符 | 1 次 LLM |

除 `.tex` 外都需要一次 **LLM 结构化**：把提取出的文本重组成带章节结构的 `main.tex`
（含 `\usepackage{ctex}`，表格用 `tabularray` —— 这两条是已实测的硬约束）。
用 DeepSeek 的 1M 上下文可整篇一次喂入，预估一篇 1~2 万 token。

#### 实测得到的三条结论（都改变了实现方式）

**① 不要用 Office / WPS 的 COM 自动化 —— 实测会挂死。**
`win32com` 调 `Word.Application` 时**连到了使用者正在运行的 WPS 实例**并挂死 2.5 分钟
（`Documents.Open` 弹对话框、无返回）。H5 后端要无人值守运行，不能依赖桌面上
某个应用的状态。所以一律走纯 Python：`python-docx` + `olefile` + `PyMuPDF`。

**② `.doc` 老格式在 Python 生态里支持很差，但有后备路径。**
`python-docx` **只支持 `.docx`**，读 `.doc` 直接报错。实测该 `.doc` 是 WPS 保存的
OLE2 容器（流里带 `WpsCustomData`），但 `WordDocument` 流以 **UTF-16LE 存正文**，
纯 Python 能粗提取出可读中文（样本 6.2k 字）。
**策略**：优先引导"另存为 `.docx`"（10 秒操作、质量最好），后备才用粗提取，
并在界面上标明"提取可能不完整，请核对预览"。

**③ PDF 提取必须做「行合并」，不能逐行拼。**
PDF 的一行句子会被列宽硬切成多行 —— 实测出现
`...conveying the researcher's scholarly id` 这种**断在半句**的情况。
必须按标点判断句末再合并，否则喂给 LLM 的文本是碎的，重建出的章节结构跟着碎。

#### ⑤ 同一篇论文有 `.doc` 与 `.pdf` 两版时，优先用 `.pdf`

实测（拿同一篇论文的两个版本逐步交叉比对）：

| 指标 | `.doc` | `.pdf` |
|---|---|---|
| 中文字数 | 2934 | 2811 |
| 章节命中 | 5/5 | 5/5 |
| 内容 | 两者等价（句子级重合约 50%，差异来自切句方式，不是内容缺失） | |
| **信噪比** | **混入评阅表字段**（评阅表 / 学号 / 姓名 / 满分分数 / 签字） | **干净** |

两者内容等价，但 `.doc` 的粗提取**必然**会带上文档开头的表单区
（"课程论文评阅表"之类），而 `.pdf` 是纯正文。LLM 通常能忽略这类噪声，
但表单字段出现在**开头**，会影响它判断"这是不是一篇论文"。

⚠️ **顺带记一个我自己踩了两次、方向相反的坑**（对实现者比使用者更重要）：
`.doc` 的抽取正则最初是**白名单**字符类，漏一个标点就会**无声截断**句子 ——
实测 `尼诺·法兰克` 里的 `·`（U+00B7）漏在名单外，
「摘要: 黑色电影自1946年被法国影评人尼诺」就断在那里，且没有任何报错。
但把它改成"放开全部可打印范围"**更糟**：WordDocument 流里的二进制结构数据
会被解码成"看起来像中文"的垃圾段（`襜鉾髭谝究牨猨砨`），句子数虚增、
章节命中从 5/5 掉到 2/5 —— 垃圾把正文淹没了。
**结论：要扩充白名单，不要取消白名单。**
（最终判据：段内汉字落在 GB2312 之外的占比 ≥ 50% 即判为残留并丢弃，
实测残留段是 50%~100%、真实正文与表单字段都是 0%。）

#### ⑥ 不要指望 Word 的标题样式（实测：真实文档 heading 数为 0）

我原先的假设是 `.docx` 比 `.pdf` 强在"能拿到标题层级"，用自造样本测也确实有。
但拿**真实文档**一测就穿帮了：**使用者手写的 Word 普遍不使用标题样式**
（靠手动加粗/放大做标题），`python-docx` 读到的 heading 数是 **0**。

影响：**`.docx` 相对 `.pdf` 的"结构优势"实际上不存在**。三种格式都得靠
**LLM 从正文内容推断章节结构**，这直接提高了对结构化 prompt 的要求 ——
必须在 prompt 里明确写「标题可能没有任何样式标记，请按内容语义与数字序号
（`1` / `1.1` / `三`）识别章节」，否则结构化质量会明显偏低。

#### 三方交叉比对（同一篇论文的 `.doc` / `.docx` / `.pdf`）

| 格式 | 中文字数 | 去重句 | 噪声词 | 标题层级 |
|---|---|---|---|---|
| `.doc` | 6161 | 221 | 6 | 无此信号 |
| `.docx` | 6067 | 210 | 5 | **0** |
| `.pdf` | 6041 | 210 | **1** | 无此信号 |

重合度：`doc vs docx` **89.0%**（内容几乎一致）；两者 vs `pdf` 约 66~70%
—— 这个差异主要来自**切句方式**而非内容缺失（PDF 的句子会被列宽切开）。
**结论：三种格式内容等价，`.pdf` 信噪比最高，优先用它。**

#### 顺带能拿到的增益：图片

现有 `gkk_mengxin/main.tex` 是**零图**的，导致整套幻灯片无图。
`.pdf`（PyMuPDF）与 `.docx`（python-docx）都能提取内嵌图。建议提取到 `figures/`
并让 tex 可引用 —— 这是"上传 PDF 自动转"相比人工重建的一个实际增益。

#### 「转换结果可预览」这一步仍然要保留

理由不变：转换错了**下游无法补救**，而从成片里几乎看不出来。
**只读预览应在 P0 就有**（成本很低），编辑能力放到 P2/P3。

#### ④ 已知局限：PDF 的标题识别还不够准（P1 优化）

提取时只有文本、没有版式信息，所以标题行会和作者行/正文粘在一起
（实测 `PAPER2VIDEO: AUTOMATIC VIDEO GENERATION FROM SCIENTIFIC PAPERS`
与 `Zeyu Zhu* Kevin Qinghong Lin* ...` 被并成一段），页眉（如 `preprint`）
也会混进正文。

优化方向（放 P1）：
- 用 PyMuPDF 的 `get_text("dict")` 取每个 span 的 **字号**，按字号识别标题
  —— 标题字号通常显著大于正文，这是最可靠的判据；
- **剔除页眉页脚**：在多数页面的相同纵向位置重复出现的行，判为页眉页脚丢弃。

这两条不需要 LLM，纯本地可做，性价比高。

### 决策 B：界面范围 —— ✅ 已定：B2

含**内联视频播放器 + 逐页素材浏览**（幻灯片图 / 讲稿 / 光标 JSON）。
理由：「生成完了，但还得去文件夹里翻」体验上等于没做完；而内联预览只是静态文件服务 + `<video>`。

### 决策 C：历史任务与续跑 —— ✅ 已定：做

`--stage` 与 `--reuse_script` 已经支持续跑，界面上不做就浪费了。
实现：**任务列表 + "只重跑 stage 2/3"按钮**（省 76% 费用）。放 P1。

### 决策 D：技术栈 —— 建议 React + Vite + TDesign + FastAPI

**理由（按权重排序）**

1. **组件复用是最大收益**：上传（带真实进度）、表格（任务列表）、进度条、消息提示、
   对话框、标签页 —— TDesign 全都有。自己写这些要花数倍时间，而且**长任务界面的
   状态同步最容易写错**，正是组件库已经帮你解决的那类问题。
2. **决策 C 已确认**：任务列表 + 续跑 + 产物浏览让界面状态明显变多，
   框架化的收益随之上升；纯手写 DOM 在这个复杂度上会开始失控。
3. **你的熟练度**：这套栈你本来就在用，出问题能自己改 —— 这是维护成本里最大的一项。
4. **风险低**：本地工具，不必考虑 SEO、首屏、多端兼容这些前端常见的坑。

**但要加三条约束，避免过度工程**：

| 约束 | 理由 |
|---|---|
| `vite build` 产物由 FastAPI 用 `StaticFiles` 直接服务 | **运行时只有一个进程**，不用同时管前后端两个服务；开发时才用 vite dev server 的 HMR |
| 不引路由库、不引全局状态库 | 单页 + `useState` / `useReducer` 足够；上了 Router / Redux 只会增加你要维护的东西 |
| SSE 用一个自定义 hook 封装 | 进度流是全应用唯一「持续变化」的状态，集中在一处比散落各组件要好 |

**为什么不选单页 HTML（零构建）**

它在「只想要个能跑的最小验证」时更快出结果，但一旦加上
「上传进度 + SSE 实时进度 + 任务列表 + 视频预览」，手写的状态同步会迅速失控 ——
而这几项正是已确认的 B2 + C。

**一个额外变量：如果有多个使用者**

你提到过"使用者"，所以要先想清楚这工具是只给你自己用，还是也给别人用：

- **只自用**：前端可以不打包，`vite dev` + 后端两个进程也行，怎么快怎么来。
- **给他人用**：需要**一键启动**（一个脚本同时拉起后端并打开浏览器），
  并考虑对方机器上的 Node / Python 环境。这会让"静态产物由后端服务"
  从"建议"变成"必须"。

## 10. 交付时的人工测试要点

按你之前的约定，前端由你本人验收。这里列**必须覆盖的点**（含边界与异常）：

**上传与格式转换**（决策 A 是本次最大的新增风险面，测试重点放这里）
- [ ] 三类输入各跑一次：`.docx` / `.pdf` / `.tex`，确认都能进到"转换预览"
- [ ] **`.doc`（老格式）** —— 应走"引导另存为 `.docx`"或后备粗提取，**不能直接崩溃**
- [ ] **扩展名与实际格式不符**：把 `.docx` 改名成 `.pdf` 上传 —— 应靠 magic bytes 嗅探识破，
      而不是解析到一半才失败（实测很多文件扩展名不可信）
- [ ] 章节结构是否被正确识别 —— 对照原文数一遍：摘要 / 引言 / 结论 / 参考文献在不在
- [ ] 同一篇论文的 `.doc` 与 `.pdf` 各传一次，**对比哪个预览更干净**
      （预期 `.pdf` 无表单噪声；`.doc` 会带上"课程论文评阅表"之类的字段）
- [ ] **PDF 的行合并**：找一段跨行的句子，看预览里是否被切成半句
- [ ] 双栏排版的 PDF —— 提取出的文字顺序是否错乱（PDF 最常见的翻车点）
- [ ] 加密 / 扫描版 PDF —— 应明确报"无法提取文本"，不要静默产出一个空的 `main.tex`
- [ ] 超大文件（>50MB）—— 上传要有真实进度，不能看起来像卡死
- [ ] 转换出的 `main.tex` **能否编译**（中文必须 ctex + tabularray，见已知的宏包冲突）
- [ ] 人像图：无脸 / 多脸 / 侧面 —— 数字人环节会失败或效果极差，**能否在提交前提示**
- [ ] 上传中途取消 / 刷新页面 —— 不应留下半个破损的素材文件

**语言与类型**
- [ ] 预设选 `zh` 后，界面是否清楚说明"幻灯片仍是英文"
- [ ] 手动改 `--slide_lang` 后，预设是否被正确覆盖（优先级：显式轴 > 预设）
- [ ] `--paper_type` 选 `humanities` 后重新生成，幻灯片里**不应出现**任何数据集名/指标/对比表

**API key**
- [ ] 故意填错 key → 应报"鉴权失败"，并说明去哪改
- [ ] **余额不足的 key** → 应报"欠费"，而不是含糊的"请求失败"（这是最需要测的一条）
- [ ] 刷新页面后 key 是否还在（内存存储会丢，这是预期行为，但要让用户看懂）
- [ ] 检查 `run.log` 和接口响应里**不含完整 key**

**运行与容错**
- [ ] 提交后立刻再点一次 → 不应创建两个任务（按钮应禁用 / 后端应幂等）
- [ ] 跑到一半点取消 → 进程真的被杀、显存真的释放（用 `nvidia-smi` 确认）
- [ ] 跑到一半**手动**在终端起另一个流水线 → H5 应提示显存占用，而不是两个都崩
- [ ] 生成到一半关掉后端再重启 → 任务状态应能恢复（或明确标记为"中断"），不能显示成"正在运行"
- [ ] 完成后视频能拖进度条（验证 Range 请求支持）

**产物**
- [ ] 视频有音轨（不是静音）
- [ ] 成片时长 ≈ 各页音频时长之和
- [ ] 数字人逐页时长 = 对应音频时长（零偏差）
- [ ] 光标落点准确率（现有 `scripts/verify_gkk_3combos.py` 可直接复用到 H5 产物上）

## 11. 风险与已知坑

| 风险 | 影响 | 对策 |
|---|---|---|
| Word / PDF → LaTeX 转换有误 | 结构错，成片里难以察觉 | 转换预览让使用者过一眼（P0 必做） |
| `.doc` 老格式支持差 | `python-docx` 直接报错 | 引导另存为 `.docx`；后备走 OLE2 粗提取 |
| 用 Office / WPS 的 COM 自动化 | **实测连到使用者正在用的 WPS 实例并挂死 2.5 分钟** | 一律纯 Python，不碰桌面应用状态 |
| **断电 / 进程被强杀** | 任务卡在"运行中"，半成品与显存残留 | 启动时按 pid 与心跳核对任务状态并标记"中断"；产物按阶段可复用（`--stage`） |
| API 余额耗尽伪装成空响应 | 误判为"网关抖动"，白排查一轮 | 提交前自检，明确报"欠费" |
| **输出撞 `max_tokens` 被截断**（同样表现为"空响应"） | 与上一条症状一样、修法相反 | 报错现场打印 usage 的 completion_tokens 并分诊（已实现） |
| TTS 自回归退化（单页 10 分钟+） | 任务看起来卡死 | 已有时长护栏；UI 上区分"在算 / 卡死" |
| 单卡被手动进程占用 | 双进程抢显存互崩 | 提交前检查 GPU 与 `pipeline.py` 进程 |
| 任务含中文路径 | 部分模型加载器报错 | job 目录用英文 id；素材落盘避免非 ASCII 文件名 |
| 本机文件操作慢（受腾讯电脑管家影响） | 上传/复制大文件耗时长 | 上传流式落盘，不整块读进内存；界面给真实进度 |
| 长任务让页面失去连接 | 使用者以为失败了 | 任务状态以后端为准，页面重连后重新拉取，不依赖前端内存 |

## 12. 部署与迁移（学校服务器）

**背景（2026-09-18 确认）**：本工具当前在使用者本机（Windows + RTX 5070 Ti **16GB 单卡**）
开发，向导师演示通过后**会搬到学校服务器使用**。这条迁移路径改变了若干设计约束，
而其中一部分问题**在开发机上完全看不出来**。

### 12.1 迁移阻塞项（不提前处理，就会在演示当天才暴露）

| 项 | 原状 | 迁移后的后果 | 处理 |
|---|---|---|---|
| **中文字幕字体** | `language_config.py` 把中文讲稿字体**硬编码为 `Microsoft YaHei`** | Linux 无此字体 → libass 回退到 `subtitle_render.DEFAULT_FONT`，而那段代码的 Linux 分支是 **`DejaVu Sans`（不含任何汉字）** → **中文字幕变方框或丢失** | ✅ 已改为按平台解析（`_cjk_subtitle_font()`），Linux 默认 `Noto Sans CJK SC`，可用 `PAPER2VIDEO_CJK_FONT` 覆盖。**服务器需装 `fonts-noto-cjk`** |
| 权重与缓存路径 | `.env` 指向 `E:\ai-models\...` | 服务器上路径不存在 → 加载失败 | 全走环境变量 + 默认值；**代码里不要出现盘符** |
| GPU 档位 | `--talking_profile musetalk-local`（单卡 16GB 写死） | 服务器可能是多卡 / 显存更大 | 用 `talking_config` 的档位抽象，提交前按实际显存探测；**不要写死** |
| Windows 专有调用 | 已排查：当前**无** `win32` / 注册表 / `startfile`（COM 路线在输入层就已被排除） | — | 保持现状；新增代码也不要引入 |

⚠️ 字体这条危险在于：**英文讲稿不受影响**（DejaVu 覆盖拉丁字母），
所以「英文演示正常、中文演示炸了」这种组合最容易蒙混过关 —— 而中文才是主要使用场景。

### 12.2 从"自己用"变成"几个人用"要补的四件事

1. **任务隔离**：任务目录按人分开（`jobs/<user>/<job_id>`），产物互不可见。
   本机自用不存在这个问题，多人用就必须有。
2. **排队可见性**：单卡仍是串行队列，但要**显示"前面还有几个任务"**，
   否则使用者不知道要等多久。
3. **用量归集**：若 API key 由学校统一提供，需要按人统计 token 消耗
   （`token.json` 已经在记，按人汇总即可）。
4. **不要暴露到公网**：即使上了服务器，也**只监听内网 / `127.0.0.1`**，
   或至少加一层认证 —— 这个界面上有 API key 和文件系统访问。

### 12.3 部署方式

**推荐 Docker**：GPU 驱动之外的依赖（CUDA runtime、ffmpeg、TeX、**字体**）
全部锁进镜像，避免"换台机器就装不上"。

两个注意点：
- **中文字体必须进镜像**（见 12.1，这是最容易漏的一条）
- **权重不要进镜像**（几十 GB），用挂载卷，`.env` 指向挂载点

不用 Docker 的话，至少要有一份**锁版本的 requirements** 和一份
「服务器需预装什么（ffmpeg / TeX / 中文字体 / CUDA / 驱动版本）」的清单。

### 12.4 演示前必做的一次彩排

既然要当着导师演示，**要专门彩排一次"中文全链路"**：

- 中文讲稿 + **中文幻灯片**（走完整中文路径 —— 字体问题只在这条路径上出现）
- 用一篇**真实论文**走完整流程，而不是已有的 `gkk_mengxin`
- 完成后核对：字幕是中文（不是方框）、时长正常、有音轨

目的是避免"演示当场才发现某个组合从来没跑过"。
