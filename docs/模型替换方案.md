# Paper2Video 模型替换方案（2026-09 版）

> 目标：把论文/仓库里的**全部本地模型换成当前最新的国产开源模型**，把**全部 API 模型收敛到 DeepSeek-V4.1-Flash**，并保证能在本机 **RTX 5070 Ti 16 GB（sm_120）** 上真正跑起来。
> 选型原则：**优先可用（能装、能跑、显存够）> 其次效果**；同等条件下优先国产、优先宽松许可证。
> 依据：`docs/Paper2Video.pdf`（arXiv 2510.05096v2）、`Paper2Video-main/src/` 源码，以及 2026-09-16 对 HuggingFace API 的一手核验（核验脚本：`scripts/hf_check.py`）。

## 一、为什么原组合在你这台机器上是死局

先把"必须换"的硬约束列清楚，否则容易误判成"随便升级一下"。

| 原模型 | 在 RTX 5070 Ti 16 GB 上的实际障碍 |
|---|---|
| F5-TTS | 显存没问题，但**许可证是 CC-BY-NC（禁止商用）**；且 `f5_tts==1.1.6` 依赖 triton/vocos，Windows 原生安装链条脆 |
| UI-TARS-1.5-7B | bf16 权重约 14–15 GB，加视觉编码器与 KV cache 需 ≥16–18 GB，**正好卡在 16 GB 天花板上，开箱必 OOM** |
| WhisperX | 能跑（~3 GB），但**对齐精度是这次的短板**，且 `speech_gen.py:53` 在逐页循环内被调用会反复重载大模型 |
| Hallo2 | **双重死结**：① 官方锁定 torch 2.2.2 + CUDA 11.8，而 cu118 的 torch **不含 sm_120 编译目标**，装上即报算力不支持；② 只测过 Ubuntu，Windows 原生要凑 insightface/mediapipe/basicsr 一串原生依赖。显存 12–16 GB 还需独占 |
| SpeechBrain ECAPA | 能跑，但精度与速度均已被国产模型超越 |
| GPT-4.1 / Gemini 系 | 能用，但成本高、且脚本里 API Key 是**硬编码空字符串** |

**核心矛盾**：论文的设计前提是 **逐页并行**（`multiprocessing.Pool` 按 `gpu_list` 铺开，**每个进程各加载一份完整模型**，因此官方要 8×A6000 48G）。单卡要跑通，必须把"并行"改成"串行 + 分阶段加载"。

## 二、本地模型逐个说明

### 1. 语音合成：F5-TTS → Qwen3-TTS-12Hz-1.7B-Base

**原方案问题**：F5-TTS 权重 0.34B，显存只要 2–4 GB，但许可证是 **CC-BY-NC**——这个仓库的 README 里也标了非商用。如果这个工具将来要用于你的餐饮门店短视频或对外交付，F5-TTS 是个法务雷。

**替代**：`Qwen/Qwen3-TTS-12Hz-1.7B-Base`（阿里通义，2026-01 发布）

一手核验（HF API 实测）：

```
license = apache-2.0
params  = 1.93B
downloads = 3,783,983     ← 当前 HF 上最主流的开源 TTS
lastModified = 2026-01-23
```

- **功能对位**：Base 版本正是"零样本音色克隆"分支，3 秒参考音频即可克隆，与 F5-TTS 的角色完全一致。
- **显存**：权重约 3.9 GB，实际运行 4–6 GB（比 F5 略高，但 16 GB 卡毫无压力）。
- **加分**：10 种语言、首包流式延迟 97 ms、官方支持 vLLM；**与第 2、3 项同属 Qwen 生态，依赖栈可以合并**。
- **效果参考**：Seed-TTS-Eval 上中文 WER 2.12 / 英文 2.58 / 说话人相似度 0.89（自报数据，优于同表 MiniMax 与 ElevenLabs）。

**备选（按需）**：

| 模型 | 许可证 | 显存 | 何时选它 |
|---|---|---|---|
| `IndexTeam/IndexTTS-2` | Apache-2.0（GitHub） | 4 GB 起 / 7–8 GB 常规 | **需要"精确控制时长"或"情感解耦"时**——这是它独有的能力，社区在 RTX 5070 Ti 实测 RTF 0.44 |
| `FunAudioLLM/Fun-CosyVoice3-0.5B-2512` | Apache-2.0 | ~8 GB | 需要大量**中文方言**（18 种）或 2026 年中文自然度口碑第一时 |

> **关于时长控制**：这一点对本项目有特殊价值。幻灯片合成语音的长度直接决定光标动画与最终合片节奏，Qwen3-TTS 与 F5-TTS 都没有显式时长控制。**如果后续发现音画对不齐，优先把 TTS 换成 IndexTTS-2**，而不是去调后处理。

**代码改动点**：`src/speech_gen.py`
- 第 8 行 `from f5_tts.api import F5TTS` → 改为 transformers 加载 `Qwen3TTSForConditionalGeneration`
- 第 22 行 `f5tts = F5TTS()` 所在的 `inference_f5()` → 新增 `inference_qwen3tts()`
- 第 54 行 `if model_type == "f5"` → 增加 `elif model_type == "qwen3tts"` 分支（`tts_per_slide` 已把 `model_type` 作为参数，改动面很小）

### 2. 光标空间定位：UI-TARS-1.5-7B → GUI-Owl-1.5-4B-Instruct

这是**性价比最高的一处替换**。

**原方案问题**：`src/cursor_gen.py:44` 用 transformers `pipeline()` 直接加载 `ByteDance-Seed/UI-TARS-1.5-7B`。7B 的 bf16 权重本身就是 14–15 GB，加上视觉编码器和 KV cache，实际需要 16–18 GB——**你这张 16 GB 卡开箱就是 OOM**。而 ByteDance 后续的 UI-TARS-2 是 **23B 激活参数的 MoE**，更不可能本地跑。

**替代**：`mPLUG/GUI-Owl-1.5-4B-Instruct`（阿里通义实验室 X-PLUG / MobileAgent 团队）

一手核验（HF API 实测）：

```
license = mit              ← 比 Apache-2.0 还宽松
params  = 4.44B
downloads = 933
同系列还有：GUI-Owl-1.5-2B-Instruct（2.13B, MIT）
            GUI-Owl-1.5-8B-Instruct / 8B-Think / 32B-Instruct / 32B-Think
GGUF 量化：mradermacher/GUI-Owl-1.5-2B-Instruct-GGUF 等（社区已提供）
```

**为什么它是最优解——三个"恰好对上"**：

1. **架构与坐标系同源，但输出协议不同**。GUI-Owl 1.5 系列**基于 Qwen3-VL 构建**，输出 **0-1000 归一化坐标**（`MobileAgent-v3.5/README.md` 两处明确写 "GUI-Owl 1.5 outputs relative coordinates (0–1000) by default"），与原代码 `parse_action_to_structure_output(..., factor=1000, model_type="qwen25vl")` 的坐标约定一致。
2. **体量刚好**。4.44B bf16 ≈ 9–10 GB，在 16 GB 卡上留出约 6 GB 余量；若还要给显存瘦身，8B/2B 都有现成 GGUF。
3. **专才胜过通才**。它是**为 GUI grounding 专门后训练**的模型（统一了感知、定位、规划、动作），在 20+ 个 GUI 基准上取得开源 SOTA。这种任务上，专用 4B 通常优于通用 7B。

> ⚠️ **一处实测修正（原判断有误）**：早先版本认为"解析逻辑同源、近乎零改造"，**这是错的**。
> 查 `MobileAgent-v3.5/grounding_and_kb/eval_grounding_benchmarks.py` 后发现，GUI-Owl 的 grounding 走的是**工具调用协议**，不是 qwen-vl-utils 那套 `<|box_start|>(x,y)<|box_end|>`：
>
> - **system 消息**里必须声明一个 `computer_use` 工具，其中含关键一句 `* The screen's resolution is 1000x1000.` —— 模型正是靠这句建立坐标系约定；
> - **user 消息**是「图片 + 原始指令文本」，无需任何自创的格式说明；
> - **输出**形如 `<tool_call>{"name":"computer_use","arguments":{"action":"left_click","coordinate":[x,y]}}</tool_call>`；
> - 官方解析顺序：先 `\((\d+),\s*(\d+)\)`，再 `\[(\d+), (\d+)\]`，取**最后一个**匹配。
>
> 因此 `cursor_gen.py` 里的 grounding 辅助函数是**重写**，不能复刻原解析。自创提示词（例如"请输出 `<point>x y</point>`"）格式不在训练分布内，属必然失败。

**代码改动点**：`src/cursor_gen.py`
- 模型 ID 换成 `mPLUG/GUI-Owl-1.5-4B-Instruct`，用 `Qwen3VLForConditionalGeneration` + `AutoProcessor` 加载（需 transformers ≥ 4.57）
- **新增** `build_grounding_prompt()`：原样照搬官方的工具调用 system 提示
- **重写** `parse_point()` / 新增 `parse_tool_call_point()`：优先解析 `<tool_call>` 内 JSON，再回退官方两条正则
- `infer_cursor()` 的消息结构改为 system + user 两条，且不再把自创说明拼进 prompt
- 官方 ``Quick Start`` 里的 `torch_dtype="auto"` 在 16 GB 卡上会按 fp32 载入，**必须显式指定 `torch_dtype=torch.bfloat16`**

**顺带必须修的性能坑**：`infer_cursor()` 里的 `pipe = pipeline(...)` 写在**函数内部**，而该函数被 `multiprocessing.Pool` 反复调用——**每句字幕都会重新加载一遍 4.4B 模型**。20 页 × 约 3 句 = 60 次重载，这会成为整个 pipeline 最慢的环节。应改为模块级惰性单例。

**方案 B（零本地部署）**：既然 DeepSeek-V4.1-Flash 原生支持图像输入，完全可以把"幻灯片图片 + 指令"直接发给它、要求返回归一化坐标，**从而砍掉这个 9 GB 的本地模型**。代价是通用 VLM 的细粒度定位精度通常低于专用 grounding 模型。**建议先用 50 条抽样做 A/B，再决定是否保留本地模型**。

### 3. 转写与时间对齐：WhisperX → Qwen3-ASR-0.6B + Qwen3-ForcedAligner-0.6B

**原方案问题**：WhisperX 承担三件事——参考音频转写、词级时间戳（决定光标何时指向何处）、生成视频的字幕回抽比对。它是"能跑但精度不够好"的典型：中文场景下 Whisper-large-v3 平均 CER 9.86%、会议场景 18.87%，与国产专项模型差 5–6 个百分点；对齐精度上也被新方案超越。

**替代**：`Qwen/Qwen3-ASR-0.6B` + `Qwen/Qwen3-ForcedAligner-0.6B`（阿里通义，2026-01 发布）

一手核验（HF API 实测）：

```
Qwen/Qwen3-ASR-0.6B            license=apache-2.0  params=0.94B  downloads=627,789
Qwen/Qwen3-ASR-1.7B            license=apache-2.0               downloads=2,656,067
Qwen/Qwen3-ForcedAligner-0.6B  license=apache-2.0  params=0.92B  downloads=529,614
```

- **为什么拆成两个模型**：Qwen3-ASR 负责转写（30 种语言 + 22 种中文方言/口音），`Qwen3-ForcedAligner` 专门负责**时间戳对齐**——它把 force alignment 重构成 slot-filling 问题，在转写文本的每个词后插入 `[time]` 槽位，一次性并行输出离散时间索引，**完全非自回归（NAR），RTF 约 0.001**。
- **精度**：人工标注集上累计平均偏移 **27.8 ms**，**比 WhisperX 好 67–77%**。这直接决定光标跟随字幕的贴合度。
- **显存**：两个模型各约 2 GB，可串行加载；总占用低于原 WhisperX 方案。
- **为什么优先它而不是 FunASR**：FunASR（SenseVoice 234M / Paraformer 220M）确实更轻、生态更全（VAD/标点/说话人分离一条龙），但官方明确说明 ⚠️ **Fun-ASR-Nano 的 checkpoint 不提供可靠的原生字级时间戳，要做逐字对齐必须改用 Paraformer**；而 Paraformer 以中文为主。本项目论文演示是**英文学术报告**，`Qwen3-ASR`（30 语言）更稳妥。此外 FunASR 内嵌 ModelScope SDK，**离线环境启动时会尝试连 modelscope.cn 校验而卡住**。

**备选**：`FunAudioLLM/SenseVoiceSmall`（0.234B，多语言 + 情感 + 音频事件，GPU 约 170× 实时、CPU 约 17×，q8 后仅 250 MB）——**若确定只做中文**，它是更轻的选择。

**代码改动点**：
- `src/speech_gen.py:6`（`import whisperx`）、`:11-16`（`transcribe_with_whisperx`）
- `src/speech_gen.py:53`：`if ref_text is None: ref_text = transcribe_with_whisperx(ref_audio)` → 换成 Qwen3-ASR；**同时把模型加载提到循环外**（原实现在逐页循环内被调用，会反复重载）
- `src/cursor_gen.py:159`（`whisperx.load_model("large-v3")`）→ Qwen3-ASR + ForcedAligner
- `src/evaluation/MetaSim_content.py:71` → 同上

### 4. 数字人：Hallo2 → InfiniteTalk

这是**整条链路上唯一的"卡死项"**，也是替换收益最大的地方。

**原方案问题**：Hallo2 由 SD 1.5 UNet + AnimateDiff + wav2vec2 + sd-vae + RealESRGAN + CodeFormer + insightface/mediapipe + MDX-Net 组成，权重合计约 15 GB，推理需 12–16 GB 且要独占。真正的障碍不在显存：
- 官方锁定 **torch 2.2.2 + CUDA 11.8**，只测过 Ubuntu 20.04/22.04
- RTX 5070 Ti 是 Blackwell **sm_120**，**cu118 的 torch 2.2.2 不含 sm_120 编译目标** → 装上直接报算力不支持
- 必须升到 torch 2.7+/cu128，再逐个去救 `basicsr`、`xformers`、`insightface` 等原生依赖
- 论文自己也承认这是瓶颈："generating only a few minutes of talking-head video typically takes several hours"

**替代**：`MeiGen-AI/InfiniteTalk`（美团基础研发平台视觉智能团队）

一手核验（HF API 实测）：

```
license = apache-2.0      downloads = 36,090
底层：Wan-AI/Wan2.1-I2V-14B-480P + TencentGameMate/chinese-wav2vec2-base
```

**为什么它同时解掉了显存和架构两个死结**：

| 维度 | Hallo2 | InfiniteTalk |
|---|---|---|
| 最低显存 | 12–16 GB 且独占 | **8 GB**（Q4 量化 + 360p/480p） |
| CUDA | **锁定 11.8** → sm_120 不支持 | **官方建议 ≥ 12.8** → 与 cu128 一致 |
| 时长 | 长视频易崩（官方 open-source plan 里的痛点） | **不限时长**，靠 soft conditioning 动态决定控制强度 |
| 驱动范围 | 仅嘴唇 | 嘴唇 + 头部 + 身体姿态 + 表情（稀疏帧配音路线） |
| 许可证 | 需查 | Apache-2.0，可商用 |

- **8 GB 档位配置**（社区实测）：分辨率 360p/480p、Q4 量化、音频 CFG 3–5；开启 FusionX LoRA 后采样步数从 30–40 降到 4–8（注意：**超过 1 分钟的长视频开 LoRA 会有轻微色偏**，长视频建议关）。
- **磁盘**：模型文件较大，建议预留 40 GB 以上 → 放 F 盘（余 1897 GB）。
- **同源优势**：它与第 6 项的 Wan2.2-S2V、以及 OmniAvatar **同属 Wan 视频模型家族**，可以共用一套 diffusers/torch 环境，不再需要 Hallo2 那套独立环境。

**备选**：

| 模型 | 许可证 | 显存 | 说明 |
|---|---|---|---|
| `OmniAvatar/OmniAvatar-1.3B` | （model card 未标） | 资料建议 4090 24 GB | 浙大 + 阿里夸克；1.3B 是 Wan 系里最轻的音频驱动方案，但**许可证字段缺失，商用前必须确认** |
| `Wan-AI/Wan2.2-S2V-14B` | Apache-2.0 | bf16 ~32 GB；GGUF Q4 可降 | 阿里官方、效果最强（16.3B）；本机需 `QuantStack/Wan2.2-S2V-14B-GGUF` 重度量化，速度会很慢 |
| `ByteDance/LatentSync-1.6` | openrail++ | 较低 | **只做口型同步**，不产动作。适合"已有视频只改嘴型"的场景，可作补充环节 |
| `tencent/HunyuanVideo-Avatar` | 腾讯社区协议（**非商业**） | 24 GB 官方 / 10 GB 优化后 | 效果好，但许可证不适合商用交付 |

**代码改动点**：`src/talking_gen.py` —— 目前是 `sys.path.insert(0, "hallo2")` 复用官方 `inference_long.py` + `long.yaml`，需要改成调用 InfiniteTalk 的推理入口。改动较大，但**不属于"改代码换模型"，而是"换掉整个子模块"**。

### 5. 音色相似度：SpeechBrain ECAPA → CAM++（3D-Speaker）

**原方案问题**：`src/evaluation/MetaSim_audio.py:26` 用 `speechbrain/spkrec-ecapa-voxceleb` 提取说话人嵌入、算余弦相似度。能跑，但 ECAPA-TDNN 是 2020–2022 年的架构。

**替代**：**CAM++**（阿里达摩院 3D-Speaker，ModelScope `iic/speech_campplus_sv_zh-cn_16k-common`）

- **依据**：CAM++ 基于密集连接时延神经网络，在公开的 **CN-Celeb 与 VoxCeleb** 上测试，"相比主流的 ResNet34 和 ECAPA-TDNN，**不仅获得了更高的准确率，还具备了更快的推理速度**"。论文的 Speech Similarity 指标是拿生成语音与真人录音比，**英文数据集 VoxCeleb 也在其验证范围内**，迁移无风险。
- **体量**：模型仅数十 MB，显存 < 1 GB，CPU 亦可。</br>
- **备选**：`iic/speech_eres2netv2_sv_zh-cn_16k-common`（ERes2NetV2，分组向量化注意力，精度更高一档）；`WeSpeaker` 的 ResNet34 英文模型。

**代码改动点**：`src/evaluation/MetaSim_audio.py:26` —— 从 `EncoderClassifier.from_hparams(...)` 换成 ModelScope `pipeline(task='speaker-verification', ...)`，取 `result['embs'][0]`。注意会新增 `modelscope` 依赖。

### 3.3 关键：换成 DeepSeek 几乎不需要改代码

`src/wei_utils.py` 的 `get_agent_config()` 末尾有一个**兜底分支**：

```python
else:
    agent_config = {
        'model_type': model_type,
        'model_platform': ModelPlatformType.OPENAI_COMPATIBLE_MODEL,
        'model_config': None
    }
```

也就是说，**任何不在白名单里的模型名，都会被当成 OpenAI 兼容模型处理**。而 DeepSeek 提供 OpenAI 兼容接口。因此：

```bash
# 环境变量（替代散落在 5 个文件里的硬编码空字符串）
export OPENAI_API_BASE="https://api.deepseek.com/v1"
export OPENAI_API_KEY="sk-..."

# 直接传模型名即可，无需新增白名单分支
python pipeline_light.py --model_name_t deepseek-flash --model_name_v deepseek-flash \
                         --if_tree_search True --stage '["0"]'
```

> 具体 base URL 与 camel 对 `OPENAI_COMPATIBLE_MODEL` 读取的环境变量名，请以 DeepSeek 开放平台文档与 `camel` 版本为准（建议落地时先跑一次最小连通性测试）。

### 3.4 为什么 AI 观众必须换人

DeepSeek-V4.1-Flash 的输入模态是 **text + image，不含视频**。而论文里那个"VideoLLM 代理观众"要看的是**生成出来的完整视频**——这是纯图像模型无法覆盖的。

**推荐 `Qwen3.5-Omni-Plus`**（阿里百炼）：Qwen3.5-Omni 在 **215 项音视频基准上取得 SOTA**，音视频综合得分超过 Gemini 3.1 Pro；支持 **256K 上下文（约 400 秒 720P 视频 @1FPS）**、**10 小时以上长音频**，且原生音视频联合分析（不是"抽帧当图片"）。

**低成本降级方案**：如果不想再引入一家供应商，可以用 `ffmpeg` 抽帧（如 1 fps）+ `deepseek-flash` 逐帧看。代价是丢失音频/时序信息，而"演讲视频的观众体验"恰恰高度依赖时序。**建议只在成本敏感时使用，评测指标会失真。**

### 3.5 顺带修掉的两个 bug

1. **`models/gemini-2.5-pro-flash` 不是合法模型 ID**（Google 只有 `gemini-2.5-pro` 或 `gemini-2.5-flash`），照抄必然失败。换成 `deepseek-flash` 后此问题自动消失。
2. **API Key 硬编码为空字符串**，散落在 `pipeline.py`、`pipeline_light.py`、`evaluation/MetaSim_content.py`、`evaluation/PresentArena.py`、`evaluation/IPMemory/ip_qa.py` 等至少 5 处（形如 `os.environ["GEMINI_API_KEY"] = ""`、`genai.configure(api_key="")`）。应统一收敛到 `.env` + `python-dotenv`，并加进 `.gitignore`。

> ⚠️ **必须改的一件事**：`pipeline.py` 用 `multiprocessing.Pool(processes=num_gpus)`，**每个 worker 会各自加载一份完整模型**。单卡上如果让 worker 常驻持有 TTS + ASR + GUI-Owl + InfiniteTalk 四套权重，显存需求是**相加**（约 24 GB+）而不是取最大。**必须改为按阶段加载/卸载，或按阶段拆成独立进程串行执行**，才能让峰值落在 10 GB。
>
> 另一个已验证的采集事实：你机器上 NVIDIA 驱动**平时就占着约 6.8 GB 显存**（可用约 9.5 GB）。跑大模型前要先清出显存，否则 10 GB 峰值会撞上 9.5 GB 可用。

## 六、成本估算

假设一篇论文产出约 20 页幻灯片，各环节调用量如下（**均为量级估算，非实测**）：

| 环节 | 输入 token | 输出 token | 说明 |
|---|---|---|---|
| 幻灯片代码生成（含树搜索 4 路候选） | ~600K | ~30K | 整篇 LaTeX 重复进上下文，**大量命中缓存** |
| 字幕 + 光标提示 | ~80K | ~30K | 含 20 张 400dpi 幻灯片图 |
| 评测（PresentArena 成对比较为大头） | ~800K | ~120K | 20 页 × 6 组合 × 2 顺序 |
| **合计** | **≈1.5M** | **≈180K** | |

按闲时牌价计算：`1.5M × $0.15/1M = $0.225`（若多数命中缓存则降至约 `$0.005`），输出 `180K × $0.60/1M = $0.108`。

> **结论：一篇论文全流程约 $0.1–0.4（闲时）／$0.2–0.8（忙时）**，即不到 1 美元。
> 同等调用量按公开牌价粗略对比，GPT-4.1 约贵 13 倍、Gemini-2.5-Pro 约贵 10 倍。**成本上基本可以忽略，真正的瓶颈是本地生成时间（数字人）。**
>
> **省钱的免费动作**：把批量任务排到**北京时间 09:00–12:00 与 14:00–18:00 之外**，或周末跑——全部单价直接减半。

## 十、落地期间的实测修正记录（2026-09-17）

以下结论来自 Phase 1 实际动手时的验证，**推翻了本方案最初的几条推断**，以此处为准。

### 1. `deepseek-flash` 的 API 行为（实测）

```
GET  /v1/models          → 200，返回 ["deepseek-flash", "deepseek-v4-pro"]
POST /v1/chat/completions → 图像输入正常，识别准确
```

关键特性 —— **它是推理模型**，响应里有两个字段：

| 字段 | 内容 |
|---|---|
| `message.reasoning_content` | 思考过程（推理 token，计费） |
| `message.content` | **最终答案（要读这个）** |

⚠️ 踩到的坑：首次测试给 `max_tokens=80`，结果 `completion_tokens=80` 且 `reasoning_tokens=80`，**`content` 是空字符串，HTTP 200 不报错**。这不是错误而是静默失败 —— 排查时极易误判为"模型不支持图像"。

> 正确做法：全流程 `max_tokens ≥ 2048`；只读 `content`；`finish_reason == "length"` 即说明预算被思考吃光了。
> 同一次请求改 `max_tokens=1200` 后返回 `'3种颜色；中间。'`（测试图为左红右蓝、中间白色方块），耗时 1.4 s。

### 2. `qwen-tts` × `qwen-asr` 的 transformers 死结（实测）

逐版本查 PyPI metadata 后确认 —— **不存在可对齐的组合**：

| 包 | 全部版本范围 | 对 transformers 的约束 |
|---|---|---|
| `qwen-tts` | 0.0.2 ~ 0.1.1（共 6 版） | 全系 `==4.57.3` |
| `qwen-asr` | 0.0.1 ~ 0.0.6（共 6 版） | 全系 `==4.57.6` |

而 PyPI 上 transformers 最新为 5.x。原脚本写 `transformers>=4.57` 会被解析到 5.x，**两个推理包同时失效**。

**处置**：钉 `4.57.6`（较新的一侧），`qwen-tts` 用 `--no-deps` 安装并手动补齐其自身依赖（librosa / soundfile / torchaudio / accelerate）。
**依据**：`qwen-asr` 发布时（1/30）特意钉 4.57.6，说明它**需要**该版本的修复；`qwen-tts` 晚了 7 天（2/6）却仍钉 4.57.3，更像模板复制留下的陈旧 pin。且只在 patch 段内跨越（.3→.6），语义化版本下不引入破坏性变更。
**兜底**：`install_deps.py --smoke` 会跑一次真实 `generate_voice_clone` —— 版本推断只到概率层面，跑通才算数。

### 3. 另外三处需要落到代码里的细节

- **`Qwen3-TTS-12Hz-1.7B-Base` 自带 `speech_tokenizer/`**（682 MB），**无需**单独下载 `Qwen3-TTS-Tokenizer-12Hz`。
- **`create_voice_clone_prompt()` 可复用**：参考音频只需编码一次，跨页复用，避免逐页重复编码。
- **不要装 flash-attn**：官方推荐但它需要编译，Windows 上极难成功；`sdpa` 精度无损失，小模型上速度差异可忽略。
- **官方 Quick Start 用 `torch_dtype="auto"`**：在 16 GB 卡上可能解析成 fp32 而直接 OOM，**必须显式传 `torch_dtype=torch.bfloat16`**。
- **对齐结果的层级**：`model.align()` 返回按音频分组的列表，单条音频取 `results[0]`（词条序列）。判断层级时**不要用 `isinstance(x, list)`**（模型侧若返回 tuple 就判错），改为检查元素是否具备 `start_time` 属性。

## 十一、Phase 2 / Phase 3 决策与本机路线修正（2026-09-17 续）

### 11.1 Phase 2 取消：本地小模型直接定稿

**决策（用户）**：不做「GUI-Owl 本地 vs DeepSeek API 出坐标」的 50 条 A/B，直接用本地专用小模型。

**依据**：
1. **导师明确要求尽可能使用本地模型** —— 这比「精度/成本哪个更优」优先级更高；
2. 后续会在**更高性能的学校算力服务器（8×A6000）**上运行，本机只作为开发与验收环境。

**验收标准据此调整**为：**保证本机能够有效运行**即可，不追求本机达到最终性能。
并额外要求：**预留移植到高性能服务器的接口（只做抽象，不做具体实现）**。

### 11.2 数字人路线修正：WSL2 走不通，改 Windows 原生

原方案建议「数字人放 WSL2（Windows 原生成功率低，路径还不能含中文）」。实测**该路线在本机不可行**：

```
wsl.exe 被本机安全策略列入程序黑名单
→ 提示明确写明「不可批准、不可绕过」，且禁止通过其他 shell 或脚本间接调用
→ 本会话内任何 WSL2 方案都执行不了
```

因此数字人**只能走 Windows 原生**。侦察后确认这条路可行，三个关键事实：

| 疑点 | 实测结论 |
|---|---|
| `flash-attn` 是硬依赖吗？ | **不是**。`wan/modules/attention.py` 用 `try/except` 包住两个 flash-attn 导入，缺失时退化到 `torch.nn.functional.scaled_dot_product_attention`（第 184 行）。Windows 上的头号拦路虎被排除 |
| `xformers` 能装吗？（运行时真的在用，见 attention.py 263/266/380 行） | **能**。`xformers 0.0.35` 有官方 **win_amd64 wheel**，且只要求 `torch>=2.10`（下界，非死钉） |
| `xfuser` 能装吗？（attention.py 顶层硬导入） | **能**。`xfuser 0.6.0` 是纯 Python 包（`py3-none-any`） |

另外确认 `generate_infinitetalk.py` 对单卡是友好的：`world_size` 缺省为 1，`init_process_group`
有 `world_size > 1` 守卫，`dist.is_initialized()` 有判断；非分布式下它还会**断言**
`t5_fsdp`/`dit_fsdp` 为假、`ulysses/ring ≤ 1` —— 这正好约束了单卡档位的参数组合。

### 11.3 环境三个必须做对的地方

1. **Python 必须 3.12，不能 3.13**。InfiniteTalk 钉 `numpy>=1.23.5,<2`，而 **numpy 1.x 没有 cp313 的
   wheel**，pip 会退化成源码编译并在 metadata 阶段直接崩（实测 `metadata-generation-failed`，
   报 Meson bug）。Python 3.12 有 numpy 1.26.4 的 wheel。
2. **torch 必须从 pytorch 官方 cu128 源装**。PyPI 上 Windows 的 `torch` 是 **CPU-only**；
   且 Blackwell(sm_120) 只有 cu128 及以后才有编译目标。锁 `torch==2.11.0`（与主环境一致，已实测可用）。
3. **`transformers` 要钉 4.x**。需求写的是 `>=4.49.0`，直接解析会拿到 5.17.0；
   本项目已在主链路上实测 5.x 会破坏 qwen 生态，故钉 `4.57.6`。
   （InfiniteTalk 实际只用到 `Wav2Vec2FeatureExtractor`、`Wav2Vec2Model/Config`、
   `AutoTokenizer`、`AlbertModel` 等稳定符号，4.x 完全够用。）

### 11.4 下载量优化：76.6 GB → 29.7 GB

原估算「底模 33 GB + adapter 12 GB」已过时（HF API 实测底模全仓库 **76.6 GB**、InfiniteTalk **157 GB**）。
依据 `wan/multitalk.py` 的两条互斥分支，**16 GB 卡必然走量化那条**：

```python
if quant is not None:                       # ← fp8 走这里
    model_state_dict = load_file(quant_dir)     # 单文件 = 已合并 adapter 的量化 DiT
else:
    if dit_path is None:
        weight_files = [7 个 diffusion_pytorch_model-*.safetensors,   # 62.5 GB
                        f"{infinitetalk_dir}"]                        # 9.5 GB
```

也就是说量化分支**根本不加载那 7 个 bf16 分片，也不用 `infinitetalk_dir`**
（后者只在 else 分支第 219 行被引用）；底模真正要读的只有 `config.json`（第 197 行）、
VAE、CLIP 与两个 tokenizer；T5 权重由 `quant_models/t5_fp8.safetensors` 顶替
（`t5.py` 第 506-508 行按 `<quant_dir>/t5_{quant}.safetensors` 去找）。

| 仓库 | 只取 | 体积 |
|---|---|---|
| Wan-AI/Wan2.1-I2V-14B-480P | config.json、Wan2.1_VAE.pth、CLIP、xlm-roberta-large/、google/umt5-xxl/ | 4.96 GB |
| MeiGen-AI/InfiniteTalk | quant_models/{infinitetalk_single_fp8,t5_fp8,t5_map_fp8} | 24.43 GB |
| TencentGameMate/chinese-wav2vec2-base | pytorch_model.bin + 两个 config | 0.35 GB |
| **合计** | | **29.74 GB** |

### 11.5 中文路径隔离

InfiniteTalk 明确要求纯英文路径（其依赖的 cv2 / ffmpeg / C 扩展在窄字符 API 上读不到中文路径），
而本项目路径是 `E:\Development\26年\...`。**不把中文路径喂给它**，而是：

```
参考图/音频 → 复制到 ASCII 工作区(E:\ai-models\tmp\talking\<idx>)
          → 在纯英文环境里生成
```

顺带在这一步把参考图**居中裁成正方形**：InfiniteTalk 要求正方形人像，而项目自带的
`zeyu.png` 实测是 **658×660**（差 2 像素）。与其指望使用者每次先裁好，不如代码保证。

### 11.6 移植接口：运行档位层（`talking_config.py`）

把「本机 16 GB 单卡」与「8×A6000 服务器」的差异**全部收敛成 profile**，
本层只做「profile → 命令行参数」的翻译。**迁移时只改档位名，不改代码。**

> 不显式传时它会被代码按 `world_size` 自动改写（第 460-461 行）。
