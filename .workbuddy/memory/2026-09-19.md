## 数字人产物"能不能复用"的判定规则（2026-09-19 查证）

使用者问「手动上传相同素材，会直接复用数字人产物吗」。查代码后结论：**不会**。

复用判据只有一条 —— **产物路径是否存在**，而它由两个变量决定：

- 落点：`<result_dir>/talking_<backend>/<音频序号>/<参考图主文件名>/merge_video.mp4`
  （`pipeline.py:338` 拼 `talking_save_dir`，`talking_gen._target_paths()` 拼余下部分）
- 跳过条件：`merge_video.mp4` 已存在（`talking_gen.py:283` 与 `:715` 两处同判据）

`result_dir` 是**每任务一份** ⇒ 手动上传 = 新任务 = 新的空目录 ⇒ **一页都不会跳过**。
中间 workspace 也没给复用留口子：`avatar_id = "pv_<YYYYmmdd_HHMMSS>_<gpu>"`，
注释写明「必须每次运行唯一」——否则上游在 avatar 目录已存在且 `preparation=True` 时
会走进 `input()` 阻塞分支。

⚠️ 容易误读的一处：`_file_sha1()` 只用于**在一次运行内**把同一张参考图的多页归成一组
（共用一个 avatar / latents），**不做跨运行去重**，别把它当成"内容哈希去重"。

只有**续跑（rerun）**会复用：它把 `config.result_dir` 指向原任务目录，
于是新任务与原任务共用同一份产物。

顺带补一个重建记录的遗漏：重建受损任务的 `job.json` 时只从进程命令行取参数，
而 `source_path` **不在 argv 里**（它是 `_prepare_latex` 单独读的字段），
漏了会让续跑在"需要结构化"那步被拒。已补上，并把两份同内容 PDF 用 sha1 核对过。

## ⚠️ 数字人跳过判据**不含音频**（2026-09-19 发现，未修）

顺着"要不要加复用某任务产物入口"这个问题查出来的真缺陷。

`talking_gen._target_paths(save_dir, idx, ref_img_path)` 的跳过键只有
**（页号, 参考图主文件名）** —— **音频完全不参与**。而合片
`merge_slides_and_talking()` 的签名里**根本没有音频参数**，音轨取自数字人视频
自带的那条（进函数前还有 `_has_audio_stream(talking_path)` 校验）⇒ 被跳过的那一页
会**连同旧配音一起进成片**，本次新生成的 TTS 音频被静默丢弃；
页展示时长也跟数字人视频走 ⇒ 字幕与声音整体错位。**全程不报错。**

触发条件（两个都已存在）：
1. 续跑时显式 `reuse_script: False`；
2. 讲稿文件丢失时 —— `if args.reuse_script and path.isfile(...)` 不成立就重新生成讲稿，
   哪怕请求里写了 `reuse_script=True` 也照样重生成 ⇒ 音频变、页数不变 ⇒ 静默沿用旧配音。

候选修法：
- **A（治本，推荐）**：跳过判据纳入音频指纹 —— 每页目录落一份 `.inputs.json`
  （参考图 + 音频的 sha1 / size），跳过前比对。
- **B（最小）**：把"允许跳过"与"本次不会重生成音频"绑定。
- **C（长期）**：产物目录按输入指纹寻址（内容寻址缓存），顺带解决多人共享与覆盖。

## 内容寻址 / 去重（2026-09-19，待决策未实施）

使用者提出按指纹寻址 + 顺带避免服务端重复保存。**实测证实重复存在**：
同一份 PDF 存了 3 份（`86ea0bb70e0b`）、同一张人像 2 份（`f6edd2a0e351`）、
`paper_text.md` 也各 3 份，**重复占用 3.8 MB**。根因：三个上传端点都用
`uuid4().hex[:8]` 命名（`app.py:1095/1151/1276`）；
而 `jobs/_voices/` 早就是内容寻址（`sha1[:16]`，`app.py:1306`）。

**但收益要排序**（免得把最不重要那条当主理由）：
① 省 API 费用（最大）—— 同一篇论文重进时 `main.tex` 可复用（实测 10482 token），
再往前幻灯片+讲稿（讲稿占一篇 token 的 **76%**）也可复用；
② 防静默错配（大）—— 指纹天然解掉「跳过判据不含音频」那个缺陷；
③ 省磁盘（最小）—— 输入侧只有 3.8 MB，而单任务 `result/` 就 15.7 MB（且是残缺任务）。

**三条必须先一起处理**：隐私边界（内容寻址天然跨用户共享 ⇒ 输入库按用户分桶、
产物指纹必须含全部影响输出的输入，少一个字段就跨出隐私边界）、
引用计数（否则按任务删除会误删他人还在用的文件 —— 与本次误删事故同类）、
不可变性（只对**原始上传文件**取哈希，缓存键要带处理版本号，否则换了预处理仍命中旧缓存）。

分三阶段：① 输入按内容命名（`sha1[:12]` + 按用户分桶，立刻得到 main.tex 复用）；
② 页目录落 `.inputs.json` 接进跳过判据；③ 产物按完整指纹寻址（此时才需要 GC）。
**待使用者决定输入去重范围**（仅同一用户 / 允许服务器级共享库）。

## 阶段 3：产物缓存（按输入指纹寻址）已实施（2026-09-19）

新增 `scripts/artifact_cache.py`。整条链路**只有两步联网付费**（stage 0 结构化、
stage 2 讲稿——讲稿占一篇 token 的 76%），把这两步的产物按指纹缓存：

    jobs/_cache/struct/<指纹>/main.tex          正文+论文类型+LLM → LaTeX 工程
    jobs/_cache/deck/<指纹>/slide_imgs/ ...     上述 main.tex+两种语言+两个模型
                                subtitle_w_cursor.txt  +数字人档位 → 幻灯片+讲稿

命中后：复制幻灯片/讲稿进本次产物目录，`stages` 收敛成 ["2","3"] + `reuse_script=True`
（stage 1 不再生成幻灯片、stage 2 不再调 VLM），其余本地 GPU 阶段照跑。
只要 stage 1 而幻灯片已命中时，连流水线进程都不起。

### 关键设计：**两类缓存各有一份写死的字段表**

加字段前必须回答「它会改变产物吗」——两个方向都会出错：
少一个字段 → 输入不同却命中 → **静默产出错误内容**；
多一个字段 → 输入变了其实输出不变却重算 → **白花一次钱**。
所以 struct 不含语言/人像/音色，deck 也不含人像/音色（"换头像不废缓存"是**特性**）。

### 写这一版踩到的三个真问题（都值得记住）

1. **写入键 ≠ 查询键 ⇒ 缓存永远命中不了，而且不报错。**
   最初 publish 时重算指纹，而流水线可能改写 `main.tex`（指纹的输入之一）。
   修法：**键只算一次**，`lookup_*`/`publish_*` 都收 `key=`，由调用方一路带下去。
   → 通用判据：**凡"算出来的东西既用于查询又用于写入"，就必须算一次传下去**；
     算两次就一定会漂移，且漂移的方向是"静默失效"。
2. **输入取不到指纹时会「塌成同一个键」**（测试暴露的）。
   两个输入完全不同、但都取不到指纹的任务，字段都是 None → 指纹相同 →
   后跑的直接拿到前一个的产物。修法：`REQUIRED_FIELDS` 规定"输入必须可辨认"，
   缺了就**既不命中也不写入** —— 退化成不用缓存（多花一次钱），换"绝不拿错产物"。
3. **命中改动的 config/argv 没落盘。** `_run_job` 就地改了 `config.stages`/
   `reuse_script` 并重建 argv，但收尾只写 exit_code/elapsed_min/cache →
   任务记录里还是"请求时的样子"，事后没人能解释"为什么这次没跑 stage 1"。

### 只增不删

模块里**没有任何删除实现**（有静态断言守着）；`plan_gc()` 只读地列出"无人引用"的
候选（判据是任务记录里的 `cache.*_key`）。另有 `force_regenerate` 逃生门。
新增只读接口 `GET /api/cache`（清点 + 候选清单）。

### 测试

第 12 组 54 项，核心是**两阶段端到端**：假流水线跑一次（造出幻灯片与讲稿）→
断言缓存被回写；再用同样配置跑第二次 → 断言 deck_hit、config.stages==["2","3"]、
reuse_script=True、**真实 _build_argv** 过一遍确认落到命令行、幻灯片被复制进产物目录、
日志写明省了什么。外加反面对照（换讲稿语言 → 不许命中）与顺序守卫
（命中检查必须在 `_prepare_latex` **之前**）。全量 **257 项全过**。

留在库里 → 下次跑本组"对照组"命中上次遗留 → **假失败**；

## 复核 `--if_tree_search`：文档里的解释过时了（2026-09-19）

使用者问「为什么写死 False、它是干什么的」。查完后：**结论对，但理由要改**。

### 它是做什么的

上游 README 叫 *tree search for slide layout refinement*，实现在
`slide_code_gen_select_improvement.improve_layout()`，是**幻灯片编译成功后的布局微调**：

1. 从编译反馈取 `warning: Overfull` 行 → 按行号映射回所在 frame → 只留含 `\includegraphics` 的页；
2. 每页生成 **4 个候选**（图片宽度 × 1 / 0.75 / 0.5 / 0.25），各编译、各渲染，拼成 **2×2 带 A/B/C/D 标签的对比图**；
3. 把对比图交给 **VLM 选一个** → 用选中那份替换该页 → 重排版重编译 → 写 `*_refined.tex` 并返回其 PDF。

即「**宽度 4、深度 1 的束搜索，VLM 当评估函数**」。

### 为什么"必须写死 False"这条现在不准确

- 早先记的理由是"默认值 True 会走 `latex_code_gen` → NameError"。实测事实是：
  上游 `pipeline.py` 的 `if/else` **else 分支**引用了**被注释掉的 import**
  `# from slide_code_gen import latex_code_gen`，而 `latex_code_gen` 在整个仓库
  **只出现在那一行注释里、从未定义** → 走那条分支必 NameError。
  **我们的 pipeline.py 已把 if/else 合并成单分支并透传开关**（`pipeline.py:245-251`）
  ⇒ **这个崩溃点已经不存在**。
- `symtable` 复核（比手写 AST 遍历可靠，能正确处理嵌套/闭包）：整个模块只有一处真未定义名
  `beamer_save_path`，在 `improve_per_slide` 里，而它的调用点（第 197 行）**是注释掉的**
  → 死代码，不在链路上。`improve_layout` 调用链干净。
- ⇒ 现在写死 False 的真实理由是**成本 + 未验证**：每张溢出页多 4 次编译 + 4 次渲染 +
  **1 次带图 VLM 调用**；关掉不影响出片（幻灯片照常生成，只是不做事后微调）。

**已更正三份文档 + MEMORY**（Web可视化方案 / 项目讲解 / 课堂演示PPT大纲）：
保留历史，写清"不是必然崩溃，而是收益未验证、成本确定"。

### 方法论留档

- 检查"未定义名字"要**用 `symtable` 而不是手写 AST 遍历**：后者会把嵌套函数/闭包自由变量
  误报成未定义（这次就误报了 `_to_rgb` / `img` / `repl_*` 一堆）。
- 判断"某个开关到底会不会崩"，**看调用链上有哪些名字、而不是看历史笔记** ——
  我自己的记录里这个 bug 的方向出现过两次相反结论（09-17 记 True、09-18 记 False），
  说明当时的排查并没有把方向钉死。


## `--if_tree_search` 做成界面开关（默认关）+ 指纹同步（2026-09-19）

使用者拍板："加上这个开关吧，这本就是论文的一大核心，默认关，指纹字段也同步更改"。
上一轮已核实它**不是"会崩"**（上游那条引用 `latex_code_gen` 的 else 分支已被我们合并），
理由是成本与未验证 —— 所以这次只是把它从"写死的常量"变回"可配置项"。

### 改了什么

- `_build_argv`：从 `cfg.get("if_tree_search")` 读，**默认 False**（与上游 argparse 的
  `default=True` 相反，所以必须显式传 `--if_tree_search False` 才能关）。
- `_artifact_facts` 加这个字段，并经 `_as_bool()` **归一成 bool**。
- `artifact_cache.DECK_FIELDS` 加 `if_tree_search`；`STRUCT_FIELDS` **不加**（它改的是
  幻灯片，不是 main.tex；加了就是白花钱）。
- `/api/options.toggles` 下发开关的文案/默认值/成本口径（删掉原先的 `hidden_flags`
  "这个开关不存在"声明）；前端只渲染、不硬编码，提交时随 `config.if_tree_search` 走。
- 开启时 run.log 写一行 `[toggle] 已开启…` —— 它是唯一会额外花钱的开关，
  事后没人能解释那次耗时的时候，这一行就是答案。

### 关键设计：`_as_bool` 归一化

`True` / `"True"` / `"true"` / `1` 在指纹里是**四个不同的值** ⇒ 行为完全一样却互相不命中，
症状是"缓存时灵时不灵"，比彻底不命中难查得多。前端传布尔、CLI 传字符串，两种都要接住。

### 缓存迁移（没有丢钱）

你 02:14 那次真实运行的 deck 缓存是按旧字段表算的键，加字段后旧键**再也命中不了**。
删掉它等于白扔一次 stage1+讲稿的钱，所以做了迁移：从 `job.json` 的 argv 确认它当时是
`--if_tree_search False`，据此算出新键并改名 + 重写 manifest（不是删）。
`struct` 字段表没变 ⇒ struct 缓存键不变、照常命中。

### 测试

- 第 12 组新增 16 项：deck 对 `if_tree_search` 敏感 / struct 不敏感、四种写法归一成同一个键、
  端点里第四例"开着开关跑一遍"（勾选 → config → 真实 argv `True` → 日志 `[toggle]`）、
  4 条静态守卫（字段表里有、struct 表里没有、从 config 读、默认 False）。
- **新增 A0 段：字段表 ↔ `_artifact_facts` 一一对应**。指纹有**两个地方**在写，
  各写一份就一定会漂移：加了上报却没进表 → 输入不同却命中；进了表却没人上报 → 恒为 None
  形同摆设。这条守卫把两种漂移一起挡住。
- 全量 **273 项通过**（原 257 + 16）。

### 顺带挖出并修掉一个"静默残留"机制

排查中一度以为测试在漏缓存条目，逐层跟踪（快照差集 → 建/删调用序列 → 手工删同一目录成功）
后确认：**删除被调用了，但 Windows 上偶发失败，`ignore_errors=True` 把它吞了**。
一晚上攒下 7 个 `smoke_cache_*` 目录 + 一批缓存条目，而危害是**延迟**出现的 ——
下一次跑同一组会命中上次遗留，断言"第一次跑必须未命中"失败（本文件里出现过两次同款假失败）。

修法：`main()` 末尾加 `_final_sweep()`，**必删、必报**，并把"按规矩保留（有任务引用）"
与"删不掉"**分开报**（混在一起会让人以为清扫失败）。删除判据只用证据：
`jobs/smoke_*`（测试独占命名空间）+ `manifest.from_job == "smoke"`；有任务引用的一律不碰。
首跑清掉 13 项历史残留，再跑显示"清掉 0 项"，说明套件自身已干净。
