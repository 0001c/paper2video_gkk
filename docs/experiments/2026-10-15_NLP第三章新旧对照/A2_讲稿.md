# A2 · 第三章12分钟目标讲稿

## 1. 从定义表达式到得到结果

我们先看一个真实困惑：当你在代码里写下 h = sigmoid(W·x + b)，屏幕上却没出现任何数字——为什么定义了表达式，还拿不到结果？


这是因为 TensorFlow 1.x 的图模式把‘描述计算’和‘执行计算’严格分开了。就像建筑师画好施工图，不等于房子已经盖好；图只是记录了运算依赖关系，它本身不会自动算出数值。


整个流程必须三步走：第一，定义依赖——用 Operation 节点搭建计算图；第二，提供数据——通过 feed_dict 给占位符赋值，或初始化变量；第三，执行求值——启动 Session，明确告诉系统‘我要取回 h 的值’。


注意，这里的关键不是‘写了什么公式’，而是‘谁在什么时候触发了计算’。比如 h 的表达式里包含 W 和 x，但 W 是变量、x 是占位符——它们的值在图构建阶段都未知，必须等到会话运行时才注入。


接下来我们会用一个极简例子 z = (a + b) × c 来手算全过程：先建图定义 a、b、c、d=a+b、z=d×c；再设 a=2, b=3, c=4；最后开 Session 求值 z。你会看到，只有第三步才真正产出 20 这个数字。

## 2. E1：计算图的两步运算

上一节我们写出了表达式 z = (a + b) * c，但它还只是符号——没有数值结果。为什么？因为 TensorFlow 1.x 的计算图分两步：先定义依赖关系，再执行求值。


看这个具体例子：教材符号是 d = a + b；z = d * c。


为便于手算验证，本实验统一补充教学设值：a = 2，b = 3，c = 4——注意，这是教学辅助值，非原书给定。


第一步：d = 2 + 3 = 5；第二步：z = 5 * 4 = 20。这个顺序不能颠倒，因为 z 依赖 d 的结果。


其中，‘加法’和‘乘法’是两个 Operation，它们各自执行一个操作；而 d 和 z 是这两个操作的输出，在 TensorFlow 中称为 Tensor。


关键区分：构图时，Tensor 是‘待求值的符号’；只有进入会话、提供输入数据后，它才变成具体数值。比如 z 在未运行前，不等于 20，只是一个指向乘法节点的引用。


易错点：学生常误以为‘写了 z = d * c 就等于 z = 20’。其实不然——就像写‘明天8点开会’不等于会议已开；没执行，就没有数值。


数值为教学补充；教材PDF第9–10页说明了这一流程，我们下一页将展开张量的秩、形状与名字等属性，它们在构图阶段就已确定。

## 3. 张量的秩、形状与名字

上一节我们用 z = (a + b) * c 的计算图，明确了‘构图’与‘执行’的分离：先建图记录依赖，再通过会话求值。


现在进入实操关键——当你看到一个张量标识如 add:2 或 matmul:0，必须立刻能回答三个问题：它有多少维？每维多长？存的是什么类型数据？


这三个问题的答案，就是张量的秩、shape 和 dtype。


注意：‘秩’不是线性代数里的矩阵秩，而是轴的数量。向量 [1,2,3] 沿单一方向延伸，只有1个轴, 所以秩是1；它的 shape 是 [3]，表示该轴含3个元素。


矩阵 [[1,2,3],[4,5,6]] 有行与列两个独立方向，秩为2；shape 写作 [2,3]，顺序对应行数、列数。


易错点：shape 不是元素总数。[2,3] 共6个元素，但秩仍是2——维度数不等于元素个数，这是初学者高频混淆处。


名字后缀如 add:2 表示操作节点 add 的第三个输出（索引从0开始）。同一个操作可能产出多个张量，调试时必须精确定位到具体输出项。


图中边分两类：数据边传递实际数值，控制边仅约束执行先后顺序——例如确保 d 计算完成后再算 z，但它本身不携带任何值。


请牢记：张量在构图阶段只是符号占位符；只有运行会话并提供输入，它才被赋予具体数值。下一节我们就聚焦会话如何精准触发所需计算。

## 4. 会话负责执行和资源管理

计算图已经构建完成——所有节点、边和张量的依赖关系都已记录，但此时图仍是静态的蓝图，不会自动产生任何数值结果。


真正执行计算的是会话（Session），它承担两项核心任务：一是按需触发运算路径，二是统一管理底层资源，包括内存、GPU显存与计算线程。


调用session.run(h)时，你明确请求h的值；系统会智能回溯h的所有前置依赖——比如x、W、b、矩阵乘、加法与sigmoid——仅执行这条必要路径，而非全图遍历。


必须警惕一个常见误解：创建会话绝不等于启动训练或自动求梯度。教材第13页曾表述‘启动Session会自动计算所有梯度’，这是不严谨的；梯度必须显式定义如tf.gradients(loss, [W,b])，再单独run它。


会话像租用一台计算工作站：申请时分配资源，使用完毕必须显式关闭（session.close()），否则资源持续占用，可能导致后续实验因显存耗尽而失败。


构图是声明式描述‘要做什么’，执行是命令式动作‘何时做、怎么做’；下一环节将看到，x是占位符，需feed_dict供值；W和b是变量，必须初始化后才能参与计算——这些操作均在会话内发生，但全赖你主动触发。

## 5. 占位符与变量：谁供值，谁初始化

我们已经构造好计算图，现在面临一个关键问题：图里的节点到底谁来提供数值？谁又需要提前准备？


x 是占位符（placeholder），它像一个空插槽——图构建时只声明‘这里将来要塞一个 [1,10] 的张量’，但不存任何数值；真正运行时，必须通过 feed_dict 显式传入数据，比如 np.random.rand(1,10)。


而 W 和 b 是变量（Variable），它们代表模型参数，生命周期贯穿整个会话。变量在图中被定义后，内存里还是一片未初始化的随机区域；必须显式执行初始化操作，才能填入合法数值。


这里有个经典误区：定义初始化器（如 tf.global_variables_initializer()）只是生成一个操作节点，并不执行它。就像写好‘开灯’指令 ≠ 灯真的亮了——你得调用 .run() 才真正触发初始化。


所以完整流程是四步：先初始化变量 → 再用 feed_dict 提供 x 的值 → 然后求值 h → 最后关闭会话释放资源。漏掉任何一步，都会报错或得到未定义结果。


注意：本例仅做单次前向求值，没有梯度计算，也没有训练循环。这意味着 W 和 b 虽然被初始化了，但仍是随机值，不会自动更新——会话从不替你做训练。

## 6. E2：沿教材代码核对形状

现在我们来严格核对教材代码中前向传播的张量形状——这是理解计算图执行逻辑的关键一步。


输入x定义为shape [1,10]，权重W是[10,5]，矩阵乘法要求左矩阵列数等于右矩阵行数，这里内维10匹配，结果必为[1,5]。


偏置b的shape是[5]，TensorFlow按最后一轴广播：它被自动扩展为[1,5]与结果对齐，加法后形状仍为[1,5]。注意，广播只作用于末轴，不是任意维度都能自由扩展。


sigmoid函数是逐元素非线性变换，它不改变张量结构——输入[1,5]，输出h仍是[1,5]。每个元素独立经过S形曲线，维度完全保留。


参数量可精确计算：W含10×5=50个标量，b含5个，共55个可训练参数。这个数字直接关联模型复杂度与梯度计算开销。


特别强调：x和W均为随机初始化，教材未给定具体数值，因此h的输出值不唯一。我们只能验证形状与运算流程，绝不能编造如‘h=[0.6,0.3,…]’这样的确定结果——这是常见误区。


最后确认代码顺序：教材PDF第14–16页明确使用tf.matmul(x,W)，即x乘W，而非W乘x。顺序颠倒会导致内维不匹配，运行时报错。矩阵乘法不可交换，构图必须严格忠实代码。

## 7. 从客户端到实际执行设备

我们已经构造出计算图，比如 h = sigmoid(W·x + b)，但图只是静态描述——它不会自己跑起来。真正驱动它的是执行系统，而这个系统由三个逻辑角色协同完成。


client 是发起者，它把定义好的图连同执行请求一起提交出去；就像你写好实验步骤，交给实验室调度系统。


master 负责全局协调：它接收请求后，分析依赖关系，把整张图拆解成子任务，并分配给执行单元；它不计算，只做调度决策。


worker 是实际执行者，它拿到分配的子图后，调用 CPU 或 GPU 运行运算；关键在于——它只执行当前请求所必需的依赖路径，绝不会无谓遍历全图。


这里必须澄清一个常见误解：在单机环境中，client、master、worker 这三个职责完全可以合并在同一个进程里，不需要三台物理机器；它们是逻辑分工，不是硬件绑定。


再强调一次：系统严格按需执行——Session.run 指定什么，就只算它的直接依赖。例如你只 fetch h，它就不会触发 W 的梯度计算，也不会初始化未被引用的变量。这正是‘定义≠执行’原则在运行时的具体体现。

## 8. 回顾：把一次求值完整串起来

现在我们把一次完整的前向求值串起来——不是只写代码，而是理解每一步在图模型中实际发生了什么。


首先，定义图与张量：你声明x是占位符、W和b是变量、h是sigmoid(Wx+b)的输出，这一步只是画出计算蓝图，没有任何数值被算出来。


接着初始化变量：W和b必须显式运行初始化操作；若跳过这步直接求h，TensorFlow会报错‘Attempting to use uninitialized value’，因为变量初始状态是未定义的。


然后提供输入：x作为占位符，必须通过feed_dict传入具体数值，比如一个[1,10]的随机矩阵；若漏掉feed_dict，系统会提示‘You must feed a value for placeholder tensor’。


进入执行阶段：调用Session.run(h)，系统自动追溯h的依赖——先算matmul(x,W)，再加b，最后sigmoid；它不会计算图中其他无关节点，只走最小依赖路径。


为什么x乘W得到[1,5]？因为x形状是[1,10]，W是[10,5]，矩阵乘法要求内维10匹配，结果外维为[1,5]；这是线性代数规则，不是TensorFlow特例。


注意：定义、执行、训练是三个独立阶段。本例只有定义与单次执行，没有优化器、没有梯度、没有循环——所以W和b仍是随机初值，没被训练过。


最后关闭会话释放资源；不关会话虽不报错，但长期运行会累积内存泄漏。整个流程像做一道菜：备料（定义）、开火（初始化+feed）、炒制（run）、关火（close）——缺一步，菜就做不成。


检查环节提醒我们：缺少feed_dict或初始化，程序会明确报错；而形状错误往往在定义阶段就触发异常，比如x[1,10]与W[5,10]相乘会因内维不匹配失败。
