> 起因：`--if_tree_search True` 第一次打开就撞上

> 顺着它扫出上游一整类"平台编码"地雷，才意识到需要一个**总账**：

## 先纠正一个长期误记：上游代码**在**本仓库 Git 里

早先的笔记写着「`Paper2Video-main/` 已在 `.gitignore` 中忽略，**不要修改、不要提交**」。
**这是错的**，已核实：

```
$ git ls-files Paper2Video-main/src/ | wc -l
172                       # src 下的文件全部被跟踪
$ git log --oneline -- Paper2Video-main/src/pipeline.py | wc -l
11                        # 上游文件本身就是被提交的
$ git check-ignore -v Paper2Video-main/src/pipeline.py
（无输出 = 未被忽略）
```

`.gitignore` 里与它相关的只有**构建产物**（`assets/*.mp4`、`**/slides.pdf`、
`**/*.aux|log|fls|fdb_latexmk|synctex.gz`）与 `__pycache__`。

⇒ **我们对上游的补丁随本仓库 Git 一起走，服务器上 `git clone` + 检出即可，
不需要手工重打。** 唯一**不在**这份 Git 里的是 **MuseTalk**（独立仓库，在
`E:\ai-models\MuseTalk`）—— 只有它需要「重装后重打」，见 `docs/MuseTalk补丁.md`。

> 这条纠正很重要：如果按旧笔记理解，要么以为补丁会丢（于是浪费时间重打），
> 要么不敢碰上游文件（于是把补丁散落到外面、反而真的会丢）。

## 平台编码这一类：为什么是"类"而不是"一处"

Windows 上 `open()` 不带 `encoding` 用 **ANSI(cp936)**，Linux 上是 UTF-8。
全仓库扫出 **92 处**文本 `open()` 没指定编码（其中 81 处在 `evaluation/` 那棵
论文评测子树里，我们的链路不使用）。

修法分两层，**两层都要**：

1. **逐处**：我们链路上的 11 处显式写 `encoding="utf-8"`（含 3 处写 `.tex`）。
   → 命令行直接跑 `pipeline.py` 也安全，不依赖环境变量。
2. **治本**：流水线子进程环境加 `PYTHONUTF8=1`（`web/app.py` 的 `_run_job`
   与 `scripts/gkk_3combos.py`）。一条覆盖上游全部 `open()`，
   并**让 Windows 开发机的行为对齐 Linux 服务器** —— 正是本项目的迁移目标。

> ⚠️ 这里推翻了早先的一个决定。早先刻意**只**设 `PYTHONIOENCODING`
> （"把影响限制在标准流上、不改变 `open()` 默认编码"）。理由是当时的症状只在
> stdio。现在有反例了：上游大量 `open()` 假设 UTF-8 ⇒ 那个理由不成立，改为两者都设。

## 一个必须记住的判据：**编译成功 ≠ 内容还在**

实测（`tectonic`，同一份 beamer 文档两种写法）：

| 写法 | 合法 UTF-8 | 退出码 | PDF 里「测试标题甲」/「内容乙」/「→」 |
|---|---|---|---|
| 平台默认（cp936） | 否 | **0** | **False / False / False** |
| `encoding="utf-8"` | 是 | 0 | True / True / True |

tectonic 对 GBK 文件只打一句
`Invalid UTF-8 byte or sequence at line N replaced by U+FFFD`，**退出码仍是 0**。
而我们的 `compile_tex` 只认退出码 —— 所以**编码问题必须在写入端解决**，
靠"编译没报错"是发现不了的。

（顺带：写 emoji 这类**不在 cp936 里**的字符会直接 `UnicodeEncodeError` 崩掉；
而 `→`、`≥` 这些在 cp936 里，所以**静默**。两种都要防。）

## 自检

```bat
.venv\Scripts\python.exe scripts\smoke_web_api.py       :: 第 13 组专测这一类
.venv\Scripts\python.exe scripts\verify_musetalk_patch.py --musetalk-root E:/ai-models/MuseTalk
```

第 13 组含两条**反面对照**：① `evaluation/` 里仍能扫出 81 处未指定编码的 `open()`
（证明扫描器本身有效，不是"永远通过"的假绿灯）；② 在**干净环境**（剔除 `PYTHONUTF8`）
下不带 encoding 读那份提示词确实失败（证明这不是假想问题）。

> ⚠️ ② 这条验的是"平台默认"，所以**必须另起进程且剔除 `PYTHONUTF8`**：
> 开发机的 shell 里本身就设了 `PYTHONUTF8=1`（WorkBuddy 宿主设的），
> 直接在宿主进程里测会得到"一切正常"的**错误结论**。我踩过这一脚。
