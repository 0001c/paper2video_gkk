## 1. 从定义表达式到得到结果

我们先看一个真实发生的问题：当你在代码里写下 h = tf.nn.sigmoid(tf.matmul(x, W) + b)，屏幕上并没有打印出任何数字——为什么定义了表达式，却得不到数值结果？


这是因为 TensorFlow 1.x 采用图模式，它把整个计算过程严格拆成三个阶段：第一，定义依赖关系，也就是构建计算图；第二，提供具体数据；第三，执行求值操作。


这就像你写一道代数题：‘设 d = a + b，z = d × c’——这仅仅是符号表达式，没给 a、b、c 赋值前，你无法算出 z。同样，h 的定义只说明‘它由 x、W、b 经过矩阵乘、加法和 sigmoid 得来’，但没告诉系统这些输入到底是什么。


本课路线就围绕这三步展开：先理解计算图如何记录依赖，再认识张量作为‘待求值的输出占位符’的属性，接着用会话（Session）触发实际计算，最后通过示例完整走通流程。


特别注意一个常见误区：定义变量或创建会话本身并不会自动计算结果。比如执行 tf.Variable(...) 只是声明了一个可训练参数，而 session = tf.Session() 仅准备了运行环境——真正产生数值，必须显式调用 session.run() 并传入 feed_dict 提供输入值。


接下来，我们就用一个极简例子 E1 来手算这个过程：给定 a=2、b=3、c=4，表达式 z = (a + b) × c 应该如何分步得到 20？这将帮我们看清‘定义’与‘执行’之间那道关键的鸿沟。

## 2. E1：计算图的两步运算

我们刚刚看到，定义表达式 h = tf.matmul(x, W) + b 并不会自动给出数值——现在就用这个极简例子 E1 来亲手走一遍：为什么必须分两步算？


教材符号是 d = a + b，z = d * c；这描述的是依赖关系：z 的计算必须等 d 算完才能开始。


但符号本身没有数字，所以我们教学补充一组具体值：a = 2，b = 3，c = 4——注意，这些数值仅用于本例手算解释，不是原书给定，也不代表真实模型参数。


第一步：执行加法操作（Operation），把 a 和 b 的值代入，得到 d = 2 + 3 = 5。这里 d 是一个张量（Tensor），它此刻代表‘已求值的结果’，即标量 5。


第二步：执行乘法操作（Operation），把上一步输出的 d 和 c 代入，得到 z = 5 × 4 = 20。z 同样是一个张量，此时它的值是 20。


关键在这里：Operation 负责‘做什么’——比如加、乘；Tensor 负责‘产出什么’——它是操作的输出，可能尚未求值（如定义阶段的 z），也可能已是具体数值（如执行后的 z=20）。


学生常犯的错误是：以为写了 z = d * c 就等于 z = 20。其实不然——在 TensorFlow 图模式里，这行代码只创建了两个节点和一条数据边，系统只记下‘z 依赖 d 和 c’，并不计算。真正触发计算，必须通过会话（Session）显式运行。


再想一个问题：如果 c 没给值，只设 a=2、b=3，你能算出 z 吗？不能——因为 z 依赖 c，而 c 是未提供的输入。这正说明：定义图 ≠ 提供数据 ≠ 执行求值。三者缺一不可。


接下来我们会看到，张量除了数值，还有更重要的属性：它的秩、形状和名字——这些决定了它在图中如何被连接、广播与索引。我们下一页就讲清楚这些。

## 3. 张量的秩、形状与名字

上一节我们看到，z = d * c 这个表达式在图中只记录依赖，不产生数值——那系统怎么知道这个 z 到底是标量、向量还是矩阵？它有多少个元素？又该和谁连接？


答案就藏在张量的三个核心属性里：秩、形状与名字。


秩（rank）就是轴的数量。比如一个向量 [1,2,3] 只有一行数据，它只有一个轴，所以秩是1；而矩阵 [[1,2,3],[4,5,6]] 有两行三列，两个轴，秩就是2。


shape 描述的是各轴的长度。向量 [1,2,3] 的 shape 是 [3]，表示第一轴长为3；矩阵 [[1,2,3],[4,5,6]] 的 shape 是 [2,3]，表示第一轴2个元素、第二轴3个元素。


dtype 是元素的数据类型，比如 tf.float32 或 tf.int64，它决定了每个元素占多少内存、支持哪些运算。


这里有个易错点：学生常把‘元素总数’当成秩。注意——[1,2,3] 有3个元素，但秩是1；[[1,2,3],[4,5,6]] 有6个元素，秩却是2。秩只数轴，不数数字。


再看名字：add:2 表示 add 节点的第三个输出——因为索引从0开始，:0 是第一个，:1 是第二个，:2 就是第三个。


为什么需要名字？因为在复杂图中，一个操作可能产出多个张量（比如 split 操作），必须靠后缀编号区分它们；同时，名字也用于 fetch——你调用 session.run(h) 时，系统正是靠名字定位到那个张量节点。


最后提醒一条关键规则：数据边负责传值，控制边只约束先后顺序。比如你加一条控制依赖，它不会给下游节点多送一个数值，只是说‘等我做完你再开始’。


现在你可以试着回答：如果某张量 shape 是 [4,1,5]，它的秩是多少？共多少元素？——答案是秩3, 元素总数 4×1×5=20。这个判断能力，将直接决定你能否正确连接 x 和 W 的矩阵乘法。

## 4. 会话负责执行和资源管理

上一节我们明确了张量的秩、形状与名字——这些属性在图构建阶段就已确定，但它们仍只是‘蓝图’，没有数值。那么问题来了：谁来把这张蓝图变成实际计算？谁来管理CPU或GPU上的内存与计算资源？


答案是：会话（Session）。它负责执行和资源管理。


整个过程严格分两步：先构图记录依赖，再运行所需计算。你写 h = tf.matmul(x, W) + b 时，系统只在图中添加节点并连好边，不产生任何数值；直到你启动会话并调用 run，它才按依赖关系真正算出结果。


Session.run 的作用很明确：你请求某个张量（比如 h），它就自动追踪所有前置依赖，只执行必要子图，返回你想要的结果。注意——它不会多算，也不会少算；你没请求的梯度或中间变量，它根本不去碰。


这里有一个关键误区必须澄清：创建会话 ≠ 自动求所有梯度或训练。教材第13页曾笼统说‘启动Session会自动计算梯度’，这是不严谨的。实际上，run 只执行你显式 fetch 的张量及其依赖；梯度需要你额外定义 grad = tf.gradients(loss, vars)，并把它作为 fetch 目标传给 run。否则，W 和 b 的值永远不会更新。


还有一点常被忽略：会话占用系统资源。一旦你完成计算，必须显式关闭它——session.close() 或用 with session: 语句块——否则内存和设备句柄将持续被占用，尤其在循环中反复创建会话会导致显存泄漏。


举个教学小例子：假设你定义了 z = (a + b) * c，且 a=2, b=3, c=4。即使你已构造完整图，z 的值仍是未知的；只有当你创建会话、调用 session.run(z)，系统才依次算出 d=a+b=5，再算 z=d*c=20。这个过程完全由会话驱动。


现在请你思考：如果我只调用 session.run(d)，而没请求 z，那么 z 会被计算吗？——不会。系统只会算到 d 就停止。这正是‘按需执行’的核心优势：避免冗余计算。


下一节我们将看到：在真正执行前，你还得解决两个关键问题——哪些数据要运行时提供？哪些参数需要初始化？这就要引入占位符与变量的概念。

## 5. 占位符与变量：谁供值，谁初始化

上一节我们讲了会话如何驱动执行，但会话本身并不知道‘数据从哪来’、‘参数初始值是多少’——这正是本页要解决的核心问题：占位符与变量的分工。


x 是占位符（placeholder），它在图构建阶段只声明形状和类型，比如 shape=[1,10]、dtype=float32；真正的数值必须等到运行时，通过 feed_dict 字典提供。你可以把它想象成一个空插座：图纸上画好了插孔位置，但通电前必须插进电源线。


而 W 和 b 是变量（Variable），它们代表模型中需要学习或手动设定的参数。变量在图中不仅有形状，还自带‘初始值生成逻辑’——比如 W 由 tf.random_uniform([10,5]) 生成随机数，b 由 tf.zeros([5]) 初始化为零。


这里有个高频误区：定义初始化器 ≠ 已经执行初始化。就像你写好‘把电池装进遥控器’的说明书，不等于遥控器已经能开机。你必须显式调用 session.run(tf.global_variables_initializer())，系统才会真正把随机数或零值写入 W 和 b 的内存位置。


整个执行流程是严格有序的四步：先初始化变量 → 再通过 feed_dict 提供 x 的具体数值 → 然后求值 h → 最后关闭会话释放资源。漏掉任何一步，都会报错：未初始化的变量访问会触发 FailedPreconditionError，未提供的占位符会报 InvalidArgumentError。


特别注意：本例仅为单次前向求值，即给定输入 x，算出输出 h；它不包含训练循环，因此 W 和 b 的值在本次运行中不会更新。如果你误以为‘只要 run 一次就自动训练了’，那就会混淆推理与训练两个阶段。


现在请你思考：如果我跳过初始化步骤，直接 run(h)，会发生什么？——答案是报错，因为 W 和 b 还是未定义状态。这正说明：变量必须显式初始化，而占位符只需在 run 时提供值，二者职责截然不同。

## 6. E2：沿教材代码核对形状

上一节我们明确了占位符与变量的分工：x 是运行时通过 feed_dict 提供值的占位符，W 和 b 是需要显式初始化的变量。


现在我们进入本节核心任务：沿教材代码严格核对前向计算中每一步的张量形状——这不仅是形式检查，更是避免维度错位导致崩溃的关键防线。


先看第一层运算：x 的 shape 是 [1,10]，W 的 shape 是 [10,5]。矩阵乘法要求左矩阵列数等于右矩阵行数，这里内维 10 完全匹配，因此 tf.matmul(x, W) 的结果 shape 必为 [1,5]。


接着加偏置项 b，它的 shape 是 [5]。在 TensorFlow 中，加法遵循广播规则：当两个张量最后一轴长度一致时，较短张量会沿前面的轴自动扩展。这里 [1,5] + [5] 相当于把 b 复制 1 行，结果仍是 [1,5]。


然后应用 sigmoid 函数。注意：sigmoid 是逐元素非线性变换，它不改变输入张量的形状，只对每个标量独立计算 1 除以（1 加 e 的负 t 次方）。因此 h 的 shape 依然保持 [1,5]。


再看参数规模：W 是 10 行 5 列的矩阵，共 10×5=50 个可训练标量；b 是长度为 5 的向量，含 5 个标量。两者合计 55 个自由参数——这就是这个单层网络的全部可调权重数量。


这里必须强调一个易错点：x 和 W 的数值是随机生成的，教材代码中未指定具体种子或固定值，因此我们绝不能编造唯一的 h 输出数值。比如有人说‘算出来 h 是 [0.6, 0.3, …]’——这是错误的，因为每次 run 都可能不同。


最后确认运算顺序：代码明确写的是 x 乘 W，即 tf.matmul(x, W)，不是 W 乘 x。矩阵乘法不可交换，若误写成 tf.matmul(W, x)，shape 将因内维 5≠10 而报错。请务必以代码为准，而非公式简写习惯。


现在请你思考：如果我把 b 的 shape 写成 [6]，会发生什么？——答案是广播失败，TensorFlow 会抛出 InvalidArgumentError，提示维度不匹配。这正说明：形状核验不是可选项，而是执行前的强制校验。


接下来我们将看到：当这张图被提交给会话执行时，背后实际是由 client、master、worker 协同完成的——为什么需要这种分层架构？它如何确保只计算你真正请求的部分？我们下一页就来拆解这个执行引擎。

## 7. 从客户端到实际执行设备

上一节我们核对了前向计算中每一步的张量形状，确认了 x 乘 W 得到 [1,5]、加 b 后仍为 [1,5]、sigmoid 不改变形状——这些数值规则保障了图能正确构建。但图建好了，谁来真正把它算出来？


这就引出本节核心：从客户端到实际执行设备的分工机制。系统不是靠一个黑箱直接跑图，而是通过三层职责协作完成求值。


首先，client 是你写代码的地方——它负责提交整张计算图，并发出‘请计算 h’这样的执行请求。注意：client 不执行任何运算，它只发起指令。


接着，master 接收这个请求，它像一个调度员：分析图结构，识别哪些子图是计算 h 所必需的依赖路径，然后把任务切分给执行单元。它不碰数据，只管协调与划分。


最后，worker 真正干活：它拿到分配到的子图片段，调用 CPU 或 GPU 硬件，逐个执行加法、矩阵乘、sigmoid 等操作，把中间结果传回，最终拼出 h 的数值。


这里有个关键澄清：在单机实验环境下，client、master、worker 的职责完全可以由同一个 Python 进程承担——它们是逻辑角色，不是物理机器。你不需要三台电脑，一台笔记本就能完整走通整个流程。


更重要的是，系统绝不会‘全图跑一遍’。它严格遵循‘只执行请求结果所需的依赖’原则：比如你只 fetch h，它就只算从 x、W、b 到 h 的路径；若图中有个 add 节点不在该路径上，根本不会被触发。


现在请你思考：如果图里有个未被依赖的节点，比如一个孤立的 tf.constant(42)，它会被执行吗？——答案是不会。这再次说明：定义图 ≠ 执行图，而执行引擎的分层设计，正是为了精准、高效地响应你的 fetch 请求。

## 8. 回顾：把一次求值完整串起来

现在我们把前面七节课的知识串成一条完整的执行链：从定义图开始，到最终拿到数值结果。


第一步是定义图与张量——你写下x、W、b、h这些符号表达式，系统只记录它们的依赖关系和属性，比如x的shape是[1,10]，W是[10,5]，此时没有任何数值产生。


第二步必须显式初始化变量：W和b是Variable，它们的初始值由tf.random_uniform和tf.zeros生成，但这些值不会自动装入图；你需要调用tf.global_variables_initializer().run()才能让W和b真正拥有数值。


第三步提供输入：x是placeholder，它本身没有值，必须在Session.run时通过feed_dict={x:某矩阵}传入具体数据；若漏掉feed_dict，系统会报错‘未提供占位符x的值’。


接着调用Session.run(h)，系统才真正执行：它沿依赖路径计算matmul(x,W)→加b→sigmoid，最终返回h的数值；取回后记得关闭会话释放资源。


检查第一个问题：缺少feed_dict会怎样？——会抛出InvalidArgumentError，因为placeholder无默认值；缺少初始化呢？——W和b仍为未定义状态，run时触发FailedPreconditionError。


检查第二个问题：为何x乘W得到[1,5]？——因为x是[1,10]行向量，W是[10,5]矩阵，内维10匹配，矩阵乘法规则决定输出shape为[外维1, 外维5]，即[1,5]；这是形状推导的刚性规则，不是近似或约定。


最后强调：定义图是建模，执行是求值，训练是反复更新变量——三者阶段不同、操作不同。本例中只有单次前向求值，没有优化器、没有梯度、没有循环，因此绝不能说‘已经训练了模型’。


至此，你已能完整复现一次TensorFlow 1.x风格的求值流程：建图→初始化→喂数据→run→取结果→关会话。
