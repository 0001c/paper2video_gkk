# 事故与排查记录：光标定位"卡住" + 测试清理误删运行中任务

> 时间：2026-09-19 01:13–01:30
> 涉及任务：`job_0919_004702_866d`（13 页，中文幻灯片 + 中文讲稿，音色=预置「白桦」）
> 结论：**光标定位没有卡死**（已完成 18 条 VLM 回退指令）；但排查过程中**我自己的测试清理删掉了这个正在运行的任务目录**。

---

## 一、现象

使用者在 01:13 报：前端页面卡在「光标定位」，显存占用 15.3 GB 已持续 10 分钟。

## 二、现场证据（01:13）

| 项 | 观察值 |
|---|---|
| `job.json` | `status=running`，`phase_key=struct`（**陈旧字段**，见下） |
| `progress.jsonl` | 最后一条是 01:01:17 的 `{"phase": "cursor"}`（只有阶段边界） |
| `run.log` | 14892 字节，最后写入 **01:06:46**（已静默 6.5 分钟） |
| GPU | 98% util / 15672 MiB（≈15.3 GB） |
| 进程 | `pipeline.py` 父(22484, 1 线程) + 子(29348, 36 线程, 106% CPU) |

**为什么界面显示"光标定位"而 job.json 显示"struct"**：`read_progress` 优先用
`progress.jsonl` 的阶段（那是流水线真报的），`job.phase_key` 只在阶段边界被写
（结构化/启动/收尾），流水线内部的阶段它不跟踪 —— 界面是对的，job.json 那个字段
在运行期间是陈旧的（不影响行为，但读起来会困惑）。

## 三、真因 1：光标阶段的进度**在界面上完全不可见**（已修）

40 秒连续观察后日志开始增长 → 它在动，只是**慢且不可见**：

```
[cursor_gen] PDF 文本定位命中 34/52 条（其余回退 GUI-Owl）
[cursor_gen] 单卡串行模式，共 18 条指令
[cursor_gen] 10/18          ← 只有这一行（每 10 条才打印一次）
[cursor_gen] 已释放 GUI-Owl
```

- GUI-Owl 那 18 条回退指令实际耗时约 **12 分钟**（01:02 → 01:14），其中**某一条
  6 分半**（其余约 30 秒/条）；
- 而 `cursor_gen` 只在 `(idx+1) % 10 == 0` 时打印 ⇒ 那 6 分半里日志一动不动；
- `progress.jsonl` 里光标阶段**只有一条阶段边界记录** ⇒ 界面只有"光标定位"四个字。
  ⇒ "在动"与"卡死"在界面上**无法区分**。使用者的判断完全合理。

**已修**：

1. `cursor_gen` 逐条打印耗时，并 `progress_report.report("cursor", done=k, total=N)`；
2. 阶段模型把"计数"做成通用能力，新增 `unit`：语音/数字人 = **页**，光标 = **条**，
   前端显示「第 k / N 条」；
3. 卡住阈值按阶段给：**光标 600 秒**（单条 VLM 调用可以合法地慢），数字人 420 秒，
   其余 300/180；
4. 顺带修掉一个很阴的坑：`total_pages` 原先取**所有**进度记录 `total` 的最大值，
   而光标的 total 是"指令条数"（18）⇒ 会得出"18 页"，而界面显示「第 k/18 页」
   看着还挺正常。现在只有 tts/talking 的 total 计入页数。

## 四、真因 2 / 事故：测试清理删掉了**正在运行的任务**（已修 + 已恢复）

### 经过

01:17 为验证改动运行全量冒烟测试。`test_pages_and_rerun` 的 `finally` 里写的是：

```python
for name in os.listdir(app.JOBS_ROOT):
    if name.startswith("job_") or name.startswith("smoke_"):
        shutil.rmtree(os.path.join(app.JOBS_ROOT, name), ignore_errors=True)
```

**"凡是 `job_` 开头就删"** ⇒ 把使用者的任务目录整个删掉：
`job.json`、`result/`（已生成的 13 张幻灯片 + 13 段音频）、`latex_proj/main.tex`、
`progress.jsonl` 全部丢失。`run.log` 幸存，因为**Windows 不允许删除正在被写入的文件**
—— 这也解释了现场"只剩一个 run.log"这种特征。

单人测试环境下 `jobs/` 里只有测试自己的目录，所以这个写法长期"看着没问题"。

### 影响

- 数字人阶段**能跑完**：它在 01:13:55 就把 13 页的输入 staging 进了 MuseTalk 自己的
  workspace，产物会写回（被重建的）`result/talking_musetalk/` 下；
- 但**合片阶段必然失败**：缺幻灯片 / 音频 / 字幕；
- 损失口径：stage 1/2 已花的 API 费用 + 约 25 分钟机器时间需要重跑。

### 已做的修复

| 位置 | 改动 |
|---|---|
| `test_pages_and_rerun` | 进函数拍 `jobs/` 快照，`finally` **只删差集** |
| `_cleanup_orphan_jobs` | 加护栏：①只删**本次测试期间**改动过的（`started_at` 之前存在的一律不碰）；②"没有 job.json"不足以判定是测试残留 |
| 新增行为断言（第 9 组 I 段） | 造"1 小时前建的无 job.json 目录"与"刚建的无 job.json 目录"，断言只删后者 |

验证：修复后重跑全量（167 项通过），使用者的任务目录**活了下来**。

### 恢复

用**运行中进程的完整命令行**（27 个参数）+ 日志里的 `[voice]` 行重建了 `job.json`
（含 `config` / `ref_img` / `paper_latex_root` / `argv`），任务重新出现在任务列表里、
收尾时会被正常写成 `failed`，而不是从界面上凭空消失。

**建议的恢复路径**：等数字人跑完（约 01:28）后，用续跑接口起一个
`stages=["1","2","3"]`、`reuse_script=false` 的任务 —— 它复用同一个产物目录，
于是幻灯片/讲稿/音频重跑（一次 API 费用），而**数字人 13 页会被跳过**
（`talking_gen` 对已存在的 `merge_video.mp4` 直接跳过），省约 10 分钟 GPU。

## 五、规矩（已写进跨项目记忆）

1. **共享目录里的清理只能用"进入作用域前 vs 现在"的快照差集**；名字前缀/模式
   只用来辅助判断，绝不能作为删除依据 —— 前缀是别人也在用的命名空间。
   判据：删共享目录里的东西前，先问"它可能是别人正在写的吗？"不确定就别删
   （留一个空壳的成本 << 删错一份数据的成本）。
2. **`done/total` 这类计数要先确认单位再聚合**：多阶段都用同名 `total` 但单位
   可能不同（页 / 条），混在一起取 max 会得出荒谬结论，而界面还显示得很正常。
3. **Windows 特征**：目录被 `rmtree` 后若"只剩一个日志文件"，说明那个文件当时
   正被写入 —— 可用来快速判断"是被删的"而不是"没生成"。

## 六、遗留

- **那条 6 分半的指令为什么慢，原因未知**：当时没有逐条耗时记录，也没有那条的
  模型输出。已加逐条耗时打印，下次出现可直接定位（可能是生成长度异常、
  或该页图像/指令特别大）。不在没有证据的情况下给结论。
- 15.3 GB 显存是数字人阶段的正常占用（MuseTalk unet + whisper + 人脸解析 + VAE），
  该阶段与「光标定位」无关 —— 界面显示的光标是**进度没更新**，不是显存没释放。
