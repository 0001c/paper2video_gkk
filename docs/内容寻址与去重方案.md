# 内容寻址与去重方案（评估）

> 起因：使用者提出「按指纹寻址作用更大，还能避免同一份文件在服务端重复保存」。
> 本文给出实测数据、收益排序、必须先解决的三件事，以及分阶段落地路径。
> **状态：阶段 1 与阶段 2 已实施**（2026-09-19），见文末「实施记录」；阶段 3 待定。

## 一、实测：重复确实在发生

对 `jobs/` 下所有上传素材按内容 sha1 分组（2026-09-19 01:38 实测）：

| 内容 sha1 | 大小 | 副本数 | 位置 |
|---|---|---|---|
| `86ea0bb70e0b` | 1488 KB | **3** | `ingest_cb7bc0be` / `ingest_e00fceef` / `ingest_e168d6d1` |
| `4f215ea0a950` | 335 KB | **3** | `ingest_12efe75c` / `ingest_2b5177a9` / `ingest_9632a7e2` |
| `6c62b9bc3332` | 57 KB | **3** | 三份 `ingest/*/paper_text.md` |
| `f6edd2a0e351` | 127 KB | **2** | `portrait_07bead43` / `portrait_2ed9bbf6`（同一张 `15861 (2).jpg`） |
| `13e43bdc5d8f` | 21 KB | **3** | 三份 `ingest/*/paper_text.md` |

**重复占用合计 3.8 MB。**

原因很直接 —— 三个上传端点都用随机 id，没有任何去重：

```python
tmp_id = "ingest_"   + uuid.uuid4().hex[:8]      # web/app.py:1095
tmp_id = "portrait_" + uuid.uuid4().hex[:8]      # web/app.py:1151
tmp_id = "voice_"    + uuid.uuid4().hex[:8]      # web/app.py:1276
```

对照：`jobs/_voices/` **已经是内容寻址**（文件名 = `sha1[:16]`，见 `app.py:1306`），
实测命中缓存 0.01 秒 —— 音色因为天生是"生成物需要缓存"，早就是这套做法。

## 二、但收益要排序：磁盘不是主要那条

| 收益 | 量级 | 说明 |
|---|---|---|
| ① **省 API 费用** | **最大** | 同一篇论文重复进入时，`main.tex`（结构化，实测 10482 token / 20 秒）可复用；再往前一步，幻灯片 + 讲稿（讲稿占一篇 token 的 **76%**）也可复用 |
| ② **防静默错配** | 大 | 指纹是判据的基础：输入变了指纹就变，天然不会误跳过（直接解掉 `技术风险-数字人跳过判据不含音频.md` 那个缺陷） |
| ③ 省磁盘 | **最小** | 输入侧实测只有 **3.8 MB**（上传的 PDF/图片本来就小），单任务 `result/` 就有 15.7 MB —— 而这是**只剩下数字人分片的残缺任务**，完整任务还含幻灯片 PNG、音频、中间 mp4 |

也就是说：**结论仍然成立，但主要理由应该是①，不是③。**
"避免重复保存"在输入侧省的是 MB 级；真正贵的是"同一篇论文第二次还要再付一次 token"。

## 三、必须先一起解决的三件事

### 1. 隐私边界（最硬）

内容寻址**天然是跨用户共享的**，放到多人服务器上就是两类事故：

- 共享**输入**库 ⇒ B 上传时发现"文件已存在" ⇒ 能推断出 A 上传过什么；
- 共享**产物**库 ⇒ 更严重：成片里有**上传者本人的脸和声音**，B 拿到的是 A 的成片。

⇒ 两条硬约束：

- **输入文件的去重只在同一用户内做**（`jobs/_users/<uid>/ingest/<sha1>/`）；
- **产物指纹必须包含全部影响输出的输入** —— 论文正文、人像、讲稿配置、音色。
  指纹相同即意味着"双方本来就有同样的输入"，此时共享才没有隐私问题。
  ⚠️ 少一个字段就会跨出隐私边界（这正是 `技术风险` 那篇里"只看页号 + 人像名"的教训）。

### 2. 引用计数 / 删除语义

内容寻址下同一份文件被多个任务"指向"，**按任务删除就会误删别的任务还在用的文件**，
症状是别处静默 404 或 "缺少幻灯片"。

⇒ 要么做引用计数，要么规定"内容库只增不删、由独立 GC 统一清理"。
这与本次误删事故是同一类问题：**删之前先问"谁还在用"**。

### 3. 不可变性

内容寻址的前提是文件**永不就地修改**。本仓库有就地改写的地方
（`_stage_inputs` 把参考图铺白底另存、MuseTalk 补丁直接改上游源码、
`_prepare_latex` 会写 `main.tex`）。

⇒ 哈希**只对原始上传文件**计算，派生文件一律不参与寻址。
派生结果的缓存键要额外带上**处理版本号**（提取器版本 / 模板版本），
否则换了预处理逻辑却仍命中旧缓存 —— 这是内容寻址最经典的坑。

## 四、分阶段落地

**阶段 1：输入按内容命名（改动最小，立刻见效）**

- `ingest_/portrait_` 的目录名从 `uuid4[:8]` 换成 `sha1[:12]`，放按用户分桶的子目录；
- 指纹 = `(原始文件 sha1, 提取器版本)`，版本变了就重新提取；
- 直接收益：同一篇论文重复上传 ⇒ 同一个目录 ⇒ **`main.tex` 天然复用，省一次结构化**。

**阶段 2：把指纹接进产物跳过判据**

- 每个产物页目录落 `.inputs.json`：记录参考图、音频的 sha1 与 size；
- 跳过前比对，不一致就重生成 —— 一次修掉「跳过判据不含音频」那个缺陷。

**阶段 3：产物目录按完整指纹寻址（可选）**

- fingerprint = (正文, 人像, 讲稿, 音色) → 目录按指纹命名；
- 此时才需要引用计数 / GC。

## 五、验收判据

1. 同一份论文连传两次，`jobs/` 下**只有一个** ingest 目录，且第二次不再产生结构化 API 调用；
2. 同一张人像连传两次，只有一个 portrait 目录；
3. 换了人像或讲稿后，数字人阶段**不再跳过**（对比 `.inputs.json`）；
4. 删除任意一个任务目录后，另一个任务的产物仍可访问（引用计数有效）；
5. 跨用户不可见：A 的内容库在 B 的会话里查不到。

## 六、待决策

**输入文件的去重范围**：只在同一用户内（安全，推荐）？
还是允许"同一课题组/同一台服务器共享一份论文库"（省更多磁盘与 token，
但等于承认"谁传的论文在服务器上互相可见"）？

这条决定阶段 1 的目录结构，建议先定它。

## 实施记录（2026-09-19）

### 阶段 1：输入按内容寻址 ✅

`web/app.py` 新增区块「上传内容库（内容寻址）」：

```
jobs/_content/<sha1[:12]>/
    meta.json          # sha1 / kind / size / original_names / created_at
    input/<sha1[:12]><扩展名>    # 原始上传件，**不可变**
    ingest/            # 派生：paper_text.md + ingest_meta.json（仅论文）
```

- **唯一入口**：`_upload_work(upload_id)` 负责把上传 id 解析成目录。
  新旧两种 id 都认：`content_<sha1[:12]>` 与任何**单个路径段**的名字（老 `ingest_<随机>`）。
  校验的是「只有一个路径段、不以点开头」而不是「前缀在白名单里」——
  前缀白名单挡不住 `content_../..`，却会误伤手工/工具建的目录名。
- 三个上传端点全部改造：`/api/ingest`、`/api/portrait`、`/api/voices/upload`
  （音色上传改成用临时文件，最后一个随机 id 目录也去掉了）。
- **命中判据**：文件内容 sha1（隐含在目录名里）
  + `paper_ingest.EXTRACTOR_VERSION`（**改了提取逻辑必须 +1**，
  否则会命中旧缓存且不报错）。
- 派生的 `paper_text.md` 仍会**按任务复制一份**到 `<job_dir>/ingest/`
  —— 让任务自包含：内容库将来被 GC 也不影响已完成的任务。
- 任务记录新增 `ingest_id` 与 `source_digest`（溯源 + 阶段 3 的缓存键上半截）。
- 失败路径：提取失败时只清 `ingest/` 派生目录；**内容目录只在"这次新建、且 id 还没
  被返给任何人"时才删**（那时不可能有引用）—— 判据写进注释了，别改成无条件删。

实测（真实 HTTP，同一份 1.5 MB PDF 连传两次）：
两次同一个 `content_86ea0bb70e0b`、第二次 `cached=true`；换文件名仍是同一份；
库里只有 `input/86ea0bb70e0b.pdf` 一份；原名记在 `meta.json` 的 `original_names`；
人像同样（`f6edd2a0e351.jpg`，1262×1262）。

⚠️ **诚实说明收益**：本地提取本身只要 0.2 秒（零 API 成本），所以
"第二次秒出"感知不强。阶段 1 真正的价值是**不重复落盘**与**为阶段 3 铺路** ——
钱在后面的 LLM 步骤（结构化 + 讲稿），那要等 main.tex / 讲稿接进指纹才省得到。

### 阶段 2：指纹接进产物跳过判据 ✅

见 `docs/技术风险-数字人跳过判据不含音频.md` 文末「已实施」。
每页产物目录落 `.inputs.json`（参考图 + 音频的 size/sha1），跳过前比对；
任何不确定都判为「不能复用」。

### 阶段 3：产物按输入指纹寻址 ✅（2026-09-19 实施）

新增 `scripts/artifact_cache.py`。整条链路只有两步联网付费，这两步的产物按指纹缓存：

```
jobs/_cache/
    struct/<指纹>/main.tex           正文 + 论文类型 + LLM → LaTeX 工程
    deck/<指纹>/slide_imgs/          上述 main.tex + 两种语言 + 两个模型
               slides_rendered.pdf   + 数字人档位 → 幻灯片 + 讲稿
               subtitle_w_cursor.txt （讲稿是**唯一必须联网付费**的 stage 2 步骤，
                                     实测占一篇 token 的 76%）
```

**两类指纹各有一份写死的字段表**（`STRUCT_FIELDS` / `DECK_FIELDS`），加字段前必须
回答一句「它会改变产物吗？」，因为两个方向都会出错：

| 方向 | 后果 |
|---|---|
| 少一个字段 | 输入不同却命中 → **静默产出错误内容**（数字人跳过判据那次就是这个病） |
| 多一个字段 | 输入变了其实输出不变却重算 → **白花一次钱** |

所以 `struct` 刻意**不含**语言/人像/音色，`deck` 也**不含**人像/音色 ——
实测断言证明了这点：「换头像」「换声音」不会让两份指纹变（缓存继续可用），
而「换讲稿语言」「换模型」「改论文类型」一定会变。

**命中后的动作**：把缓存的幻灯片与讲稿复制进本次产物目录，`stages` 收敛成
`["2", "3"]`、`reuse_script=True` —— 于是 stage 1 不再生成幻灯片、stage 2 不再调
VLM（pipeline 自己还会用 `validate_script_output` 复查一遍讲稿，缓存损坏也不会被
当成好讲稿用）。剩下 TTS / 光标 / 数字人 / 合片照常跑（本地 GPU，不花钱）。
若用户只要 stage 1 而幻灯片已命中，则**连流水线进程都不起**。

**只增不删**：模块里**没有任何删除实现**（有一条静态断言守着），
`plan_gc()` 只读地列出「无人引用」的候选（判据是任务记录里的 `cache.*_key`），
删不删由人决定。另有 `force_regenerate` 逃生门：传了就完全不碰缓存。

#### 写这一版时踩到的三个真问题（都不是猜的）

1. **写入键 ≠ 查询键 ⇒ 缓存永远命中不了，且不报错。** 最初 publish 时重新算指纹，
   而流水线可能改写 `main.tex`（指纹的输入之一）—— 于是写入和查询落在不同的键上，
   功能静默失效。改成**键只算一次**：`lookup_*` / `publish_*` 都接一个 `key=`，
   由调用方把查询时那个键一路带下去。
2. **输入取不到指纹时会「塌成同一个键」。** 这条是**测试暴露的**：两个输入完全不同、
   但都取不到指纹的任务，字段都是 `None` → 指纹相同 → 后跑的直接拿到前一个的产物。
   修法：`REQUIRED_FIELDS` 规定「输入必须可辨认」，缺了就**既不命中也不写入**
   （代价是退化成不用缓存，多花一次钱；换来一定不会拿错产物）。
3. **命中改动的 config/argv 没落盘。** `_run_job` 会就地改 `config.stages` /
   `reuse_script` 并重建 argv，但收尾只写了 `exit_code`/`elapsed_min`/`cache` ——
   于是任务记录里看到的还是"请求时的样子"，实际跑的是另一套参数，
   事后没人能解释「为什么这次没跑 stage 1」。现在两者都会落盘。

#### 测试

第 12 组 **54 项断言**，其中最有价值的是**两阶段端到端**：
先用假流水线跑一次（它会造出幻灯片与讲稿）→ 断言缓存被回写；
再用**完全相同的配置**跑第二次 → 断言 `deck_hit`、`config.stages == ["2","3"]`、
`reuse_script=True`、真实 `_build_argv` 过一遍确认这两项真的落到命令行、
缓存的幻灯片确实被复制进产物目录、日志里写明「省下了什么」。
外加反面对照（改讲稿语言 → 不许命中）与静态守卫（命中检查必须在 `_prepare_latex`
**之前**，放后面就等于"钱花了才想起可以省"）。

#### 还没做的

- **GPU 侧的产物**（TTS 音频 / 光标 json / 数字人分片 / 成片）没进指纹缓存。
  它们不花钱、只花时间，而阶段 2 已经保证「输入变了不会被误跳过」。
  真要做的话，`deck` 那套机制可以照搬（多一个 `render` 类目）。
- 界面上还没显示"本次命中了缓存"（后端 `job.cache` 已有完整信息，日志里也有）。

### 老目录怎么办

不自动迁移：老任务的 `source_path` / `ref_img` 是**绝对路径指进老目录**的，
动它们等于改历史记录。实测统计（2026-09-19 02:0x）：

| 情况 | 数量 | 例子 |
|---|---|---|
| 已被某个任务引用 | 4 | `ingest_cb7bc0be`、`ingest_e168d6d1`、`portrait_07bead43`、`portrait_2ed9bbf6` |
| 无人引用、且内容已入库（可删，但没删） | 1 | `ingest_e00fceef` |
| 无人引用、内容也还没入库 | 6 | 3 份重复的《议程设置》PDF、`2609.14542v1.pdf`、两张旧人像 |

合计可回收约 1.2 MB —— **不值得为它去动历史记录**。
判据是"谁还在用"，不是"名字长什么样"（这条是踩过误删事故才写的）。
